scripta-metrics-report

scripta-metrics-report turns a frozen copy of a book plus optional annotations into one validated assessment bundle and the five readable reports rendered from it. It measures what deterministic code can measure, states a reason for everything it cannot, and keeps every score advisory. It is a separate-phase skill: it is chosen for a review and never runs while a chapter is being written.

What the skill covers

Reports are useful only if a reader can trace a number back to the text that produced it, and dangerous if an unavailable measurement is rendered as a zero. The skill is built around that distinction. It reads an assessment packet, which is a frozen copy of one accepted version with a manifest of hashes and sizes, and it writes one bundle in which every result names its method, inputs, coverage and limits. Deterministic code measures similarity, exact overlap, rule adherence, contamination from a verifiable dataset record and efficiency from opt-in timing; everything that needs judgement comes from supplied annotations or is reported as unavailable with its missing prerequisite written out.

The folder contains SKILL.md with the contract, references/metric-catalog.md with every metric definition, references/literary-rubric.md with the eight interpretive indicators, references/report-contract.md with the bundle and view contract, references/calibration.md with the proposed calibration protocol, references/literary-cases.md with the synthetic case library, skill.json as the catalog manifest, dependencies.md as the local dependency record, scripts/build-report.mjs as the report executable, scripts/validate-cases.mjs as the validator of the case library, scripts/lib/ with the loading, measuring, aggregation, assembly, rendering and case-validation modules and fixtures/literary-cases/ with the cases themselves.

The skill also publishes the vocabulary it accepts, so that a producer of annotated observations can build a document the report will validate instead of guessing its lists. schema/annotations.v1.json states the metric and indicator statuses, the indicator identifiers with their source categories, the segment kinds, the EAP orderings, the finding kinds, severities, certainties and statuses, the departure statuses and the rating scale, and the validators under scripts/lib/ remain the authority on what is accepted. The annotation stage of a review composes its prompt from those published lists, so the two sides cannot drift apart silently: tests/vocabulary.test.mjs drives the real validators with the published values and with values outside them, and it fails whenever a published list and the validators disagree.

fixtures/literary-cases/ holds 24 paired short texts, twelve Romanian and twelve English, written for this repository as synthetic teaching and regression material. Each pair keeps its text and changes exactly one literary feature, so a reading, an annotation prompt or a rule can be checked against text whose intended effect is known; the cases anchor their expected evidence at real UTF-8 byte offsets and record acceptable alternative readings and an explicit synthetic provenance. A declared subset is reserved for prompt-regression checks. The library is not a human benchmark: its index declares human_benchmark: false, every case is labelled synthetic, and node scripts/validate-cases.mjs prints the counts or exits 2 with one problem per defect. Evaluator agreement is kept separately in model-agreement.json, which currently reports status: "unperformed" because no evaluator has been run against the library.

Command and inputs

node skills/scripta-metrics-report/scripts/build-report.mjs --input <packet-dir> --out <result-dir> --profile <profile.json> [--annotations <annotations.json>] [--corpus <manifest.json>] [--trigger <request|arc>] [--arc-id <id>]

The packet is an assessment-input.v2 document: every declared path is validated through real paths, every file is checked as UTF-8 against its byte count and hash, and the accepted-version identity is recomputed and compared with the declared one. A missing manifest, a superseded schema, a duplicate path or artifact identifier, a path escape including a symlink, a missing file, a byte or hash mismatch, a stale version, an undeclared role, an invalid encoding or a dishonest scope is refused with the shared rejection code and exit status 2, and nothing is written. A declared partial packet names the chapters it omits, and a textual_only packet carries prose alone, in which case the reports state that no continuity context was available instead of implying a clean book.

--trigger names the event that caused the run and defaults to request; --trigger arc requires --arc-id <id> and is refused without it, --arc-id is refused with any other trigger, and an unknown trigger value is a usage error, so the host's own requested/arc vocabulary is mapped onto these two values before the command runs. The published bundle keeps trigger and adds trigger_ref, which is {"kind":"request"} or {"kind":"arc","arc_id":"<id>"}, and index.md states the same event on its Trigger line, so a stored report and the page a reader opens both name what produced them without consulting the host's run record.

The profile (evaluation-profile.v1) declares the scope — a scene, a chapter, an arc or the whole book — and the optional rubric and aggregation profile. Chapter selections are resolved against the accepted inventory before any measurement, so a duplicate or nonexistent chapter is a contract violation; material outside the selection can be supplied as context_chapters, which explain a fact without being counted as candidate text. The annotations file carries what cannot be computed: judged metric annotations, the eight literary indicators, a versioned rule registry with outcomes stored per rule and output, an optional embedded continuity result, an opt-in timing study, findings and the passages worth preserving. The corpus manifest names reference texts with their hashes, languages, provenance and permitted use, and it is read only from that explicit file: the corpus is never downloaded, the candidate's own source version is excluded from comparison, and genuine duplicate text in another reference is flagged rather than silently dropped.

Metrics, indicators and the five views

The registry holds twelve metrics — coherence, narrative quality, continuity control, character attribute drift, emotional arc, compliance adherence, originality, similarity, novelty and cliché, contamination, textual overlap and author efficiency — each with a definition version, a purpose, a method, a direction, a unit, its limits and a discriminated value kind. Two further names, VAD and BCI, are reserved without a sufficient definition and are never given a value. Alongside them stand the eight literary indicators: narrative coherence, thematic depth, character complexity, originality, stylistic quality, emotional impact, interpretive openness and cultural value.

A result is a scalar, a set of anchored components or an ordered trajectory, so a diagnostic profile is never flattened into an invented number. The coherence score keeps its four dimensions and derives its experimental scalar only when all four are assessable; the originality index keeps its three dimensions and the comparison scope it was judged against; the novelty and cliché score keeps its two dimensions separate; the emotional arc keeps the order, focalization, valence, tension, evidence and uncertainty of every segment; contamination needs a dataset record whose referenced files are hashed locally; and the efficiency gain comes from opt-in timing records with a positive comparable baseline, where a negative result is a real result. A bare supplied number where components are required is classified as unsupported legacy data rather than becoming a score.

Every result carries one of five statuses: measured by deterministic code, judged from an annotation, not assessable because a prerequisite is missing, not applicable because the question does not apply, or an error from a failed method. A zero is a measurement and is rendered differently from an unavailable result, which names what is missing. The composite score stays disabled until a validated profile exists, a missing input never silently redistributes its weights, and a continuity finding is charged once rather than again as an independent penalty. The aggregate runs under one of two named policies: research is an experimental formula that an ordinary report may use with declared weights, an explicit advisory note and a stated emotional intention, and it claims nothing about readers, while production claims calibration support and therefore stays unavailable until a completed study bound to the rubric and profile versions, the language and the scope exists; the refusal says that the aggregate is optional and off by default and names the research profile.

The five views are rendered deterministically from the one bundle: the rule-adherence view reports the general rule set and its unresolved and failed checks, the specification-adherence view maps the request and the brief to what the text did, the metrics-and-indicators view lists every status, scope, unit and reason, the score-justification view shows the components, arithmetic, bounds, coverage and limits of each result, and the detected-issues view prioritizes findings, preserves alternatives and keeps the passages worth retaining. A navigation index sits beside them and is not a sixth evaluation. A renderer reads the bundle and never changes a score or judges the text again, so re-rendering a stored bundle is byte-identical; supplied text is escaped so it cannot break a table, a code span, a link, raw HTML or a heading.

Publication, dependencies and boundaries

The whole bundle is staged in a fresh sibling directory, its inventory is verified and it is published with a single rename, so a reader sees either the previous complete assessment or the new complete assessment and never a mixture. An output equal to, nested under or symlink-aliased into the packet or another supplied input is refused before any write, decided on real paths, and an existing accepted assessment is never overwritten file by file; a failed execution leaves no apparently current assessment.json with missing views.

The folder needs Node.js 20 or later and nothing else: the command uses built-in modules for file access, paths, hashing and UTF-8 decoding, and it has no npm package, no vendored code, no external command and no network access at runtime. Its tests use the built-in node --test runner and cover packet validation with the shared rejection codes, evidence verification with multibyte text, the similarity and overlap arithmetic against independently computed values including overlapping and nested matches, the tokenizer's declared applicability, empty and short inputs, self-exclusion, scope resolution with earlier context, the rule registry and CAR coverage, the component, trajectory, timing, contamination and aggregation contracts, output separation and atomic publication, deterministic re-rendering and the rule that the packet is byte-identical after a run. Two further suites validate the synthetic case library — its schema, its pairing, the single-feature rule, the 12/12 language split, the reserved regression subset, the anchored evidence offsets and the unperformed agreement record — and the trigger flags with their refusals.

The boundary is that this skill measures and reports. It does not rewrite the book, does not change the canon, does not start a model by itself and does not block a chapter from being accepted. A calibration study with held-out examples, and any threshold that might follow from it, is separate work; until it exists the composite stays disabled and every value stays advisory. The complete contract is specified in DS013-scripta-metrics-report-skill, and the continuity result it consumes is produced by scripta-continuity-review.
