Skills

scripta-book-export

scripta-book-export is the print skill: one command that turns the chapters of a universe into a DOCX file, a PDF file or both, using the skill's own TrueType, layout, PDF and DOCX engines. The server asks for it during an export turn, and a reader reaches the produced files from the header menu of the reader interface.

What the skill covers

The skill exists so that a book written as Markdown chapters can be produced as a printed edition without an external toolchain. The renderer contains its own font parser and subsetter, its own page layout engine, its own PDF writer and its own DOCX writer built on the compression and hashing modules of Node.js, and it depends on no npm package, no Python and no other command. It reads the book, it writes only edition files inside the exports/ folder, and its whole result is reported as a single JSON line on standard output, which is what makes it usable both by an agent and by the project check.

An export turn works in two steps: the agent writes the editorial metadata, then it runs the command and reads the JSON line back. The server then verifies that at least one edition file appeared, and fails the turn with NO_EXPORT when it did not, so a reported successful edition always corresponds to a file on disk.

Folder contents

File Role
SKILL.md The agent procedure, the command-line reference, the file naming and language rules, the accepted Markdown subset, the font search order and the hard rules of the export.
scripts/build-book.mjs The command-line entry point: it parses the options, loads the book, paginates it, calls the two writers and prints the single JSON line.
scripts/lib/*.mjs The engines, as ES modules: errors.mjs (exit codes, errors, text and byte helpers), truetype.mjs (the font parser and subsetter), fonts.mjs (the font search and BookFace), markdown.mjs (the accepted Markdown subset), book.mjs (language, labels and the book model), layout.mjs (pagination and the table of contents), pdf.mjs (the PDF writer) and docx.mjs (the ZIP and OOXML writer).
DS.md The design summary: the engines, the layout strategy, the font selection and the reasons behind the command-line contract.
skill.json, dependencies.md The catalog manifest and the local dependency record, including the optional system-font requirement and the tools used only to verify produced files during development.

Command line

node skills/scripta-book-export/scripts/build-book.mjs \
  --universe <universe-folder> [--out <folder>] [--format both|docx|pdf] [--fonts <folder>] [--language <code>]

Inside a universe the same script is reachable through the skill link, so the documented form for an agent is node .agents/skills/scripta-book-export/scripts/build-book.mjs --universe . --format both.

Option Meaning
--universe The universe folder, required; it accepts . so the command can run from inside the book.
--out The destination folder, defaulting to the exports/ folder of the universe.
--format both by default, or docx or pdf alone.
--fonts A folder of .ttf files that replaces the system font search.
--language The language of the edition labels, resolved in the order --language, then the language in the editorial metadata file, then the language of the universe, then ro.

An unknown option, a missing value, an invalid format, an invalid language code or a missing universe is a usage failure: the JSON line carries USAGE or MISSING_UNIVERSE and the process exits with status 2, so an invalid invocation never produces a partial edition.

Editorial metadata and language

Before running the command the agent writes the [editorial metadata](wiki.html#definition-edition-metadata) to exports/edition.json with a title and, optionally, a subtitle, an author, a year, a dedication, a preface, an afterword and a language. Only the title is required; a missing value is completed from the universe metadata, and the renderer itself reads the title, the identifier and the language of the universe and uses the folder name when no identifier is present. The preface and the afterword are Markdown and their section heading becomes their title; the dedication is set on its own page, and both the preface and the afterword appear in the table of contents.

The resolved edition language localizes labels only: the table of contents heading, the default preface and afterword headings, the chapter label, the fallback title of an untitled chapter and the language metadata written into the files. Romanian and English are required; any other code uses the English labels. The prose written by the agent is never translated, so a book in one language can be produced with labels in another.

Produced files

An edition file is named <slug>-<YYYYMMDD>.pdf or .docx, where the slug is the title normalized to lowercase letters, digits and hyphens with diacritics transliterated and the date is the build date. The output folder is created when it does not exist, and nothing else in the universe is touched: chapters, metadata, the editorial file and the turn records are read-only for the renderer.

The PDF has a separate title page, the optional dedication, a table of contents whose titles and page numbers are computed by the layout engine, chapters that start on a new page under the localized chapter label, footer page numbering that omits the title page, bookmarks for titles, and a subsetted serif font with a Unicode mapping, which is what makes the text selectable and the diacritics correct. The DOCX has the same structure expressed through standard styles, page breaks between chapters, footer page numbering, and a real table-of-contents field whose cached result was computed by the same layout engine, so the page numbers are correct before a word processor refreshes the field.

Input requirements and fonts

The renderer reads the chapter files of the universe sorted by chapter number and requires at least one; without a chapter it fails with NO_CHAPTERS. A chapter title is its first heading, with a fallback built from the file name and then a localized untitled label. The accepted Markdown subset is the one the narrative skill writes: level one and level two headings, with deeper levels treated as level two, paragraphs separated by a blank line, blockquotes, scene separators and bold or italic emphasis. Tables, images, code, raw HTML and links are not accepted.

For the PDF the renderer searches system font locations in a fixed order and accepts a family only when its regular face covers, through its character map, every character of the book. Missing styles fall back to the regular face, and when no family covers at least the Latin set plus the Romanian diacritics the command fails with MISSING_FONT and exit status 1. The remedy is to install a serif TrueType font package or to point the renderer at a folder of .ttf files with --fonts; OpenType CFF fonts and font collections are ignored, and no font is bundled or redistributed with the repository.

Result and exit codes

On success the single JSON line carries ok, the edition title, the chapter count, the word count and an outputs array whose entries carry the format, an absolute path, the byte size and the page count, where the page count is an integer for a PDF and null for a DOCX. On failure it carries ok: false with a message and a code such as USAGE, MISSING_UNIVERSE, NO_CHAPTERS, MISSING_FONT, BAD_JSON, IO_ERROR or INTERNAL.

Exit statuses are part of the contract: 0 for success, 2 for a usage failure and 1 for a processing failure. A caller must treat any nonzero status as a failed edition, surface the code, and never infer success from partial output or from the existence of the process. The agent is required to report only what it read from that JSON line.

Dependencies and boundaries

The folder requires Node.js 20 or later, uses only built-in modules, and needs no installation step, no build step and no network access at runtime. A system serif TrueType font is an optional requirement that becomes mandatory the moment a PDF is requested, and its absence is reported rather than worked around. The inspection tools used during development to verify produced files are listed in the dependency record as verification tools, not as dependencies of the command.

The skill is a producer, not an editor: it never modifies the book, never writes the editorial metadata itself and never decides when an edition should exist. The complete contract, including the exit codes and the language order, is specified in DS008-scripta-book-export-skill; the narrative side is scripta-ala.
