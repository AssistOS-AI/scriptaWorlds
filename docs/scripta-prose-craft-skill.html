scripta-prose-craft

scripta-prose-craft holds the craft decisions a scene needs — who perceives it, what each person wants from the exchange, where the reader's attention slows down — and validates the prose profile that records them. It is a separate-phase skill: it is chosen for design work and for a requested revision, and it never runs while ALA is writing a chapter.

What the skill covers

A chapter prompt can state what must happen in a scene; it cannot state how the scene should feel to read. This skill carries that second half of the work as a compact artifact. It starts from the scene's purpose, the focal character, the accepted conditions and the reader request, and it decides what that character notices, what they want to conceal and what they can reasonably know. Expression is a choice, not a quota: description, dialogue, narration and interior thought are used because they serve the scene, and sentence length, block ratios and adjective counts are never validation inputs.

The folder contains SKILL.md with the procedure and the schema, references/narrative-blocks.md with the structural, content, expression and rhythm vocabulary, references/voice-and-revision.md with the profile fields and the revision record, skill.json as the catalog manifest, dependencies.md as the local dependency record, scripts/validate-profile.mjs as the single executable with its rules in scripts/lib/, and tests/ with the suites and their fixtures.

The prose profile

The profile is one JSON document, proposal/prose-profile.json in an assessment workspace, with the schema version profile.v1. Its required keys are the schema version, an identifier, the language of the book, the intended reader experience and the narrator. Its optional keys record the source version, the focalization, the register, the character voices, the recurring devices and the revision priorities.

Focalization answers whose perception and knowledge limit the passage, and a deliberate violation is recorded as a design choice rather than treated as an error; the focal character is an entity reference, so it must be declared among the character voices. Each voice entry records notes a writer can use, such as answering a question indirectly to protect status or noticing machinery before faces, because two speakers can share a vocabulary while pursuing different social actions. Each recurring device records its purpose, which is what separates a motif that gains meaning from an empty repetition. Identifiers are compared after trimming whitespace and applying Unicode normalization, so two identifiers that differ only by that collide and are refused.

The optional expressive_components array carries the observations of the inspection as evidence-bearing records rather than adjectives or a score. Each entry names the layer it belongs to (focalization, description, dialogue, narration, interior_monologue, rhythm), the passage it is anchored to, its status, the evaluator and method that judged it, its rationale and the quoted evidence that supports it; an uncertain or unresolved reading states its limitation, and an alternative reading is preserved. With --context, every quote is located verbatim in the packet file it names, so a fabricated quotation or an undeclared source is refused instead of being reviewed as support.

The optional calibration object records readiness instead of assuming it: a profile is uncalibrated unless it says otherwise, an experimental profile names the protocol it follows and implies no validation, and a calibrated profile names its protocol and cites the evidence behind it. intended_use: "production" is refused until that evidence exists — the calibration study of C34 has not been run — so a profile stays advisory, and the author who chose the intended effect can always overrule it.

A prose profile and the metrics evaluation configuration are different documents with different schema identifiers: profile.v1 names this one and assessment-profile.v1 names the metrics side. A document that names another kind, or that carries the evaluation configuration's own aggregation or scope fields under profile.v1, is refused rather than validated against the wrong rules.

Validator

The skill ships one read-only command:

node skills/scripta-prose-craft/scripts/validate-profile.mjs --input <profile.json> [--context <packet-dir|manifest.json>]

The command prints exactly one JSON object with schema_version, ok, errors, warnings and context, and it exits with status 0 for a structurally valid profile, 2 for invalid arguments, malformed input, a wrong type or a violated structural rule, and 1 for an unexpected execution failure. Every error is structured as <CODE>: <message>, so a host can act on a refusal without parsing prose. It checks unique identifiers, unique device and component names, every entity reference, the component vocabulary with its statuses and required evidence, the calibration gate and the supported language code.

--context names a frozen assessment-input.v2 packet — the packet directory or its manifest.json. The manifest is verified first: its schema version (a superseded assessment-input.v1 manifest is refused as such), unique paths, artifact identifiers and chapter numbers, path containment through real paths rather than string comparison, declared byte counts and SHA-256 values, valid UTF-8, a role from the documented vocabulary, and the accepted version identity recomputed over the chapters and state containers. The profile's based_on_version is then compared with that identity — never with the book's universe identifier, which is not a version — and it must equal it, so a profile written for one accepted version is refused as stale against another. Because the result records the version and the covered scope, a validated proposal always names the accepted version and the coverage it stands on, and a quote that cannot be found in the packet file it names is refused instead of counted.

The command writes nothing: it takes no output path and refuses one (--out, --output, --emit, --write, --publish) before it reads anything, so no output can equal, nest under or alias back into the profile or the packet. The accepted proposal is written by the crafting session into proposal/prose-profile.json and published in one move — a fresh temporary file renamed into place — never by rewriting an existing accepted proposal in place, so a reader sees either the previous complete proposal or the new one. The validator applies no aesthetic judgement at all: it never counts adjectives, measures sentence length, prefers a register or demands a block ratio.

Drafting, inspection and revision

The drafting pass fixes what the scene gives the reader, the focal attention and immediate desire, the change the encounter produces, and the point at which the scene ends — which may be a complete local gesture, an unresolved silence or a changed understanding rather than a cliffhanger. The inspection that follows asks whether a repeated image acquires a different meaning; whether a suspect exchange would keep its purpose if another character spoke it, which points at the speaker's stake rather than at unusual vocabulary; whether a sentence states the lesson of the action immediately before it, which is kept only when the narrator's judgement is itself revealing; and whether the reader has any ordinary human detail through which to care about an abstract conflict.

A revision names a passage, a reason tied to this book and the effect to preserve. The default is one pass, after which the changed evidence and the structural validity are rechecked, and a change that improves cadence while contradicting established knowledge is not ready. Changed prose is submitted through the workflow that owns chapter candidates: this skill never writes a chapter, never changes permanent rules and never manufactures earlier evidence, and raising a literary score is not a reason to change a passage.

Dependencies and boundaries

The folder needs Node.js 20 or later and nothing else: the validator uses built-in modules for file access, paths, hashing and strict UTF-8 decoding, and it has no npm package, no vendored code, no external command and no network access at runtime. Its three node --test suites cover the structural rules and the argument contract, the frozen packet contract, and the read-only portable behaviour the command must keep: a minimal profile, voices and recurring devices, a deliberately formal register, duplicate and colliding identifiers, a missing note, malformed input, a non-object entry, an unsupported language, an undeclared entity reference, an unsupported schema version, a matching packet, a profile written for one accepted version refused as stale against another, the version and scope a result records, a superseded or absent manifest, a universe identifier refused as a source version, tampered bytes, a detached manifest, a symlink escape, an undeclared role, bytes that are not valid UTF-8, the required structure of an expressive component, a fabricated quote, an undeclared evidence source, the calibration gate, every refused output argument wherever it points, and the whole skill folder copied outside the repository and run from an unrelated directory.

A profile is a proposal and never evidence. An intended effect, a voice note, a device, an expressive component or a calibration claim is a direction: it is not part of the book until an accepted chapter shows it, and a proposal that contradicts the accepted version is stale rather than applicable — only an approval record and a later writing request carry directions into the book. That is why this skill is never part of the chapter prompt: ALA writes from the narrative skill, the canon and the reader request, and it neither reads nor executes this skill during a turn.

The skill owns craft decisions and the structure and declared support of the profile that records them. It does not produce chapter prose into a book, does not write canon, threads or atlas, and does not decide whether a book is good; literary judgement stays advisory and out of the mechanical pass, and the author who chose the intended effect can always overrule the profile. The complete contract is specified in DS011-scripta-prose-craft-skill; the design decisions that precede it are scripta-story-design.
