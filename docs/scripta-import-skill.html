scripta-import

scripta-import is the import skill: it turns a book the team uploaded as a PDF or a DOCX into a universe that is structurally identical to one written here. It reads the host's extraction of the uploaded file and, in import turns, copies the book's own prose into chapter files and derives the state files from that prose. It writes no narrative content of its own — importing is archiving — and what it makes is a book that can afterwards be read, continued, reviewed, measured, rewritten chapter by chapter and printed like any other.

What the import is for

A reader can upload a book instead of writing one, and the product then owes the same experience: a book that can be read chapter by chapter, continued by ALA, analysed by the separate-phase skills, revisited chapter by chapter and produced as an edition. That is possible only when the imported book is indistinguishable in structure from a written one — the same chapters/NNNN-slug.md files with # Title on the first line, the same canon.md, threads.json and atlas.json, the same vocabulary — and factually faithful to the file that was uploaded.

The skill therefore has two halves. The instructions in SKILL.md and its six reference documents tell an agent how to import one bounded range of an extraction, and how far it may go in cleaning, segmenting and describing it. The executable scripts/validate-import.mjs is what the host runs after every import turn: with no model and no budget it checks that the chapters of that range are on disk in one contiguous run, that their words are plausible against the extraction they came from, that the state files parse and cite real chapters, and that the universe carries the machine-readable mark of an import.

An import is not a summary and not a rewrite. The prose is the book's own words, in the book's own order, in the book's own language; cleaning may remove what a page has — running heads, page numbers, scanner artefacts, hard wraps — and add nothing, and it may never rewrite, translate, shorten, extend, reorder or annotate. A chapter the extraction declares with prose is always imported; only a chapter it declares with no words, such as a part title or a blank page, may be passed over, and each one is named in the record's skipped list with its reason.

An imported book also has no authorial law. The universe the host creates for it carries the law that the text is the law and that canon records what it establishes, so a later chapter turn or rewrite is bound by the same rule the import followed. An imported chapter has no drafts/NNNN-plan.md and no chapters/NNNN-offer.json: a plan is how an episode is invented and an offer is ALA's voice about what could happen next, and both appear only once the chapter is continued or rewritten.

What one import produces

The skill writes only what an agent may write inside a universe, and only the part of it an import owns: the chapter files of the range it imported, the three state files, and the record that describes the import itself. Everything the host owns — the universe metadata, the charter, the turn records, the staged extraction and the editions — is outside its reach.

Product What the import writes there
chapters/NNNN-slug.md The book's own prose, one file per chapter, four-digit numbering without a gap from the import's first chapter number, the chapter title on the first line after #. No plan, no offer and no commentary accompanies them.
canon.md The six fixed sections a written universe uses — ## Fundamental laws, ## World, ## Recurring characters, ## Timeline, ## Stable facts and ## Mysteries with a fixed cause — with every line traceable to the chapter that shows it as (ch. N). The law is copied from the universe metadata; the rest is what the imported chapters establish and nothing else.
threads.json What the book leaves open at the frontier — promises unpaid, mysteries unsolved, decisions untaken, questions unanswered — in the documented lists and vocabulary, with the chapters that created, close and owe each entry. A later turn moves what its new chapters pay into closed with a one-sentence resolution.
atlas.json The axes and nodes the imported chapters work, with the state the prose shows (mentioned, dramatized, decision or recontextualized) and the chapters that show it.
drafts/import-progress.json The import record: the machine-readable mark that this universe was imported, the identity of the upload it came from, the chapters it has written so far, the chapters it skipped, the turns it ran and the chapter the next turn starts at.

The rule that governs all four files is that the import invents nothing: no fact the imported chapters do not show, no character who has not appeared, no date the book does not give, no axis, no node for an idea the book never touches, no thread for a promise nobody made, and no mystery with a cause the book has not given. An honest gap is part of the book; an invented fact is a defect a reader will find.

How the book arrives and how it is read

An upload enters through POST /api/imports, where the body is the file itself and its name travels in the X-Filename header, with an optional X-format: pdf|docx. The bytes are streamed to the workspace outside universes/ while they are hashed and counted, so the size limit is enforced while the upload is still arriving rather than after it was accepted: a body larger than IMPORT_MAX_BYTES, 64 MiB unless the environment says otherwise, is refused during the transfer with 413 IMPORT_TOO_LARGE. GET /api/imports lists the imports with the size limit the deployment accepts and the turn limits the skill publishes, and GET /api/imports/:id reports one import together with how much of it has been imported.

Extraction is a separate step, POST /api/imports/:id/extract, which starts in the background and answers immediately: a long book must not hold a request open, and the caller follows the record's state — received, extracting, ready or error — instead of waiting. Extraction runs without a model and is deterministic: the same file always yields the same text, which is what the import turn, a later review and a later rewrite all read. The result is written beside the upload as extracted.json, with book.md as its readable twin, and the universe receives a copy under .agents/import/ so the import turn reads its input from inside its own folder.

The extraction is a book-import.v1 document: the source (file name, format, sha256, byte count and page count), the detected metadata (title, author, language) and the chapters, each with a number, a title, a word count and its text, paragraphs separated by blank lines and headings kept out of the text. A file that names itself keeps its title; a file that does not is named by the name the uploader gave it, and the field detected.title_source says which of the two it is instead of passing one off as the other. The format is decided from the bytes first and from the file name second, so a wrong extension is caught as unreadable rather than parsed as prose.

Two readers do the work, both dependency-free and both derived from the bytes alone. A DOCX is a ZIP package, so the container's own central directory is read and only the parts the text needs — word/document.xml, docProps/core.xml and docProps/app.xml — are inflated with node:zlib; media, styles and headers are listed but never expanded. A PDF has no text of its own, so its indirect objects are read, its content streams inflated, its page tree walked and its text operators interpreted into lines and paragraphs. A PDF whose text cannot be read because it has no text layer is refused with IMPORT_NO_TEXT, naming the pages that were examined: a scanned book must be recognised by OCR before it is imported, because the importer never guesses text and never returns an empty book.

A book whose boundaries the file itself shows is segmented while it is extracted — a DOCX heading style, or a short standalone heading line such as Chapter 7 or a standalone number in a PDF — and each chapter arrives with its own title. When no boundary can be detected, the book arrives as one large chapter and a warning that says so, and the segmentation then belongs to the import turn, which declares which method it used. Where the extraction could not read everything — a content stream under an unsupported filter, a page set in a subset font whose character map is not decoded — the extraction reports it as a warning rather than hiding it, so a partial result says so.

Segmenting a book that arrives without boundaries

A book that arrives as one chapter is cut by the import itself, and the record declares in segmentation which of the three methods was used. host means the extraction had already found the boundaries and the import only followed them. scene means the prose has scene breaks and no headings, so the scenes are grouped into chapters and the cut falls where the scene changes. word_count means neither exists, so the text is cut at a paragraph boundary around 2,000 words, never before 1,500 and never after 2,500, so an imported chapter reads like a written one; a segment outside that band is reported as the warning SEGMENT_OFF_BAND.

A word_count segmentation is a declared approximation rather than a discovery of the book's own structure, and the record says so. The cut segments of one source chapter occupy consecutive chapter numbers and carry their segment index 1..k, so the division stays visible and a later reader can always see how a chapter was arrived at.

How a turn is bounded, and how the next one continues

An import is a sequence of turns, because a book is far larger than one turn. One turn covers at most three extraction chapters and at most 6,000 words of their prose, whichever comes first, and always at least one chapter, so that a single chapter longer than the word bound is still importable. Whichever bound is reached first ends the window; a recorded turn above the bound is reported as the warning TURN_OVERSIZE and does not refuse the import. The window is always a prefix of the extraction from the continuation pointer, in order, with no chapter repeated and none skipped forward.

The bound is not configured on the server. The skill publishes it in schema/import.v1.json under turn_limits, and the host plans the next window with exactly the function the skill uses, planTurnWindow(chapters, fromSourceChapter, { maxChapters, maxWords }) in scripts/lib/record.mjs, so a window the host plans is a window the skill's validator agrees with. Chapter files on disk do not carry the number of the extraction chapter they came from, so the store alone cannot say what has been imported; the import record is authoritative, and its next_source_chapter is the continuation pointer — the extraction chapter the next turn starts at, or null when every extraction chapter has been imported or skipped.

The record's complete flag is true exactly when that pointer is null. POST /api/imports/:id/universe creates the universe for an extracted upload and queues the first bounded window; called again for the same import it continues where the record stopped and queues the next window, and when the import is complete it answers with the universe and no turn. Each step is therefore an ordinary queued turn of that universe — kind import, with its own turn record, its place in the queue and its progress in the event stream — which is what lets a long import be watched, retried or refused step by step. An import turn of a closed universe is refused with CLOSED.

Before a turn is accepted, the host verifies what it produced against the range it was given: the chapters of that range must be on disk, and the skill's validator must accept them with --chapters set to the range. A chapter that is missing fails the turn with NO_CHAPTER, and a set the validator refuses fails it with the validator's own code and the first of its errors, so a turn that wrote nothing stale or invented is not accepted on the agent's word.

Refusals

An unusable extraction is refused and nothing is written, because an import that invents what it could not read produces a book that is wrong in a way no later reader can repair. The skill stops on an extraction that is absent, empty or wordless (NO_EXTRACTION), on one that does not parse or whose schema version is unknown or whose chapter entry carries no text field (UNPARSEABLE_JSON, INVALID_IMPORT), on prose that arrives in a script that cannot be copied faithfully or as replacement characters, and on an import that is already finished, where there is simply nothing left to do.

A record is never repaired by guessing: one that names another upload — a different import_id or a different source.sha256 than the extraction it was given — is refused with INVALID_IMPORT rather than merged or edited. The extraction has its own refusals, produced by the host before the import ever starts: IMPORT_UNSUPPORTED for a format the importers do not read, IMPORT_EMPTY for an empty upload, IMPORT_UNREADABLE for a file that is not a readable PDF or DOCX, IMPORT_NO_TEXT for a PDF with no text layer and IMPORT_TOO_LARGE for an upload or a document past the byte limit. A failed extraction keeps its reason on the import record, answers 410 IMPORT_MISSING when the uploaded file has disappeared from the workspace, and 409 NOT_EXTRACTED when a later step asks for an extraction that never succeeded.

The validator

node skills/scripta-import/scripts/validate-import.mjs \
  --universe <universe-folder> --import <extracted.json> [--chapters <from>-<to>]

Inside a universe the same script is reachable through the skill link, so the documented form for an agent is node .agents/skills/scripta-import/scripts/validate-import.mjs --universe . --import .agents/import/extracted.json --chapters N-M. --universe is required and --import defaults to the extraction staged inside that universe; --chapters bounds the check to the universe chapter numbers one import turn wrote, which is how a twelve-chapter book is accepted turn by turn while the later chapters do not exist yet, and without it the whole import is checked.

Standard output carries exactly one JSON envelope, printed as the last line and nothing else: {"schema_version":"book-import-validation.v1","ok":…,"code":…,"errors":[…],"warnings":[…], …} with the import's identity, the range and pointer that were checked and the counts that were compared. ok is true only when errors is empty, warnings never change it, and the exit status is 0 when ok is true and 2 in every other case, including bad arguments.

The code is decided in a fixed order, the first present naming the envelope: NO_EXTRACTION, UNPARSEABLE_JSON, INVALID_IMPORT, MISSING_CHAPTER, WORD_COVERAGE, with USAGE for bad arguments. A missing or unreadable extraction stops the run because there is no text to check against, and a record that does not parse or does not hold together stops it too; chapter and state defects are collected into one answer instead. MISSING_CHAPTER covers every defect of the chapter set — an absent file, a gap in the numbering from the import's first chapter, two files for one number, a file whose name the record contradicts, or a checked range that names a chapter the import has not reached. WORD_COVERAGE covers the two measures of plausibility: a chapter whose word count falls outside 0.8×–1.2× of its extraction chapter with twenty words of slack, or whose eight-word run overlap with that chapter is below 85% in either direction. Prose that was written rather than copied fails both.

The validator is the machine-readable proof that the universe was imported rather than written: it proves that the extraction exists and holds prose, that the record agrees with it on the upload, that the chapters it names exist once in a contiguous run with their titles, that the words are plausible in quantity and in sequence, that the state files parse and cite chapters that exist, and that drafts/import-progress.json marks the book as an import — a universe without that record is INVALID_IMPORT however ordinary its chapters look. It does not prove that the cleaning kept every sentence, that a canon line is true of the book, that a thread is the right thread, or that the segmentation of a boundaryless book is the one a human would have chosen; those are readings of prose, and no deterministic check settles them.

What the imported book can do afterwards

After the last turn the imported book is an ordinary universe. It is read in the reader interface like any other, continued or rewritten by scripta-ala — which is what supplies the plan and the offer an imported chapter never had — reviewed by scripta-continuity-review, measured by scripta-metrics-report, and produced as an edition by scripta-book-export.

The prose stays in the book's language whatever the universe metadata says, and the state files are written in that language too, because they describe the book; only the schema vocabulary — file names, section names, JSON keys, thread kinds and statuses, atlas axes and states — stays English. A detected language that differs from the universe's is recorded in the record's language block and reported as the warning LANGUAGE_MISMATCH; the import never translates the book and never edits the universe metadata, which belongs to the server, so settling that difference is an operator's decision rather than a silent rewrite.

Dependencies and boundaries

The folder requires Node.js 20 or later and uses built-in node: modules only — node:fs, node:path, node:url — with no npm package, no vendored code, no external command and no network access at runtime; the extraction is an input contract rather than a dependency, and dependencies.md records that position. Its tests use the built-in node --test runner and cover the five failure codes end to end through the real command line, the precedence between them, the incremental range of a twelve-chapter book, the plausible word band, the run-overlap measure, segmentation inside and outside its band, the skipped-chapter rule, the turn journal and the oversize warning, the language decision and the record's continuation.

The boundary of the skill is that it imports and describes. It does not write prose, does not judge whether the cleaning read well, does not settle a language mismatch in the metadata and does not decide that a book is finished: a host that wants the whole book imported runs the turns until the record says complete: true, and everything written afterwards belongs to scripta-ala and to the separate-phase skills. The complete contract is specified in DS014-scripta-import-skill; the pipeline that feeds it is described on Architecture and its routes on API.
