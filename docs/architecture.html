System

Architecture

scriptaWorlds is one Node.js process, one static browser interface and one agent process per turn. The server owns a durable queue and the files that record what happened; the agent owns the narrative state inside a universe folder; the browser only reads the interface and the event stream. This page explains how those parts fit together and which one writes which file.

Components

The runtime is the modules under src/, and each one owns a single responsibility. Nothing in the runtime holds persistent state of its own: it reads and writes the universe folders and the data files of the repository, and those files are the state. The table below names the modules the store, the data sources and the turn pipeline are built from; the separate design and review phases, described in the contract reference, and the import pipeline, described below, add modules of their own that follow the same rule.

Component Responsibility
src/server.mjs Process lifecycle and HTTP routing: takes the store lock, probes the agent, recovers turns from the previous run, resumes queued turns, refreshes the per-universe skill links, prints the addresses, serves static files, and dispatches every /api route, including /api/table and /api/library. It starts a listener only when it is the process entry point, so importing it has no side effect.
src/http.mjs Request and response plumbing: JSON bodies with a size limit, the JSON error envelope, content types, static file serving with path containment, and the server-sent-events connection.
src/config.mjs Environment configuration, the accepted language list with labels, the agent probe, and the timeouts and word band that bound a turn.
src/errors.mjs The error type every layer throws: UniverseError carries the machine-readable code and the HTTP status together with the message, and notFound builds the common 404. Because the code and the status travel with the error, a handler in the router needs no translation table.
src/io.mjs The small file and text helpers shared by the store and the turn pipeline: read a text or JSON file with a fallback instead of an exception, write JSON, format a timestamp and pad a number.
src/lock.mjs The store lock: acquireStoreLock creates universes/.server.lock with the process identifier and the start time, refuses to start when the recorded process is still alive, and takes over a lock left behind by a process that is gone.
src/paths.mjs Repository locations resolved from the module itself, the universe identifier rules and slug derivation, the discovery of product skills, and the symlink refresh inside a universe.
src/periodic.mjs The Periodic Table of Speculative Ideas, the design instrument of the project: it reads data/periodic-table.json, prepares the grid the interface reads for GET /api/table, distils one cell — idea, prompt, ingredient sentence, family note, landmark and the nights that already use it — for GET /api/table/cells/:symbol, resolves a reader's ingredients against the table, composes the law from them and writes the ingredient lines that every prompt carries.
src/library.mjs The library of start templates: it reads the index for GET /api/library, reads one template for GET /api/library/:slug, answers which nights already work a cell from the cellScenes reverse index, audits the index against the folders, and turns a template into the fields a new universe needs.
src/templates.mjs The older catalog of proposed universes, cached by file modification time and localized with a fixed fallback order. The reader interface no longer reads it.
src/universe.mjs The store: creating a universe, adopting the short name the agent wrote, changing the language and the status, and the views the interface reads — the universe list, the universe detail, one chapter and the continuation ideas.
src/universe-chapters.mjs The files of one universe: the naming conventions of chapters, offers, turn records and exports, scanning them, archiving a chapter version before it is overwritten or dropped, and removing the partial files of a failed turn.
src/universe-state.mjs The state snapshots: copying the whole accepted book — canon.md, threads.json, atlas.json and every accepted chapter plus its offer — into turns/NNNN.prev/ before a turn, and restoring it when a rewrite or the recovery after a crash needs the book as it was.
src/universe-prompts.mjs The documents of a universe, composed as pure text: the charter, the first canon, the instructions in the AGENTS.md of the folder, and the structured request used when the client sent no text of its own.
src/prompts.mjs The three prompt families of a turn — a new chapter, a rewrite of an existing one and a printed edition — including the naming duty and the ingredient lines.
src/turn.mjs One turn apart from the queue: which prompt family it needs, what the agent must have produced before the turn counts as done, and the repair of the store when a turn fails.
src/jobs.mjs The job registry, the per-universe FIFO queue, the concurrency rule, the durable turn records, the event stream and the HTTP snapshots of a job.
src/omp.mjs The agent process of one turn: spawning it, parsing the JSON event stream it writes, enforcing the deadline, and composing the log that goes into the turn record. It knows nothing about the queue or the store.

The modules are grouped by what they may touch: server.mjs and http.mjs are the only ones that speak HTTP, jobs.mjs, turn.mjs, prompts.mjs and omp.mjs form the turn pipeline and never read the disk layout directly, and the three universe*.mjs modules own the folder of a universe, its snapshots and the text written inside it. periodic.mjs and library.mjs read the two data sources of the product — the table of ideas and the library of start templates — and nothing else. The browser interface is a separate module tree with no build step, described below, and both product skills are self-contained command-line programs.

Build and data steps

The runtime has no build step: node src/server.mjs runs the modules as they lie on disk. Two data sources are generated from the printed book vision/periodic_table.pdf, and both are committed so that a checkout needs neither the book nor a toolchain to run.

Step Command Output
The table of ideas npm run table (node scripts/build-table.mjs) data/periodic-table.json: twelve families with the cells that belong to them, fifteen operators and one hundred and eighty cells, each with its identifier, symbol, name, gist, prompt line, ingredient sentence, landmark and the prose sections of the book. It requires pdftotext and refuses to write anything when the book does not parse cleanly, so the committed file is never a half-built table. src/periodic.mjs reads it and every composed universe depends on it.
The library of start templates npm run library (node scripts/build-library.mjs) library/index.json — one line per template plus the cellScenes reverse index that says which nights work which cell — and the seventy-five folders under library/, rebuilt from the nights of the book and from the table. It requires the system tool pdftotext, fails with a clear message when that tool is missing, and never invents a template: it writes what the book contains.
Verification of the table npm run table -- --check A comparison between the committed data file and the book on the number of cells and on the name, operator, gist and prompt of each one, printed as problems with a nonzero exit status and without writing anything.
Verification of the library npm run library -- --check A comparison between the index, the folders on disk and the book, printed as problems with a nonzero exit status. It writes nothing, so it is safe to run on a working checkout; npm run check performs the same comparison through the store module.

The empty template is the one exception in that pipeline: it is written by hand under library/empty/, and a rebuild only re-serializes it and keeps it first in the index.

Module trees

The browser interface and the print skill are each a small tree of focused files rather than a single program. Every file of both trees stays under 500 lines, which is what allows a surface or a document writer to be read on its own.

The interface is served as it lies on disk, so a module that fails to load — typically because the interface was replaced while a tab stayed open — is reported by a reload banner instead of leaving a dead page. The print skill keeps its command-line contract in a small entry point: scripts/build-book.mjs parses the options, then delegates the font search, the layout and the two document writers to eight modules under scripts/lib/. The interface tree is documented on Reader interface and the print skill on scripta-book-export.

From a request to a chapter

A chapter is produced by a pipeline in which the only expensive step, the agent run, is surrounded by cheap and durable bookkeeping. The diagram shows the participants and the direction of the work.

The server first writes the turn record with the status queued and appends the job to the queue of that universe, so the request survives a restart before any work starts. A request is never refused because the universe is busy; a busy universe simply has a longer queue, and different universes run in parallel. Before a chapter or rewrite turn starts, the server copies the whole accepted book — canon.md, threads.json, atlas.json and every accepted chapter plus its offer — into a snapshot folder, which is what later allows a rewrite to rewind the book and what restores the last accepted book when a turn fails. A rewrite turn performs its preparation — archiving the old text and offer, dropping later chapters and restoring the pre-chapter state — under the same execution lock, not in the HTTP handler.

The agent runs in the universe folder with automatic approval, without a session and without a title, and receives its prompt on standard input. Its JSON event stream is parsed line by line: assistant text becomes live text for the reader, tool events become the activity list, and the final message becomes the answer stored in the turn record. The prompt requires the chapter file, the offer file and the updated state; it carries the fundamental law and the language of the book, and it is documented in full in DS002-model-and-agent-execution.

The server then verifies the result instead of trusting the agent's report. A chapter turn must have produced exactly one chapters/NNNN-<slug>.md and must pass the skill's own validator, an export turn must have produced a newer .pdf or .docx file, and a chapter outside the configured word band is recorded as a warning rather than accepted silently. On success the turn record is completed, the universe timestamp is touched and a done event closes the stream for that job. On failure the last accepted book is restored from the snapshot, the partial chapter files are removed, the turn is stored with status error, and the reader is offered a retry.

Durability and recovery

Durability comes from writing the intention before the work. A turn is a file, a universe is a folder, and the in-memory job objects are only a live handle on work that is already recorded. Before it touches anything else, the process takes the store lock on universes/.server.lock, because a second server on the same folder would treat the turns of the first one as its own work and mark them interrupted; the lock is released when the process stops, so a restart takes it again, and a lock left behind by a killed process is recognised as stale and taken over. Snapshots are published the same way: a turn copies the accepted book into a fresh staging directory, verifies every entry against the manifest it wrote, and only then renames it into place, so a recovery point is complete or absent and never half-written. That choice shows up at startup: the server scans every universe, re-enqueues the turns recorded as queued in turn order, and converts every turn recorded as running into an interrupted turn whose canon, thread and atlas state is rolled back and whose partial chapter is deleted. A interrupted or failed turn stays visible in the interface with its retry action, and retrying reuses the same turn number and the same request, so the book's history has no gaps.

The queue has no implicit global ceiling: each universe runs at most one turn at a time, and different universes run their turns in parallel. MAX_CONCURRENT_JOBS can bound the number of turns that run across the whole server, and its value is reported by GET /api/config and GET /api/health.

Ownership of the universe folder

Three writers share a universe folder, and each one owns a different set of paths. The server writes metadata and records, the agent writes narrative state, and the print renderer writes only edition files. This split is what makes an interrupted turn repairable and a chapter rewritable.

Path Writer Content
universe.json Server The law, the premise, the ingredients, the summary, the status, the language, the model and the timestamps; the chapter count and the last chapter title are derived on every read.
turns/NNNN.json, turns/NNNN.prev/ Server The durable record of every turn and the full accepted-book snapshot taken before it.
.agents/skills/<name> Server Links that make the product skills visible inside the universe folder.
.agents/import/extracted.json, .agents/import/book.md Server The extraction of an uploaded book, copied into the universe from the upload outside universes/ so the import turn reads its only source of prose from its own folder.
universe-title.txt Agent The short name the agent writes while the title is still provisional; the server adopts it after the first successful chapter, keeps the earlier descriptive line as the summary and removes this hand-off file once the name is taken.
charter.md Server at creation, editable afterwards The permanent rules an agent must respect in this universe, with the law repeated at the top.
canon.md, threads.json, atlas.json Agent The world state, the open and closed threads with their promises, and the thematic axes touched so far.
chapters/, drafts/ Agent The chapters, their offers and the episode plans.
chapters/.history/ Server The archive of superseded chapter versions, written when the rewrite route archives a chapter before it is overwritten or dropped.
exports/edition.json Agent Title, subtitle, dedication, preface and afterword of the printed edition.
exports/<slug>-<YYYYMMDD>.pdf, .docx Print renderer The produced editions, written only by the skill's command.

The file formats, the naming rules and the derived fields are specified in DS004-universe-storage and in the contract reference docs/contracts.md.

The import pipeline

A book that was not written here enters the same store through the import pipeline: the upload is kept outside universes/, its text is extracted without a model, and the universe it becomes is written by an import turn under scripta-import. The pipeline is a second, cheaper path into the same book folder, and its dividing line is the same one the turn pipeline draws: the host reads and records, the agent writes narrative state, and no host component writes a chapter.

Component Responsibility and files
src/import.mjs The entry point of extraction, and the one place chapter segmentation is decided. It decides the format from the bytes first and the file name second, bounds itself with the byte limit before it reads, dispatches to a format reader, and refuses what it cannot read with IMPORT_UNSUPPORTED, IMPORT_TOO_LARGE, IMPORT_NO_TEXT or IMPORT_UNREADABLE. It writes nothing; its result is the book-import.v1 object the pipeline stages.
src/import-docx.mjs, src/import-pdf.mjs, src/import-pdf-text.mjs The format readers, all built on node:zlib and nothing else. The DOCX reader walks the ZIP central directory of the package and inflates only the parts the text needs; the PDF reader reads the indirect objects, inflates the content streams and walks the page tree, and the text reader interprets the operators into lines and paragraphs, warning about what it could not decode. None of them writes a file.
src/imports.mjs The host half of the pipeline. It receives the upload into the workspace while hashing and counting it, writes the import record import.json beside the file, runs the extraction and writes extracted.json and book.md beside the upload, copies the extraction into .agents/import/ of the universe, creates the universe for it, reads where the import continues from the import record the skill writes, and plans the next window within the limits the skill publishes in skills/scripta-import/schema/import.v1.json.
The import turn, prompted by src/prompts.mjs and queued by src/jobs.mjs The only writer of the book. One process per window, reading skill://scripta-import and the staged extraction, it writes chapters/NNNN-slug.md, canon.md, threads.json, atlas.json and drafts/import-progress.json, and nothing else in the folder.
src/turn.mjs Verification of an import turn: the chapters of the range must be on disk, and the skill's validator is run over exactly that range (--chapters <from>-<to>). A missing chapter fails the turn with NO_CHAPTER, a refused set with the validator's own code, and the warnings it reports are copied onto the turn record.
skills/scripta-import/ The skill itself: the instructions and six references that bound one turn, the published contract schema/import.v1.json the host plans a window from, and the validator scripts/validate-import.mjs, which reads the universe and the extraction and writes nothing.

Only three files inside a universe come from this pipeline, and each has one writer: .agents/import/extracted.json and .agents/import/book.md are staged by src/imports.mjs, and drafts/import-progress.json is written by the import turn. The upload itself and its record live in the workspace beside the assessment workspace, never in the store of books. Nothing in the host writes chapters/: the text of an imported book reaches the store only through an import turn, which is what makes an import as reviewable, rewritable and printable as a written book.

Agent and model

The server runs one configured model for every universe and records it in the universe and in each turn. The agent binary is resolved from OMP_BIN with omp as the fallback, and a failed probe stops the server before it listens, because a machine that cannot run the agent cannot continue a book. Each turn is one process with a bounded lifetime, a prompt on standard input, and the folder of its universe as the working directory, which is what allows the agent to read and write the book with its own file tools instead of through an API surface invented for it. The invocation, the prompt contract, the timeouts and the failure repair are specified in DS002-model-and-agent-execution.

The interface in the system

The reader is a static client of the same process. It reads the universe detail for the structure of a book, reads the table of ideas and the library when it has to offer a starting point, fetches chapter prose lazily, and subscribes to the universe event stream while any turn of that universe is unfinished. When the stream cannot be kept open, the client falls back to one stream per job plus polling of the job route, so a buffering proxy costs live text but not correctness. The reading position lives in the URL and in localStorage, and a reload during a turn reconstructs the in-flight work from the job fields of the universe detail. The tree of modules behind it and the surfaces it draws are documented in Reader interface.
