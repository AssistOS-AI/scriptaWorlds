scriptaWorlds Documentation

scriptaWorlds is a place to explore possible universes and to read the story each one produces. A universe is a persistent science-fiction book defined by one fundamental law, and the chapters are written by a coding agent named ALA that runs inside the folder of that universe. A reader starts from a start template of the library or composes a world from the operations of the table of ideas, asks for what should happen next, and reads the result as a book.

What the product does

One Node.js process serves a JSON API and a static reader interface. When a client asks for a chapter, the server records a durable turn, queues it behind the other work of the same universe, and starts one headless omp process in the universe folder. The agent writes the chapter, updates the canon, the thread list and the atlas, and leaves an offer of two or three concrete decisions for the next episode. The reader presses one of those decisions to put its prompt in the request field, can ask for a chapter to be rewritten, or generate a printed edition as DOCX and PDF.

Nothing that matters lives only in memory. A universe is a folder: its law and metadata, its canon, its chapters, its version archive, its turn records and its editions are files, and the queue survives a restart because every turn is written to disk before it runs. An operator can stop the server, copy a folder, restart, and continue reading.

Getting started

The server needs Node.js 20 or later and a working omp command. Both are checked before the listener is created, so a machine that cannot run the agent refuses to start instead of failing later inside a turn. A third tool, pdftotext, is needed only to rebuild the library from the printed book; the generated library is committed.

npm run check     # verify Node.js, the agent binary, the store, the queue, the validator and the renderer
npm run server    # start the API and the reader on http://127.0.0.1:8787

Open the printed address in a browser and the start screen offers three ways in. Custom is one large field for a world of your own: write what exists in it and what is already wrong, press Start, and the text becomes the law of the new universe while its first chapter begins. Library lists the prepared worlds read from the book; choosing one puts its request text into the field at the bottom, where it can be rewritten, and Ingredients shows the table of ideas, twelve families by fifteen operators, where up to six operations compose a world and the request text builds itself. However a world is started, one request creates the universe and its first chapter, and that chapter names the book. The Universes button in the header loads a book that already exists, and the language selector next to it chooses the language of the next book. Operations documents the environment variables, the store lock, the library rebuild, the reload banner, the event stream behaviour behind a proxy, and what to do when the agent, the fonts or the queue need attention.

Repository structure

The repository separates the runtime, the interface, the product skills, the data and the documentation.

Path Role
src/ The Node.js server and store, in modules grouped by responsibility: routing and lifecycle, HTTP helpers, configuration and errors, paths and file helpers, the store lock, the table of ideas, the library, the older proposed-universe catalog, the universe store with its chapters and snapshots, the prompt families and the turn queue with the agent process.
public/ The static reader, served without a build step: one HTML document with the dialogs, a bootstrap module, the modules of public/ui/ with one per surface under public/ui/render/, the Markdown renderer and one stylesheet per surface.
library/ The start templates read from the printed book: index.json with one line per template and one folder per template with its template.json. Generated by npm run library and committed.
data/ periodic-table.json, the twelve families, fifteen operators and one hundred and eighty cells a new universe is composed from.
templates/ The catalog of proposed universes: a main file and optional part files, localized in Romanian and English, each entry with a descriptive title, a law and several openings. It is served by its own route to API clients; the reader interface starts from library/ instead.
skills/ The canonical source of the six product skills, linked into every universe folder: two that write a book and four that are chosen only in a separate design or validation phase.
universes/ One folder per book, with its metadata, canon, chapters, turn records, archives and editions, plus the .server.lock that keeps a single server on the store.
scripts/check.mjs The environment and technology-chain check run by npm run check. npm run library rebuilds library/ from the printed book and npm run table rebuilds data/periodic-table.json; both accept -- --check to verify without writing.
docs/ This documentation, the design specifications under docs/specs/, and the internal contract reference docs/contracts.md.

Conventions and verification

Coding style, module rules, dependency policy, file-size limits and the way verification is organized are defined in DS001-coding-style. The short version is that everything is a Node.js ECMAScript module using built-in modules only, the browser interface is served as plain ES modules, every path to a bundled resource is resolved from the module itself, and a new dependency needs a recorded justification in dependencies.md before it is used.

Behavior is verified with npm run check, which runs scripts/check.mjs against temporary universes: it probes the agent binary, creates and validates universes, reads a chapter back through the store, installs the skill links, runs the narrative validator and the print renderer, and reproduces a restart in which a queued turn is resumed and a running turn is rolled back. The script needs no model budget and always removes the universes it created.

The specifications under docs/specs/ are the source of truth for the product contract. When code changes behavior, interfaces, architecture, workflows or constraints, the documentation and the affected specification are updated together, and wiki.html is the single canonical page for project terminology, including every term linked from these pages.
