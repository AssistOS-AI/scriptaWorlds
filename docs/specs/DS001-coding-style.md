## Introduction

This specification is the canonical source for coding style in scriptaWorlds. It applies to the server in `src/`, the check script in `scripts/check.mjs`, the browser scripts in `public/`, and the six product skills in `skills/`. An agent that changes code reads this file first and follows it together with `docs/contracts.md`, which remains the reference for file formats, HTTP payloads and command-line interfaces.

## Core Content

### Language and module rules

Executable code is JavaScript in `.mjs` files for anything that runs in Node.js, and in `.js` files loaded as ES modules by the browser inside `public/`. Both use `import` and `export` statements with explicit named exports; the repository contains no CommonJS `require`, no transpiler and no bundler. Node.js built-in modules are imported with the `node:` prefix, for example `node:http`, `node:fs/promises` and `node:path`. Relative imports keep the file extension, as in `import { config } from './config.mjs'` and `import { renderMarkdown } from './markdown.js'`.

Asynchronous work uses `async`/`await` and promise-returning APIs. Callback-style code appears only where a Node.js API requires it, such as `createServer`, event emitter subscriptions and stream `data` handlers. File reads that may legitimately fail return a fallback instead of throwing: `readText`, `readJson` and `writeJson` in `src/io.mjs` and `fileExists` in `src/paths.mjs` are the established helpers, and new code reuses them rather than adding a second error-swallowing convention.

Every path to a bundled resource is resolved from the module itself with `import.meta.url`, never from the process working directory. `src/paths.mjs` derives `rootDir`, `universesDir`, `skillsDir` and `publicDir` this way, `src/templates.mjs` resolves `templates/universes.json` from the same root, `src/periodic.mjs` resolves `data/periodic-table.json` and `src/library.mjs` resolves `library/`. This is what lets `npm run server` start from any directory and let either skill script run through its universe symlink.

### English source text

Code identifiers, comments, log lines, error codes and messages, HTTP error payloads and command output are written in English. There is no Romanian prose in `src/`, `scripts/` or `public/`, and the static interface in `public/` is English throughout. Three exceptions are part of the product rather than leftovers and must not be "cleaned up": the language label `Română` in the supported-language list in `src/config.mjs`, which is the name of a language written in that language; the diacritic characters in the identifier rules of `src/paths.mjs`, which exist to transliterate Romanian titles; and the diacritic fixture in `scripts/check.mjs`, which tests that a chapter with Romanian letters survives the store and the renderer. The narrative vocabulary that belongs to a book is not source text either: it lives in the universe folder, follows the language of that book, and is never hardcoded in the server.

### No npm dependencies

The default is Node.js built-ins plus local code. Nothing in the repository may add an npm package, a Python runtime, a transpiler, a bundler or an external test framework for convenience. All six product skills are self-contained and portable: `skills/scripta-ala/scripts/validate-chapter.mjs` reads and validates universe files, `skills/scripta-book-export/scripts/build-book.mjs` with the engines under `skills/scripta-book-export/scripts/lib/` contains its own TrueType parser, layout engine, PDF writer and DOCX writer using `node:zlib` and `node:crypto` for compression and hashing, and the four separate-phase skills each ship their own validator or reviewer with their own small `scripts/lib/` modules. A skill script resolves its paths from its arguments or from `import.meta.url`, never from the process working directory, and never imports `src/`, so a copied skill folder runs outside the repository.

A new dependency is accepted only when the capability cannot reasonably be built from built-ins or reused from code already present. The change must first record, in `dependencies.md` at the repository root or in the affected skill's own `dependencies.md`, the purpose, scope, required or optional status, version or immutable revision, location, accepted rationale, rejected alternatives, upstream source and update procedure, license and bundled notices, startup check, and the remaining removal or replacement opportunity. Vendored source, a globally installed CLI, and a browser or CDN library are dependencies too and need the same record. Permissive licenses are preferred; LGPL is an allowed exception and must be recorded with its relinking and notice obligations. An unresolved license or an unrecorded download is not an accepted dependency.

Two external requirements are recorded in `dependencies.md` at the repository root. Node.js 20 or later is the runtime prerequisite for the server and every script. The `omp` command-line agent is mandatory for chapter and export turns, is resolved through `OMP_BIN` or the bare name `omp`, and is probed at server startup and by `npm run check`. System TrueType serif fonts are an optional requirement of the print renderer, which reports `MISSING_FONT` with remediation steps instead of shipping a font.

A required dependency is checked before the work that needs it, never after. `src/config.mjs` exposes `probeOmp()` and `requireOmp()`; `src/server.mjs` calls `requireOmp()` before it listens and exits with status 1 after printing the remediation message when the probe fails. A new feature that introduces a prerequisite follows the same shape: bounded probe, clear diagnostic on standard error naming the dependency, the required version or capability, the affected command and the installation steps, then a nonzero exit. Startup code never downloads or installs anything.

### Source layout and ownership

`src/` holds the Node.js server, one responsibility per module: `server.mjs` (HTTP routing and process lifecycle; it starts a server only when it is the process entry point and has no import side effects), `http.mjs` (request parsing, JSON and error responses, static files, the SSE connection), `config.mjs` (environment configuration, supported languages, agent probe), `paths.mjs` (repository paths, universe identifiers, project skill discovery and per-universe symlinks), `errors.mjs` (`UniverseError` and `notFound`), `io.mjs` (the low-level text, JSON and padding helpers shared by the store and the turn pipeline), `templates.mjs` (the proposed-universe catalog), `periodic.mjs` (the [Periodic Table of Speculative Ideas](wiki.html#definition-periodic-table): reading the table, resolving [ingredients](wiki.html#definition-ingredient) and composing the law), `library.mjs` (the [library of start templates](wiki.html#definition-library)), `lock.mjs` (the store lock that keeps one server per store), `universe.mjs` (the universe record and the public views of it), `universe-chapters.mjs` (chapters, turns and editions on disk), `universe-state.mjs` (full accepted-book snapshots and crash recovery), `universe-prompts.mjs` (the universe documents and the structured first request), `prompts.mjs` (the agent turn prompts), `omp.mjs` (the `omp` child process and its event stream), `turn.mjs` (what one turn does outside the queue: its prompt family and the verification of its result) and `jobs.mjs` (the [turn queue](wiki.html#definition-queue), the durable turn records and the live events). `public/` holds the static reader and is served without a build step. `templates/` holds the catalog of proposed universes and `data/periodic-table.json` the design instrument. `library/` holds the start templates. `skills/<name>/` is the canonical source of each product skill. `universes/<id>/` holds one book. `scripts/check.mjs` is the environment and technology-chain check, and `scripts/check-store.mjs` and `scripts/check-data.mjs` hold its store-and-queue group and its data-contract group so that each file stays reviewable in one pass; `scripts/build-table.mjs`, `scripts/build-library.mjs` and `scripts/build-catalog.mjs` are data builders that never run as part of the server.

A module owns the files it writes. The server writes `universe.json`, `turns/*` and the `.agents/skills/*` symlinks. The agent, guided by `skill://scripta-ala` and `skill://scripta-book-export`, writes `canon.md`, `threads.json`, `atlas.json`, `chapters/*`, `drafts/*` and `exports/edition.json`. The renderer writes only files under `exports/`. No module writes outside its share, and no module reaches into another universe folder.

Example code, reference material and dependency records stay inside the skill folder that owns them, so copying `skills/<name>/` carries everything that skill needs. New shared runtime code belongs in `src/`, not in a skill, and new skill-local code belongs in that skill rather than in a root-level scratch directory.

### Errors, validation and responses

Server-side failures are raised as `UniverseError` with a stable machine-readable code and an HTTP status, for example `BAD_LAW` with status 400, `NOT_FOUND` with 404, `LATER_CHAPTERS`, `CLOSED` and `ID_TAKEN` with 409, and `AGENT_FAILED`, `NO_CHAPTER` and `NO_EXPORT` with 502. `src/http.mjs` serializes them as `{"error":{"code":"...","message":"..."}}`, and an error thrown without a status is answered as `INTERNAL` with 500. Error codes are part of the interface and are referenced by documentation and by the reader interface; messages are human text in English and may be reworded. `OMP_MISSING` is the one code that never reaches a client: it is produced by the startup probe, which prints the remediation message and exits with status 1 before the server listens.

Input is validated at the boundary where it enters: identifiers against the universe identifier pattern, integers through `parseInteger`, languages against the supported list, request bodies through `readJsonBody` with a size limit, and export file names against the `name.pdf` or `name.docx` pattern. Validation failures answer 400 or 404 before any file is written. A language change for a book that already has chapters is refused with `LANGUAGE_LOCKED`. Content that the agent produced is verified after the turn: a missing chapter file is `NO_CHAPTER`, two files for one chapter number are `DUPLICATE_CHAPTER`, a chapter that fails the skill's structural validator is `INVALID_CHAPTER`, a requested edition format that is missing is `NO_EXPORT`, an edition file that is empty or malformed is `INVALID_EXPORT`, a rewrite without its pre-chapter snapshot is `NO_SNAPSHOT`, and an agent that ends unsuccessfully is `AGENT_FAILED`.

Log lines go to standard output and standard error with a bracketed prefix naming the area, for example `[start]`, `[job]`, `[univers]`. They are operational text in English, they never replace a structured response, and they never carry narrative content.

### Static interface rules

The reader is one HTML document, `public/index.html`, loaded by a small bootstrap module `public/app.js` that only binds the DOM and wires the events. Everything else lives in modules under `public/ui/`: `state.js` (the DOM map, the single state object and the stored keys), `api.js` (the network helper), `errors.js`, `universe.js` (loading a universe and refreshing its detail), `slides.js` (the slide models and their navigation), `overlays.js` (the dialogs), `actions.js` (sending a request), `sse.js` (the event stream and its fallbacks) and the renderers under `public/ui/render/` (`header.js`, `composer.js`, `menu.js`, `reader.js`, `explore.js`, `library.js`, `ingredients.js`). The single light theme is the stylesheets under `public/styles/` (`base.css`, `reader.css`, `live.css`, `explore.css`, `composer.css`, `overlays.css`), linked in that order by `public/index.html`. The interface uses no CDN, no framework and no build step, and it renders chapter Markdown through `public/markdown.js`, which builds DOM nodes and never assigns untrusted text to `innerHTML`. Client behaviour is data-driven: one state object holds the universe detail, the chapter cache, the live job snapshots and the configuration, and rendering functions rebuild the affected surface from that state.

Each module is loaded as an ES module with an explicit `import` and a relative path that keeps the file extension. A module that fails to load must not leave a dead page: `public/index.html` listens for a failed module script and shows a `Reload` banner, and new entry-point scripts follow that convention instead of failing silently.

Network calls go through the single `api()` helper, which sends JSON bodies, checks the response status, and throws an error carrying `code` and `status`. Streaming uses one `EventSource` per universe for the aggregate event stream, with a per-job fallback and status polling. Reading position is kept in the URL query and in `localStorage` under keys prefixed with `scriptaWorlds.`. All interface strings are English literals; user content is the only text in another language, and it is marked with the `lang` attribute of the book.

### File size and line length

Source files stay small enough to review in one pass. The repository ships `fileSizesCheck.sh` at its root for this purpose: it scans the extensions in `FILE_EXTENSIONS` (default `js mjs sys2 md html css json sh`), lists files above 500 lines as a warning and above 800 lines in red, totals lines and sizes per extension, and reports lines longer than 1000 characters in `.md`, `.html` and `.css` files.

Run it from the repository root:

```sh
./fileSizesCheck.sh
FILE_EXTENSIONS="mjs" ./fileSizesCheck.sh
```

Treat the report as review input, not as a build gate. A file that crosses the warning threshold is a signal to split the module along its existing responsibilities: the reader bootstrap `public/app.js` holds only the binding while the surfaces live in `public/ui/*` and the theme in `public/styles/*`; the store, the chapter files, the canon state, the universe documents and the prompts are separate modules in `src/`; and the print renderer keeps its entry point in `skills/scripta-book-export/scripts/build-book.mjs` with its engines in `skills/scripta-book-export/scripts/lib/`. Long lines in Markdown and HTML are expected because documentation prose and specifications are written as one logical line per paragraph and must not be hard-wrapped; the report counts them so that a real code line, which should stay readable in a terminal, is distinguishable from an intentionally unwrapped prose block.

### Verification organization

Behavior is verified by `npm run check`, which runs `scripts/check.mjs` together with its two check groups, `scripts/check-store.mjs` for the store, queue, rewrite and export integrity and `scripts/check-data.mjs` for the design instrument. That script needs no agent budget: it checks the Node.js version, probes the agent binary, asserts the `SKILL.md` of every product skill exists, creates temporary universes, exercises the language and law validation paths, asserts that `.agents/skills` symlinks are installed, reads back a written chapter through the store, closes and reopens a universe, runs the `scripta-ala` validator against a complete fixture and asserts `ok: true`, proves that malformed state answers a structured report rather than a stack trace, runs the `scripta-book-export` renderer and parses its JSON report with a positive page count, verifies that a requested edition format must exist, be non-empty and carry a real document header, lists universes, derives continuation ideas from a written offer, verifies the Periodic Table data (one hundred and eighty cells whose systematic symbol is the family letter plus the operator letter), resolves ingredients and composes the law from them, checks the creation body mapping (a `premise` wins over the older `opening`, a template fills only the gaps, free text becomes the law), audits the start-template library against its own folders and composes a creation from a template, checks that the store lock refuses a second live owner and takes over a stale one, proves that importing `src/server.mjs` neither starts a server nor takes the lock, checks that a short name is adopted while a long descriptive line is refused, checks that a language change rewrites the generated guidance and is refused once the book has chapters, verifies that a rewrite archives a later chapter before deleting it and that a snapshot restore is repeatable, checks that a queued rewrite keeps its operation kind and target across a restart, and finally reproduces a restart: a queued turn stays on disk, a running turn becomes `interrupted`, the accepted book is restored, and the partial chapter disappears. Temporary universes are always removed, and the script exits 0 only when every check passed.

New checks are added to that script in the same style when the repository gains behavior worth re-verifying without an agent: construct the smallest state that exercises the path, read the result back through the public store functions, and assert the observable outcome rather than an internal call. Node.js already provides `node --test` and `node:assert/strict`, so a focused test file using them is the accepted alternative for a behavior that is hard to express as a linear check; no external test framework is added.

Before a change is considered complete, the author runs `npm run check`, plus a scoped reproduction of the changed path. A change that alters behavior, a file format, an HTTP payload or a command-line interface also updates `docs/contracts.md`, the affected specification under `docs/specs/`, and the HTML documentation in the same change set.
