## Introduction

scriptaWorlds turns a chosen world into a book that keeps being written. A reader opens the interface, starts a [universe](wiki.html#definition-universe) from a [start template](wiki.html#definition-start-template) of the [library](wiki.html#definition-library) or composes one from [ingredients](wiki.html#definition-ingredient) taken from the [Periodic Table of Speculative Ideas](wiki.html#definition-periodic-table), asks for what should happen next, and reads the chapter that [ALA](wiki.html#definition-ala) writes in the universe folder. An operator runs the Node.js server that owns the [queue](wiki.html#definition-queue), starts one headless agent process per [turn](wiki.html#definition-turn), and keeps every universe as a folder on disk. A book can also arrive instead of being written: the team uploads a PDF or a DOCX, and the same store ends up holding it, so the books a project reviews, measures and prints are not only the ones it wrote. The behaviors below are the ones a reader, an operator or an integration depends on. Detailed contracts live in the other specifications: `DS002-model-and-agent-execution` fixes the agent invocation and the store lock, `DS004-universe-storage` the files, `DS005-http-api` the routes and payloads, `DS006-reader-interface` the browser surface, `DS007-scripta-ala-skill` and `DS008-scripta-book-export-skill` the two skills that write and print a book, `DS009-start-template-library` the library, `DS014-scripta-import-skill` the import pipeline, `DS012-scripta-continuity-review-skill` and `DS013-scripta-metrics-report-skill` the two review phases, and `docs/contracts.md` the exact formats.

## Core Content

### Main Behavior Components

| Name | Explanation |
| --- | --- |
| Universe creation from a start template or from ingredients | A reader or client picks a start template of the library, or composes a world from at most six cells of the Periodic Table of Ideas, and the server creates the universe folder with the law composed from that choice, seeds its canon with the ingredients and its local skills, and can start the first chapter immediately. |
| Naming the book with a short name | A book created without a title starts with a provisional name; the chapter prompt carries a naming duty, and the server adopts the short name the agent writes into `universe-title.txt` — two to seven words, at most 60 characters — keeping a longer descriptive line as the summary shown under it. |
| Durable per-universe turn queue | Every request becomes a durable [turn record](wiki.html#definition-turn-record) and waits in a per-universe FIFO queue; one turn runs per universe, requests are never rejected while busy, queued turns resume after a restart, and a turn interrupted by a restart becomes retryable with its canon rolled back. |
| Agent turn execution with locally installed skills | One headless [omp](wiki.html#definition-omp) process per turn writes in the universe folder with the fundamental law, the ingredients of the world, the reader's request and the book's language in its prompt, and finds the product skills through the symlinks the server installs in that folder. |
| Chapter offer and continuation ideas | ALA ends each chapter with a teaser and two or three concrete decisions, the reader sends one of them with a click, and the server derives further concrete continuations from the open threads without spending an agent turn. |
| Generic review with no setup | A reviewer asks for a report and gets one: the application supplies its own evaluation profile, freezes the accepted version into a packet with any annotations and corpus text that were declared, runs the review outside the book, and publishes components with an advisory label. Aggregation is optional, uses declared weights under the research policy, and is reported as unavailable with its reason when the caller states no emotional intention. |
| Assessment on request or at the end of an arc | The host freezes the accepted version of a book into a packet outside `universes/` and runs one separate-phase skill over it — a continuity review or an assessment with its twelve metrics and five reports — then can declare an arc complete against that version; runs are deduplicated, they never write into the book, an intervening rewrite makes an older result historical, and a queued run resumes after a restart while a running one becomes retriable. |
| One bounded revision from selected findings | An author selects findings from a review and the qualities to preserve; the revision request carries them with the version they were reported against, the prompt states them and one candidate version is asked for, and evidence from another version is refused as stale instead of applied. |
| Importing a book the team did not write | A reader uploads a PDF or a DOCX, the server stores it outside `universes/` and extracts its text without a model, and bounded import turns write the book into a universe of its own under `scripta-import`, each verified by that skill's validator, so the imported book can afterwards be read, reviewed, measured, rewritten and printed like one written here. |
| Team feedback on a frozen version | The people who read a book answer a frozen questionnaire against a copy of the exact text they were shown, and what they said is stored beside the reviews rather than inside the book: a target is frozen once per version and scope, a response is attributed to an identity the server issued, a skipped question stays skipped, nothing is averaged, and a model's annotation is never counted as something a reader said. |
| Chapter rewrite with canon restore and version history | A reader who says what is wrong with a chapter gets a new version of that chapter; the current version and its offer are archived, previously superseded chapters can be dropped with explicit confirmation, and the book is rewound to the state before the chapter under the same execution lock, so a failed or interrupted rewrite restores the last accepted book. |
| Printed edition export | A reader generates a [DOCX or PDF edition](wiki.html#definition-edition) of the book so far; the same durable turn pipeline runs the print renderer, the produced files appear in the interface, and the server refuses to report success when no edition file was produced. |
| Reader interface with live progress | The browser interface reads the book one chapter at a time, shows unfinished work and the agent's live activity in the same reading flow, keeps the reading position across reloads, and reloads the universe when a turn finishes. |

### Universe creation from a start template or from ingredients

The reader is a person who wants a story about a world whose rules they chose. The outcome is a new universe that exists on disk, is listed for everyone who reaches the server, and can be continued. There are two ways to trigger it: from the start screen of the interface, where the reader either picks a start template of the library or composes a world from cells of the Periodic Table, or from an integration with `POST /api/universes` carrying `library`, `elements`, or both together, and the optional `title`, `law`, `premise` (or its older name `opening`), `summary`, `language`, `prompt` and `start`. The older `templateId` of the proposed-universe catalog is still accepted.

A start template contributes the world, not the text of the book. `library` names one template of `library/`, and `creationFromTemplate` turns it into the fields creation accepts: the law from the prohibition of the night, the premise from its situation and its central problem, the cells of the table as the ingredients, and an empty title with the title of the template as a provisional name. The reader may add operations of their own on top of a template in the same request: the cells of the template and the submitted `elements` are merged into one list without duplicates and cut to six, and one law is composed from all of them, so a world can be a night of the book with two more operations taken from the table. The empty template is the exception: it states no prohibition and has no cells, so the request the reader sends becomes the first law of that world. What a template is and how it is produced is in `DS009-start-template-library`.

The reader may also compose the world directly. `elements` carries at most six [ingredients](wiki.html#definition-ingredient): symbols of the table such as `CA`, or elements the reader proposed as `{custom: true, name, family, operator, note}`. A law a client writes is kept and the ingredient lines are appended to it (`composeLaw`), so the human law stays first; a universe with neither a law nor an ingredient is refused with `BAD_LAW` unless the body carries `prompt`, because text sent with neither a template nor an ingredient is the free-text start: it becomes the law of the new world, exactly as the empty start template composes one from the reader's request, so a reader who only types a request still gets a world. Malformed input is refused before anything is written: `BAD_ELEMENTS` for a value that is not a list, for more than six ingredients or for an entry that is neither a symbol nor an object; `UNKNOWN_ELEMENT` for a symbol the table does not contain; and `BAD_ELEMENT_NAME`, `BAD_ELEMENT_FAMILY` or `BAD_ELEMENT_OPERATOR` for a proposed element whose name is missing or whose family or operator the table does not have. An overlong title answers `BAD_TITLE`, an unknown language `BAD_LANGUAGE`, and a title that cannot be turned into a free identifier `ID_TAKEN`.

The ingredients travel with the book, which is the point of choosing them. They are written into `universe.json` as `elements`, seeded into `canon.md` under `Ingredients`, listed in the universe's own `AGENTS.md`, repeated in every chapter and rewrite prompt, and named in the structured first-chapter request, so the agent writes from the reader's recipe rather than from a summary of it.

The first chapter request is the reader's own text. When `start` is exactly `true` the server queues the first chapter immediately with `prompt` — the text the reader edited in the request field — as its message, falling back to the `request` of the start template and, only when both are empty, to a structured request built from the title, the law, the premise and the ingredients. Nothing is created before the reader sends that text: choosing a template, or choosing ingredients, only puts text into the field.

Naming is a behavior of its own. A universe created without a client title gets `autoTitle: true` and a provisional name, which is the title of the start template or a generic placeholder. The prompt then carries the naming duty, [ALA](wiki.html#definition-ala) writes a [short name](wiki.html#definition-short-name) to `universe-title.txt` in the language of the fiction, and after a successful chapter turn the server adopts the first non-empty line only when it has two to seven words and at most 60 characters, clears `autoTitle` and removes the hand-off file, which exists only while the book has no name. A longer, descriptive line is refused and the duty returns at the next chapter. When the title being replaced was itself a whole sentence, that sentence is kept as `summary`, which the interface shows as a discreet line under the short name.

Creation writes the whole starting folder: `universe.json` with the title, the flag, the summary, the composed law, the premise, the ingredients, the language, the status `open` and the configured model; `charter.md` with the permanent narrative rules and the law as an inviolable section; `canon.md` with the law as its first section, the `Ingredients` section and the opening recorded; empty `threads.json` and `atlas.json`; the universe's own `AGENTS.md` with the working rules and the ingredients; the `chapters/`, `turns/` and `exports/` folders; and the `.agents/skills/<name>` symlinks to the project skills. The response is `201` with the public universe record and, when `start` is true, the job that will write the first chapter.

The boundary is that creation succeeds or fails as a whole: a rejected law, ingredient, title or language leaves no folder behind, and a created universe is always complete enough for an agent to work in it. A universe keeps no link back to the template or to the catalog entry it started from, so editing `library/` or `templates/` never rewrites a book that already exists; both are read-only input for the server.

### Importing a book the team did not write

The reader is a person who has a book as a file and wants it inside the project. The outcome is a universe that holds that book: the same `chapters/NNNN-slug.md` files, the same canon, threads and atlas, and the same ability to be continued, reviewed, measured, rewritten and printed as a book written here. The trigger is the `Import` tab of the start screen, or `POST /api/imports` with the file itself. A book that arrives this way is archived rather than written: importing copies the book's own prose and describes it, and an import that invented text would be worthless.

The pipeline has three stages, and only the last one can write a book. The upload is streamed into a folder of its own under the [assessment workspace](wiki.html#definition-assessment-workspace) while it is hashed and counted, and a body past the byte limit is refused during the transfer rather than after it. The [extraction](wiki.html#definition-extraction) is then deterministic and starts no model: the server reads the PDF or the DOCX itself, segments it at the boundaries the file shows — a DOCX heading style, or a short standalone heading line in a PDF — and records what it found, with the title, the author, the language, the chapters and their word counts, and a warning for everything it could not do, such as a page set in a subset font or a book whose chapter boundaries it could not detect. A scanned book without a text layer is refused with `IMPORT_NO_TEXT` instead of being guessed at, and the panel that started the upload shows the record's own state and the refusal in the server's own words.

The universe is then created and the book is written into it by [import turns](wiki.html#definition-import-turn). One turn carries a bounded window — at most three extraction chapters and at most 6 000 words of their prose, and always at least one chapter, so a single long chapter travels alone — which is the only reason a long book can be imported at all. Each window is a normal durable [turn](wiki.html#definition-turn) of the same queue: it takes a slot, is snapshotted before it writes, streams its progress like any other turn, and is verified at the boundary, and the verification is the import skill's own validator rather than the chapter validator, because a window legitimately produces fewer, or more, chapter files than it holds extraction chapters, and a chapter the extraction declares with no prose is skipped rather than invented. Where the next window starts is read from the record the turn itself writes inside the universe, `drafts/import-progress.json`, because a chapter file does not carry the number of the extraction chapter it came from.

The book that results behaves exactly like a written one, and the difference is deliberately visible rather than hidden: the import is marked by that record inside the universe, the universe is created with the law that says the text is the law, and while the import is still running a reader can see how much of the book is in the store and which window comes next. The extraction contract, the segmentation rules, the faithfulness rules for the prose and the state files, and the validator's own codes are in `DS014-scripta-import-skill`; the routes and their payloads are in `DS005-http-api`; the folder that holds the upload and the extraction staged into the universe is in `DS004-universe-storage`.

The boundary is that importing writes no prose of its own and never decides that a book is finished. It copies what the file says, it reports what the extraction could not read, and it stops when the record says that every extraction chapter has been imported or skipped; everything written afterwards belongs to `scripta-ala` and to the separate phases, exactly as for a book written here.

### Durable per-universe turn queue

The reader is the person who sends several requests in a row, or closes the browser while a chapter is being written. The outcome is that no request is lost and no universe writes two chapters at once. The trigger is any of `POST /api/universes/:id/turns`, `POST /api/universes/:id/turns/:number/retry` or `POST /api/universes/:id/chapters/:number/rewrite`, and the observable result is a `202` response with a job snapshot, including a queue position for a request that is waiting.

The rule is a FIFO queue per universe with no implicit global ceiling. A new request is appended even when the universe is already running a turn, so there is no busy error to handle; different universes run their turns in parallel; and `MAX_CONCURRENT_JOBS` optionally caps how many turns run across the whole server at once, with `0` or an unset value meaning unlimited. The queue is not kept in memory only. Enqueueing writes the turn record to `turns/NNNN.json` with status `queued` before the job is visible, then flips it to `running` when the turn starts and to `done` or `error` when it ends.

Restarting the server is the behavior that makes this contract visible. At startup the server scans every universe: turns recorded as `queued` are re-enqueued in turn-number order and continue with the same request — including the operation kind and, for a rewrite, its target chapter — and turns recorded as `running` become `interrupted`. An interrupted turn also has the last accepted book restored from the snapshot taken before it, and the candidate files that are not part of that snapshot removed, so a restart never leaves half a chapter in the book. A turn whose snapshot is missing or unusable becomes [recovery_required](wiki.html#definition-recovery-required) instead: its book refuses every new turn with `409 RECOVERY_REQUIRED` until the accepted state is established by hand, because writing on top of an unknown state would entrench the wrong book. An interrupted or failed turn stays visible in the interface with a retry action, and `POST /api/universes/:id/turns/:number/retry` reuses the same turn number and request; any other status is rejected with `NOT_RETRYABLE`.

The boundary is that the durable record is the turn file, while the job identifiers and the event buffers live only as long as the process. `GET /api/jobs/:jobId` for a job from a previous process answers `NOT_FOUND`, and the durable state of that work is read from the universe detail instead. The queue also refuses to start a chapter turn for a universe whose status is `closed`, answering `CLOSED`.

### Agent turn execution with locally installed skills

The reader is the person waiting for chapter five, and the operator is the person who installed the agent binary. The outcome is a chapter file, an updated canon and an offer, written by an agent that had the law, the ingredients of the world, the request and the narrative rules in front of it. The trigger is a queued turn reaching the front of its universe's queue.

The server composes the prompt, snapshots the whole accepted book, starts one `omp` process in the universe folder with the configured model and the configured deadline, streams its events to the interface, then verifies what it wrote. The process is invoked with automatic approval and without a session or a title, and the prompt arrives on standard input, so the agent behaves as a batch writer of files rather than as an interactive assistant. The prompt carries the inviolable law, the ingredients of the world, the book's language, the reader's request, the exact file to write, the word target, the required canon and offer updates, and the instruction to read the narrative skill before writing. `DS002-model-and-agent-execution` states the full invocation and prompt contract.

Two mechanisms are hidden from the reader but decide whether a turn can work at all. The universe folder gets `.agents/skills/<name>` symlinks to `skills/<name>` in the repository: `syncUniverseSkills()` creates them when a universe is created and refreshes them at every server startup, so the prompt's references to `skill://scripta-ala` and `skill://scripta-book-export` resolve inside the universe even though the skill source lives outside it, and a stale link to a skill that no longer exists is removed. The agent can therefore read the narrative rules, the file schemas and the atlas palette from the folder it is working in, without network access and without a global installation.

A reader may attach the [approved directions](wiki.html#definition-approved-direction) of a separate design phase to a writing request. They reach the agent as input data under the law, they are recorded with the turn together with the approval they came from, and a malformed list is refused with `400 BAD_DIRECTIONS` before anything is queued. The other mechanism is verification rather than trust. The server rejects a turn whose chapter file is missing (`NO_CHAPTER`) or duplicated for the same chapter number (`DUPLICATE_CHAPTER`), refuses a chapter that fails the skill's own structural validator (`INVALID_CHAPTER`), rejects an export that produced no edition file (`NO_EXPORT`), records a warning when the chapter is outside the expected length band, refuses a chapter whose structural contract is broken — including a missing or unusable offer, because the offer is how the reader continues the book (`INVALID_CHAPTER`) — and treats a nonzero exit, a spawn failure or a timeout as `AGENT_FAILED` with the last accepted book restored from its snapshot. A reader therefore never sees a chapter that does not exist on disk or a chapter whose state files are structurally broken, and an operator reading the turn record sees the narration, the tool list and the tail of the agent's raw output for a failed run.

The boundary is that the agent, not the server, owns narrative content. The server owns the queue, the turn records, the universe record and the symlinks, and it never writes `canon.md`, `threads.json`, `atlas.json`, `chapters/*` or `exports/edition.json`.

### Chapter offer and continuation ideas

The reader is the person who finished a chapter and does not know what to ask for next. The outcome is a concrete next step that starts a chapter with one click, in the book's language, without the reader composing a prompt. The trigger is the reading position reaching the last chapter, and the observable result is the [composer](wiki.html#definition-composer) area showing ALA's teaser and two or three labeled decisions.

The offer is written by the agent as `chapters/NNNN-offer.json` for the chapter it just finished, and the server normalizes it before publishing: a teaser bounded to 1200 characters and up to four options, each with a label bounded to 80 characters and a prompt bounded to 600 characters, where an option without a label falls back to the beginning of its prompt. The store exposes the offer on the chapter list item and on a single chapter read, so both the summary response and the chapter response carry the same object. Selecting an option submits its prompt as a normal chapter turn; editing it puts the same text in the input field so the reader can change it before sending. A chapter whose offer is missing or unusable is refused at acceptance, because the offer is how the reader continues the book, and [reads during generation](wiki.html#definition-accepted-view) never show a chapter that is still being written; a chapter stored before this rule still renders, with the interface showing an idea derived from the open threads instead of a missing offer.

The secondary behavior is the idea list, which costs no agent turn. `GET /api/universes/:id/ideas` derives up to four concrete continuations from the universe's own state: up to two open threads or promises ordered by their due chapter, at most one deferred answer, the first option of the last chapter's offer, a continuation of the last chapter title when no offer exists, and a time-skip suggestion. The prompt text is phrased in the book's language and the labels are shortened for buttons, and duplicate prompts are removed. The interface uses the first idea as a fallback suggestion in the composer when the current chapter has no offer.

The boundary is that ideas are derived from stored state, not generated: if the canon, thread list and chapter titles are empty, the idea list shrinks to the generic continuation and time-skip entries, and no model call is made to fill the gap.

### Chapter rewrite with canon restore and version history

The reader is the person who liked the book but not chapter four. The outcome is a replacement chapter that keeps the universe's laws and the continuity of the earlier chapters while obeying the reader's complaint. The trigger is the rewrite action on a chapter, or `POST /api/universes/:id/chapters/:number/rewrite` with instructions and a `dropLater` flag.

The server refuses to guess. Instructions shorter than 10 characters are rejected with `BAD_INSTRUCTIONS`, a closed universe is rejected with `CLOSED`, an unknown chapter with `NOT_FOUND`, a rewrite that would discard later chapters is rejected with `409 LATER_CHAPTERS`, and a rewrite whose target changed while the request waited, or that met a later chapter the request never authorised, is refused with `409 STALE_REQUEST` carrying the numbers of those chapters inside the error object, so the client can ask for confirmation and resend with `dropLater: true`. When the reader confirms, the later chapters are archived and removed. In every case the server copies the current version of the chapter, together with its offer, to `chapters/.history/NNNN-vK.md` before anything is overwritten, and the chapter read exposes `rewritten` and the number of archived versions, so the interface can mark a rewritten chapter and say how many earlier versions exist. The route itself only validates and enqueues; the archive, the drop and the rewind happen when the job runs, under the same per-universe execution lock as generation, so an active writer never sees its input files change beneath it.

The hidden mechanism is the snapshot of the accepted book. Before every turn the server copies the whole book — `canon.md`, `threads.json`, `atlas.json` and every accepted chapter plus its offer — into a fresh staging directory, verifies it against the manifest it wrote, and publishes it as `turns/NNNN.prev/`, so a snapshot is complete or absent and never half-copied; a restore puts back both the bytes and the membership of the accepted book, and repeating it changes nothing. That snapshot is deliberately kept after a successful turn, because rewriting chapter four requires the book as it was before chapter four existed. A rewrite starts by restoring the canon, threads and atlas from the ancestry of the chapter it rewrites — the state that preceded that chapter when it was first written, which stays the same through later rewrites of it — which is also the repair path after an interrupted turn, and then runs an agent turn that asks for the same chapter number, carries the old text as reference and requires the state files to be rewritten as if the new version had always been the chapter. Because the snapshot is a full copy of the accepted book, a failed or interrupted rewrite puts the old chapter, its offer and the state back together in one step; a rewrite whose pre-chapter snapshot is missing fails with `NO_SNAPSHOT` instead of silently continuing from today's canon.

The boundary is that the turn number and the chapter number are different identities. A rewritten chapter gets a new turn, so its discussion log stays complete and the previous log is not overwritten; the mapping from chapter to producing turn is exposed as `turnNumber` on the chapter, and `GET /api/universes/:id/turns/:number` addresses turns, not chapters.

### Printed edition export

The reader is the person who wants the book as a file. The outcome is a DOCX or a PDF edition of the chapters so far, with a title page, a table of contents, page numbers and edition labels in the book's language, downloadable from the interface. The trigger is the generate-edition action, or a chapter turn submitted with `kind: "export"` and a format of `docx`, `pdf` or `both`.

The edition runs through the same durable turn pipeline as a chapter, which is what makes it reliable: it takes a queue slot, writes a turn record, streams progress, is bounded by its own timeout, and can be retried after a failure. The agent first writes the [editorial metadata](wiki.html#definition-edition-metadata) to `exports/edition.json` and then runs the print renderer, which writes the edition files into `exports/`. The server then requires one non-empty, valid file for every requested format — a PDF must begin with its header and a DOCX must be a ZIP container — newer than the start of the turn, and fails the turn with `NO_EXPORT` when a requested format is missing and `INVALID_EXPORT` when the produced file is empty or malformed, so a reported successful edition always corresponds to a real file on disk. Every edition is exposed in the universe detail with its format, size, creation time and download URL, and the `Edition` dialog offers a download for the newest file of each format, shows `not yet` before one exists, and shows the state of an export turn instead of the generation action while one is queued or running.

The rendered files are served only through `GET /api/files/:id/:name`, which accepts a name matching the `.pdf` or `.docx` pattern inside that universe's `exports/` folder and answers as an attachment; anything else is rejected with `BAD_NAME`, so a client cannot read arbitrary files of the universe folder or of the repository.

The boundary is that the renderer reads and never writes the book: `DS008-scripta-book-export-skill` fixes the accepted chapter Markdown subset, the naming convention of the produced files, the font requirement that produces `MISSING_FONT`, and the fact that a missing edition is an error rather than an empty success.

### Team feedback on a frozen version

The reader is a member of the team who has just read the book. The outcome is a durable record of what they thought of the text they were shown — not a score, and not a remark lost in a chat. The trigger is the feedback control in the toolbar of a chapter, or the routes of the [reader feedback](wiki.html#definition-reader-feedback) family, and what they said is stored beside the reviews rather than inside the book, because it is evidence about one version of the text and it has to survive every rewrite and every re-import of the store.

The mechanism is a frozen target. When a reader opens the questionnaire, the accepted version they are looking at is copied out of `universes/` into the workspace of `DS004-universe-storage` together with the questionnaire of the moment, and the target identifier is derived from the universe, the version and the scope, so two readers of the same text answer the same frozen copy and no version is frozen twice. The text of a target is a copy byte for byte, which is what makes a quoted passage still point at the same words after the book has changed, and a response whose target is no longer the accepted version is reported as historical instead of being refused, because an opinion about an older text is evidence about that older text.

A response is one reader's answers, comments and quotations, attributed to an identity the server issued for that book and remembered by the browser. A question may be skipped, and a skipped answer stays visible as skipped rather than being read as a low score; a quotation must resolve inside the frozen copy, and the limits on a comment, a quotation and a list are enforced before anything is written. Nothing is averaged anywhere, and the counts keep provenance apart: a response whose reader kind is `model` or `synthetic` is listed and never added to the number of team readers, because the difference between what a reader said and what a model annotated is the point of keeping both. A reader may withdraw a response, which leaves it readable and marked while its answers are taken back, and correct one of their own, which is a new response naming the one it replaces. A book's feedback is also readable as one document rather than as a folder: `GET /api/universes/:id/feedback/export` returns the whole store as a reproducible dataset and `GET /api/universes/:id/feedback/summary` returns the counts and distributions of it, so another tool can read what the team said without knowing the workspace layout. The records, the questionnaire and the limits are in `docs/contracts.md` §8.7, the routes in `DS005-http-api`, the folders in `DS004-universe-storage`, and the surface a reader uses in `DS006-reader-interface`.

The boundary is that feedback never changes the book. It is written by the server, never by the agent, and never inside `universes/`; turning what readers said into a revision is still a human act — a rewrite request, or an approved direction carried by a later writing request — and not a side effect of answering a questionnaire.

### Reader interface with live progress

The reader is the person holding a phone. The outcome is that the book reads like a book, the work in progress is visible where it belongs, and nothing has to be managed. The trigger is opening the server address in a browser: with no universe loaded the reader sees the start screen, and with a universe loaded the reader sees the book.

The start screen is where a book begins. It has four tabs and no form fields of its own: `Custom` holds one large field whose text becomes the law of a new world and creates it directly with `Start`; `Import` takes a PDF or a DOCX, shows what the server read out of it and carries its import into a universe; `Library` lists the start templates of the library with their title, sector, genealogy, cell symbols and one-line summary; and `Ingredients` shows the table as a grid of twelve families by fifteen operators with a search box, a legend of the operators and at most six choices. `Library` and `Ingredients` create nothing by themselves: a chosen template and the chosen operations are composed into the request field of the [composer](wiki.html#definition-composer), which is the only input of the interface, and the universe exists only after the reader edits that text if they wish and presses `Send`. The two composing tabs do not cancel each other, so a world may be a night of the book with operations added on top of it. The language of the fiction is chosen in the header, not on the start screen, and is remembered in the browser.

Reading is the primary flow. The header shows the short title with its summary underneath, the language, the `Universes` dialog and the `⋯` menu, and a second row of chapter numbers between `‹` and `›`; a turn that is running or queued is one of those numbers, carrying the number of the chapter it will write and marked as in progress. A chapter slide holds the chapter and nothing else: `Chapter N · Title` with a toolbar of icon controls — each an inline drawing with one accessible label — then the text. The reader's own request is never rendered in the slide; it is read from the `What you asked for` dialog behind the `i` control, and the console control unfolds the record of the turn that wrote that chapter inside the card, collapsed by default. The toolbar is also where the book's analysis is reached: the feedback control opens the questionnaire about the text on screen, the review control opens a review of the frozen version with that chapter in charge of its scope, and the report control opens the reports a run published.

Nothing unfolds in the flow. Every secondary surface is a dialog: `Universes`, `Edition` (the `⋯` menu, which carries the downloads, `Generate edition` and `New universe`), `What you asked for`, `Rewrite chapter`, `Review` (the form: what to run, what to cover, who produces the observations, and the optional aggregate), `Reports` (one run and every file it published), `Reader feedback` (the questionnaire and what the team said) and `Details`, the last one showing what the book says about the cell, operator or family that was clicked in the ingredients grid. Each one is a fixed overlay with a dimmed backdrop, a visible `×`, and each closes on `Esc`, on a click on the backdrop and through the `×`. Closing and reopening a universe have no control in the interface; they remain API calls, and a reader leaves a book through `New universe`, which returns to the start screen.

Live progress is a project-specific behavior rather than an incidental detail. `GET /api/universes/:id/events` streams the events of every turn of a universe, and the interface shows a queued turn as a waiting item with its queue position and a running turn as its own numbered slice with the agent's live text, its phase line and its recent tool calls. When a turn finishes the universe is reloaded; if a new chapter arrived while the reader was not at the end, a discreet line offers to read it instead of moving the reader away. If the stream fails, the client falls back to a per-job stream plus polling, so a proxy that buffers event streams degrades the live text rather than the reading.

Two smaller guarantees keep the surface trustworthy. Reading position lives in the URL query and in `localStorage`, so reopening the page returns to the same chapter, and a reload during a turn recovers the in-flight work from `activeJob` and `queuedJobs` instead of showing an idle book. The interface is English while the book is not: chapter prose is rendered with the `lang` attribute of the universe, the accepted chapter Markdown subset is fixed by `docs/contracts.md`, and the renderer in `public/markdown.js` supports headings, paragraphs, blockquotes, scene breaks and bold or italic emphasis, which is exactly what the narrative skill is allowed to write. A module that fails to load shows a `Reload` banner instead of leaving the reader in front of a dead page.

The boundary is that the interface has no settings surface for the language of an existing book and no account system, and the identity a questionnaire is answered under is a name plus an identifier the server issued for one book rather than an account that could unlock anything. The language is chosen in the header before creation and can be changed afterwards only through `POST /api/universes/:id/settings`, and only while the book has no chapters; everything the interface can reach is readable and writable by anyone who can reach the address.
