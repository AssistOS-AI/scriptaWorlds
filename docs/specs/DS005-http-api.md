## Introduction

The server exposes one JSON HTTP API and one static file surface for the [reader interface](wiki.html#definition-reader-interface). The browser interface, and any other client that wants to build on scriptaWorlds, uses that API to read the [design instrument](wiki.html#definition-design-instrument) and the [start templates](wiki.html#definition-start-template), read universes, create them, queue turns, follow their progress, download editions, import a book the team did not write here, run a review of one frozen version and collect what the team's readers said about it. This specification states the routes, the payloads and the failure contract. Storage details behind the routes are in `DS004-universe-storage`, the library of start templates in `DS009-start-template-library`, queue semantics in `DS003-main-behavior`, the agent invocation that a turn triggers in `DS002-model-and-agent-execution`, the import pipeline in `DS014-scripta-import-skill`, the review phases in `DS012-scripta-continuity-review-skill` and `DS013-scripta-metrics-report-skill`, and the client that consumes the API in `DS006-reader-interface`. Exact JSON examples live in `docs/contracts.md`.

## Core Content

### Process and transport

The server is started with `node src/server.mjs`, which is what `npm run server` runs. It listens on `HOST` and `PORT`, defaulting to `0.0.0.0` and `8787`, creates the `universes/` folder when needed, takes the store lock `universes/.server.lock` so that only one instance owns the store, probes the agent binary and exits with status 1 when the probe fails, recovers interrupted and queued turns for every universe, refreshes the per-universe skill symlinks, and then starts listening. On startup it prints the loopback URL, every non-internal IPv4 address of the machine and the agent and model in use, so an operator can open the book from a phone on the same network. `SIGINT` and `SIGTERM` release the lock, close the listener and exit. The lock, the queue it protects and the rule that importing this module has no side effects are specified in `DS002-model-and-agent-execution`.

Every request path that does not start with `/api` is served as a static file from `public/`, with the correct content type for HTML, JavaScript, CSS, JSON, SVG, images, fonts, PDF and DOCX, and with caching disabled. Only `GET` and `HEAD` are accepted there; another method answers `405`. Unknown `/api` paths answer `404` with the code `NOT_FOUND`.

### Error envelope

Every API error is a JSON body of the shape `{"error":{"code":"...","message":"..."}}` with the matching HTTP status. [error code](wiki.html#definition-error-code) is stable and machine-readable and is part of the contract; `message` is English human text that may be reworded. Two optional fields can travel with an error when a client needs them to proceed: `laterChapters` for a confirmed rewrite, and `details` for additional structured context. Request parsing adds its own codes: `TOO_LARGE` with status 413 when a body exceeds 512 KiB, and `BAD_JSON` with status 400 when a body is not a JSON object.

Statuses follow a fixed mapping: `400` for invalid input, `404` for a missing universe, chapter, turn, job or route, `405` for a wrong method, `409` for a conflict or a refused state transition, `410` for an upload that is no longer in the workspace, `413` for an oversized body, `500` for an internal failure, and `502` for a turn whose agent run failed or whose result did not appear on disk.

The codes a client is expected to handle are: `BAD_ID`, `BAD_TITLE`, `BAD_LAW`, `BAD_LANGUAGE`, `BAD_MESSAGE`, `BAD_KIND`, `BAD_FORMAT`, `BAD_NUMBER`, `BAD_NAME`, `BAD_FILE`, `BAD_DIRECTIONS`, `BAD_FINDINGS`, `BAD_INSTRUCTIONS`, `BAD_PHASE`, `BAD_TRIGGER`, `BAD_MODE`, `BAD_ARC`, `BAD_ACTION`, `BAD_STATUS`, `UNSTABLE_VERSION`, `NO_PROFILE`, `NOT_CANCELLABLE`, `NO_PACKET`, `MISSING_FILE`, `ALREADY_DECIDED`, `BAD_DECISION`, `BAD_PROPOSAL`, `UNSUPPORTED_INPUT`, `MISSING_RESOURCE`, `HASH_MISMATCH`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `ID_TAKEN`, `CLOSED`, `LATER_CHAPTERS`, `NOT_RETRYABLE`, `LANGUAGE_LOCKED`, `AGENT_FAILED`, `NO_CHAPTER`, `DUPLICATE_CHAPTER`, `INVALID_CHAPTER`, `NO_ANCESTRY`, `STALE_REQUEST`, `RECOVERY_REQUIRED`, `SHUTTING_DOWN`, `NO_EXPORT`, `INVALID_EXPORT`, `IMPORT_FILENAME`, `IMPORT_UNSUPPORTED`, `IMPORT_TOO_LARGE`, `IMPORT_EMPTY`, `IMPORT_UNREADABLE`, `IMPORT_NO_TEXT`, `IMPORT_MISSING`, `NOT_EXTRACTED`, `NO_IMPORT_RECORD`, `INVALID_FEEDBACK`, `READER_NOT_FOUND`, `STALE_TARGET`, `NO_FEEDBACK`, `COMPARISON_NOT_SUPPORTED`, `COMPARISON_UNKNOWN_VERSION`, `BAD_COMPARISON`, `NOT_APPROVED`, `CONFLICT`, `BAD_JSON` and `TOO_LARGE` for the API surface, and `BAD_ELEMENTS`, `BAD_ELEMENT_NAME`, `BAD_ELEMENT_FAMILY`, `BAD_ELEMENT_OPERATOR`, `UNKNOWN_ELEMENT`, `BAD_TEMPLATE`, `UNKNOWN_TEMPLATE`, `NO_TABLE` and `NO_LIBRARY` for the ingredients and the start templates. The same code can carry different statuses by route: `UNKNOWN_ELEMENT` is `400` when a creation body names a symbol the table does not contain, and `404` when the single-cell route is asked for one. `INTERNAL` with status 500 is the fallback for an error that carries no code, and `FORBIDDEN` with 403 is answered by the static surface when a path tries to leave the directory it serves, not by the API. `OMP_MISSING` never travels over HTTP: it is a startup probe failure, described in `DS002-model-and-agent-execution`. The status transitions of a universe are set by the open and close routes from literal values, so the store's own status validation is not reachable from the API.

### Configuration, health, the design instrument and the start templates

`GET /api/health` answers `ok`, the agent command, its version, the configured model, the effective concurrency limit as `null` when unlimited, and the process uptime in milliseconds. It reads no universe and is the cheapest way to check that a server is running.

`GET /api/config` answers the model, the supported languages as `code` and `label` pairs, the accepted edition formats `docx`, `pdf` and `both`, the effective concurrency limit, and the chapter word band as `chapterWords` with `min` and `max`. A client builds its language selector from this response rather than from a hardcoded list.

`GET /api/table` answers the design instrument, `data/periodic-table.json`, as `families`, `operators` and `elements`: twelve families as objects carrying `name`, `label`, `letter`, a `note` (the one substantial sentence of that family) and the `cells` of that family (the symbols in grid order), fifteen operators with their `name`, `does` and `letter`, and one hundred and eighty cells carrying `id`, `symbol`, `bookSymbol`, `name`, `family`, `operator`, `gist`, `prompt`, `ingredient` and `landmark`. Two fields say the same cell in two shapes: `prompt` is the cell as one ready sentence a client can put into the request field unchanged (`A universe where organisms live in degenerate matter.`), and `ingredient` is the sentence a reader and the agent read — the name, the mechanism and the family and operator in words, with no letter code (`Neutron Life: a universe where organisms live in degenerate matter (life and evolution, extension).`). The client builds the ingredients grid from this response, and the route never writes anything. A missing or unreadable data file answers `NO_TABLE` with status 500.

`GET /api/table/cells/:symbol` answers what is worth reading about one cell, under `cell`: `id`, `symbol`, `bookSymbol`, `name`, `family`, `familyLabel`, `familyNote`, `operator`, `operatorDoes`, `essence`, `prompt`, `ingredient`, `seenIn` and `scenes`. `essence` is the idea of the cell in one line, `familyNote` is the one substantial sentence of its family, `seenIn` is the work the cell comes from, and `scenes` lists up to three start templates that already work that cell, each with its `slug`, `title`, `sector`, the `situation` it opens with and its central `story`. The route deliberately does not return the prose sections of the book for a cell: they repeat the same skeleton for all one hundred and eighty cells, so the answer keeps only what differs between them. The symbol is matched case-insensitively against the systematic symbol of the table — the family letter followed by the operator letter, as in `CA` for cosmos plus alteration — and an unknown one answers `404` with the code `UNKNOWN_ELEMENT`. The route exists so that the grid stays small enough to load at once and one cell is read in full only when a reader asks for it.

`GET /api/library` answers the index of start templates as `source`, `note`, `count`, `templates` and `cellScenes`, where each entry of `templates` carries `slug`, `kind`, `number`, `title`, `sector`, `genealogy`, `cells` and `summary`, and `cellScenes` maps the symbol of a cell to the up to three templates that work it (each with `slug`, `title`, `sector`, `situation` and `story`). `GET /api/library/:slug` answers one full template under `template`, adding `operator`, `references`, `prohibition`, `situation`, `story`, `indications`, `request` and `sourceText`; `indications` is the same material as a list of labelled lines (sector, genealogy, prohibition, active cells, situation, central tension, course references, operator), and the cells carry their `bookSymbol` as well. A slug that does not match the library slug pattern answers `BAD_TEMPLATE` with status 400 before any file is touched, an unknown slug answers `UNKNOWN_TEMPLATE` with 404, and a missing index answers `NO_LIBRARY` with 500. What a template is and how it is built is specified in `DS009-start-template-library`.

`GET /api/templates?language=<code>` answers `templates` and `count` from the older proposed-universe catalog. The query is truncated to the first two characters and lowercased, and the default is `ro`. Each template carries `id`, `tags`, `title`, `law` and `openings`, where `openings` holds three to four concrete openings of the story that say who is in it, which problem they face and what is at stake; the values are localized with the fallback order requested language, then English, then Romanian. The catalog is assembled from `templates/universes.json` plus every `templates/parts/*.json` file, merged by template identifier with the first occurrence winning, cached by the modification stamps of those files. The route reflects the catalog files; it does not modify anything. The reader interface does not call this route any more: it starts a book from `GET /api/library`.

### Universes

`GET /api/universes` answers every universe on disk as a list sorted by `updatedAt` descending. Each entry is the public universe record: `id`, `title`, `summary`, `autoTitle`, `law`, `premise`, `elements`, `status`, `language`, `model`, `createdAt`, `updatedAt`, `chapterCount` and `lastChapterTitle`.

`POST /api/universes` creates a universe, and the body has two ways to describe it, which may also be combined. With `library` holding the slug of a start template, the universe is built from that template (`DS009-start-template-library`): its prohibition and its cells become the law and the ingredients, its situation and central problem become the premise, its summary is stored as `summary`, and the title is left empty so that the provisional name is the title of the template and the book is named after its first chapter. The other fields of the body are then ignored for the universe record, except `elements` — the reader may add ingredients on top of the template, and the server merges the cells of the template with them, drops a duplicate by its symbol or by the name of a proposed element, cuts the list to six and composes one law from all of it — plus `prompt`, `language` and `start`, which always apply. The body is mapped to the fields creation accepts by the exported `universeInputFromRequest`, so the mapping itself is verifiable without starting a server.

Without `library`, the universe is built from the body: `title`, `law`, `premise` or its older name `opening`, `summary`, `language`, `elements`, `prompt`, and the older `templateId`, which names a proposed universe of the catalog. A value sent by the client always wins over the template; `premise` wins over `opening`; and a template fills only what the body left empty, so a client can start a book from a proposal without repeating its text. Text sent in `prompt` with neither a template nor an ingredient is the free-text start: it becomes the law of the new world, which is the same composition the empty start template produces, and it is also the message of the first chapter turn. `elements` is the list of ingredients: symbols such as `"CA"`, objects carrying a `symbol`, or proposed elements as `{custom: true, name, family, operator, note}`. The server resolves them against the Periodic Table, at most six of them, and composes the stored law from the client law first and the ingredient lines after it; the resolved ingredients are written into `universe.json`, seeded into the `Ingredients` section of `canon.md` and named in the universe's own `AGENTS.md`.

A law shorter than 24 characters — including a law that is empty because neither a law nor an ingredient was sent — is rejected with `BAD_LAW`, an overlong title with `BAD_TITLE`, an unknown language with `BAD_LANGUAGE` and a title that cannot be turned into a free identifier with `ID_TAKEN`. The ingredient list adds its own failures: `BAD_ELEMENTS` when the value is not a list, when it holds more than six ingredients or when an entry is neither a symbol nor an object, `UNKNOWN_ELEMENT` for a symbol the table does not contain, `BAD_ELEMENT_NAME` for a proposed element without a usable name, and `BAD_ELEMENT_FAMILY` or `BAD_ELEMENT_OPERATOR` when a proposed element names a family or an operator the table does not have. A seventh ingredient is refused in the interface's own words, `Six ingredients are the most a universe law can hold. Remove one first.`, and the same sentence is the server's `BAD_ELEMENTS` message. A rejected creation leaves no folder behind.

The response is `201` with the new universe and a `job` field, which is `null` unless `start` is exactly `true`. When it is true, the first chapter is queued immediately and its request is taken in this order: `prompt`, which is the text the reader edited in the request field; then the `request` of the start template, when one was named; then a structured first-chapter request the server builds from the title, the law, the premise and the ingredients. Every text the server composes about the ingredients — the stored law, the `Ingredients` section of `canon.md`, the ingredient list of the universe's own `AGENTS.md` and the prompts — writes the `ingredient` sentence of each cell, never its two-letter address; the symbol is the address of a cell in the table and the key of the structured data in `universe.json`. The creation route therefore answers with the provisional name and with a job, and a client that wants the final name reads `GET /api/universes/:id` again after the first turn, which reports the adopted short name with `autoTitle: false` and the previous descriptive line as `summary`.

`GET /api/universes/:id` answers the reading view of one universe: `universe`, `chapters`, `turns`, `threads`, `canon`, `exports`, `activeJob` and `queuedJobs`. A chapter entry carries `number`, `slug`, `title`, `createdAt`, `words`, `bytes`, `turnNumber` and `offer`; the `rewritten` flag and the archived version count exist only on the single-chapter route, which is the route that also returns the Markdown. A turn entry is the durable turn summary without the answer and the agent log; `canon` carries only a bounded summary; `exports` lists edition files newest first with `name`, `format`, `bytes`, `createdAt` and `url`; `activeJob` is the running job of that universe or `null`, and `queuedJobs` lists the waiting jobs in turn order. A universe that does not exist answers `404` with `NOT_FOUND`.

`POST /api/universes/:id/settings` accepts `language` and changes the language of the book, answering the updated universe; when the body carries no language it simply answers the current record. The change is applied only while the book has no chapters: it rewrites `universe.json`, the universe's own `AGENTS.md` and the generated language line of `charter.md`, and only that line, so a human edit of the charter is preserved. A book that already has chapters answers `409` with the code `LANGUAGE_LOCKED`, because its accepted prose is written in the current language. `POST /api/universes/:id/open` and `POST /api/universes/:id/close` set the status and answer the updated universe. Closing does not stop queued work retroactively; it prevents later chapter turns from starting, which the queue enforces with `CLOSED`.

`GET /api/universes/:id/ideas` answers up to four concrete continuation ideas derived from the universe's own state, each with `label`, `prompt` and `source`. It performs no agent work, and the derivation rules are stated in `DS003-main-behavior`.

### Chapters and rewrites

`GET /api/universes/:id/chapters/:number` answers one chapter including its `markdown`, its normalized `offer`, the `turnNumber` of the producing turn, `rewritten` and the number of archived versions. A missing chapter answers `404`. Body chapter files are not served as static files; this route is the only way to read one.

`POST /api/universes/:id/chapters/:number/rewrite` starts a rewrite of that chapter. The body carries `instructions`, which must be at least 10 characters or the request is rejected with `BAD_INSTRUCTIONS`, and an optional `dropLater`. A closed universe answers `CLOSED`. An unknown chapter answers `NOT_FOUND`. When chapters after the target exist and `dropLater` is not `true`, the answer is `409` with the code `LATER_CHAPTERS` and a `laterChapters` array inside the error object, so the client can show the consequence and resend with `dropLater: true`. On acceptance the route only validates the request and enqueues the job; the archive of the current version and its offer, the removal of the later chapters and the rewind to the state before that chapter all happen when the job runs under the per-universe execution lock. The answer is `202` with the job and the `droppedChapters` array. A rewrite whose pre-chapter snapshot is missing fails with `NO_SNAPSHOT`, and a chapter that leaves more than one file for its number fails with `DUPLICATE_CHAPTER`.

### Turns, jobs and retry

`POST /api/universes/:id/turns` queues a turn and always answers `202` with the job. The body carries a non-empty `message`, a `kind` of `chapter` or `export`, and, for an export, a `format` of `docx`, `pdf` or `both`. An unknown kind answers `BAD_KIND`, an unknown format `BAD_FORMAT`, and an empty message `BAD_MESSAGE`. A chapter turn for a closed universe answers `CLOSED`. A request is never refused because the universe is busy: it is queued behind the turns already waiting for that universe.

The job snapshot carries `id`, `universeId`, `kind`, `format`, `status`, `createdAt`, `startedAt`, `finishedAt`, `turnNumber`, `chapterNumber` (the chapter the job writes, `null` for an export), the `request` text, `queuePosition`, `result` and `error`. `status` is `queued`, `running`, `done`, `error` or `interrupted`. `queuePosition` is the position inside that universe's own queue for a waiting job and `0` for anything else. `result` is filled on success with `chapterNumber`, `chapterTitle`, `exports`, `warnings`, `offer` and `durationMs`.

`GET /api/jobs/:jobId` answers the same snapshot. Jobs and their event buffers live only as long as the server process, so a job identifier from an earlier process answers `NOT_FOUND`; the durable state of that work is read from the universe detail, whose `turns` list is the record of what happened.

`POST /api/universes/:id/turns/:number/retry` restarts a turn whose durable status is `interrupted` or `error`, reusing the same turn number and the same request. Any other status answers `NOT_RETRYABLE`, a chapter turn for a closed universe answers `CLOSED`, and an unknown turn answers `NOT_FOUND`. An accepted retry answers `202` with the job.

`GET /api/universes/:id/turns/:number` answers the full turn record of that turn number, including the `answer` and the composed `agentLog`. The number is a turn number, not a chapter number; the mapping from a chapter to its producing turn is the `turnNumber` field of the chapter.

### Live events

`GET /api/universes/:id/events` answers a [text/event-stream](wiki.html#definition-event-stream). Without a `job` query parameter the stream covers the whole universe: it replays the buffered events of the running turn and then forwards the events of every turn of that universe, including turns queued later, and each payload carries the `jobId` it belongs to. With `?job=<jobId>` it covers that single job, validating that the job belongs to the universe and answering `404` when it does not; a job that has already finished closes the stream after its buffered events.

Payloads are JSON objects whose `type` is one of `job`, which carries a job snapshot, `phase`, which carries a short progress line, `delta`, which carries a fragment of the agent's live text, `tool`, which carries the tool name, a short detail and a success flag with `state` of `start` or `end`, `done`, which carries the final job snapshot, `error`, which carries a message and the job, and `refresh`, which is emitted on the universe stream after a turn finished so that a client can reload the universe. The server keeps a bounded buffer of 800 events per job, so a client that connects while a turn is running receives a recent history rather than the whole run.

The stream is the live path, not the only path. A client that cannot keep a stream open can still read `GET /api/jobs/:jobId` and `GET /api/universes/:id`, and the universe detail carries `activeJob` and `queuedJobs` precisely so that a page can be reloaded in the middle of a turn without losing the work in progress.

### Editions and files

`GET /api/files/:id/:name` serves one edition file from that universe's `exports/` folder as an attachment. The name must match a `.pdf` or `.docx` file name, otherwise the answer is `BAD_NAME`; the universe must exist, otherwise `NOT_FOUND`. There is no route that serves any other file from a universe folder or from the repository.

### Book import

`POST /api/imports` takes the file itself as the request body (`application/octet-stream`), with its name in the `X-Filename` header, or in a `filename` query parameter, and an optional `X-format` header of `pdf` or `docx`. The bytes are streamed into a folder of their own under the [assessment workspace](wiki.html#definition-assessment-workspace) while they are hashed and counted, so the size limit is enforced during the transfer instead of after it, and the answer is `202` with `{"import":Import}`. An upload without a name, or with one longer than 200 characters, is `400 IMPORT_FILENAME`; an empty upload is `400 IMPORT_EMPTY`; a declared format other than `pdf` or `docx` is `400 IMPORT_UNSUPPORTED`, while a file whose name says neither is stored with the format `null` and refused later at extraction; a body that passes `IMPORT_MAX_BYTES` — 64 MiB unless the environment says otherwise — is `413 IMPORT_TOO_LARGE`; and bytes that cannot be stored are `400 IMPORT_UNREADABLE`.

`GET /api/imports` answers `{"imports":[…],"maxBytes":…,"turnLimits":{…}}`: the imports newest first, the byte limit the deployment accepts, and the turn limits the [import skill](wiki.html#definition-scripta-import) publishes in `skills/scripta-import/schema/import.v1.json` as `maxChapters` and `maxWords`, which is `null` when that contract cannot be read. `GET /api/imports/:id` answers `{"import":Import,"progress":…}`, where `progress` is `null` until the import has both a universe and an extraction and otherwise carries `total`, `imported`, `complete` and `next` (`from`, `to` and the number of extraction chapters of the next window), which is how a client reports how much of the book is in the store and what is left. An identifier that is not of the form `<YYYYMMDDTHHMMSS>-<4 hex>` answers `400 BAD_ID`, and an import that does not exist answers `404 NOT_FOUND`.

`POST /api/imports/:id/extract` starts the [extraction](wiki.html#definition-extraction) in the background and answers `202 {"import":Import}`; extraction runs only for a record whose `state` is `received` or `error`, and the reader follows the record's `state` (`received`, `extracting`, `ready`, `error`) instead of holding a request open. Extraction is deterministic, starts no model and never guesses: it reads the file from the workspace, and a failure is recorded in the record itself as `state: "error"` with an `error` text that begins with `IMPORT_NO_TEXT` for a book with no text layer, `IMPORT_UNREADABLE` for a truncated, mislabelled or unparsable file, `IMPORT_UNSUPPORTED` for a format the extractors do not read or `IMPORT_TOO_LARGE` for a pathological page or entry count.

`POST /api/imports/:id/universe` creates the universe of a ready import, or continues an import that already has one, and queues the next [import turn](wiki.html#definition-import-turn). The body may carry `title` and `language`, both optional, and the answer is `202 {"universe":Universe,"turn":Job|null,"range":{"from","to"}|null,"progress":…}`, with `turn: null` when every extraction chapter has been imported or skipped, which is what a client shows as a finished import. An import whose extraction is not ready answers `409 NOT_EXTRACTED`, an upload whose file has disappeared from the workspace answers `410 IMPORT_MISSING`, and creating or continuing the import of a closed universe answers `409 CLOSED`.

An [import record](wiki.html#definition-import-record) is `book-import.v1` and carries `import_id`, `filename`, `format` (`pdf`, `docx` or `null`), `sha256`, `bytes`, `state`, `source`, `created_at`, `extracted_at`, `universe_id`, `detected`, `chapters`, `words`, `warnings` and `error`. Its `detected.title_source` says whether the title was read out of the file (`file`) or taken from the name the reader uploaded (`filename`), so a client never tells a reader that a file named itself when it did not. Where the upload, the extraction and the universe of an import live on disk is in `DS004-universe-storage`, and the extraction contract, the bounded window and the validator that accepts a turn are in `DS014-scripta-import-skill`.

An import turn is verified at the boundary like any other turn. A record that does not say the turn carried the window it was given answers `502 NO_IMPORT_RECORD`; a window whose record names no chapter of this universe, or names one that is not in the book, answers `502 NO_CHAPTER`; and a window the import skill's own validator refuses fails with `502` and that validator's code, so an import is machine-checkably the book that was uploaded rather than a paraphrase of it.

### Reviews, approvals and arc completions

`POST /api/universes/:id/assessments` starts one review of the frozen [accepted version](wiki.html#definition-accepted-version) of a book and answers `202 {"run":Run}`, where the run is the [assessment run](wiki.html#definition-assessment-run) that was recorded for it. The body carries `phase` (`continuity` or `metrics`, `metrics` by default), `profile`, `annotations`, `corpus`, `fromTurn`, `force`, `scope`, `chapters`, `aggregate`, `intention`, `weights` and `mode`. An unknown phase is `400 BAD_PHASE`; a metrics request that sends no profile receives the host's generic profile with a resolved scope rather than a refusal; a declared input the phase does not consume is `400 UNSUPPORTED_INPUT`; a corpus manifest without the text of the references it names is `400 MISSING_RESOURCE`; a supplied text whose bytes do not match the hash its reference declares is `400 HASH_MISMATCH`; and a packet is captured only from a stable version, so a book with a queued or running turn answers `409 UNSTABLE_VERSION` unless `fromTurn` names the immutable snapshot of a finished turn. Two requests with the same fingerprint are the same assessment: the second answers `202` with the run that already exists and that run carries `deduplicated: true`.

`mode` decides who produces the semantic observations, meaning the judgements about the text that only a model can make, and it is one of `supplied`, `generic` and `deterministic`. `supplied` means the caller brought an `annotations` document; `generic` means the host composes the prompt from the vocabulary `skills/scripta-metrics-report/schema/annotations.v1.json` publishes, runs the agent binary in the run's own workspace with the model from `SCRIPTAS_MODEL`, validates the answer against the frozen packet and keeps it beside the run, and this is the default, set by `ASSESSMENT_MODE=generic|deterministic`; `deterministic` means nobody does, so those results stay unavailable with their reason instead of being invented. Supplied annotations and a generated mode are mutually exclusive and answer `400 BAD_MODE`, as does an unknown mode; the continuity phase has no model stage, so it accepts `supplied` or `deterministic` and refuses the rest with the same code.

The model work belongs to the run rather than to the request. The route captures the packet, writes the run record and returns, and the [annotation stage](wiki.html#definition-annotation-stage) followed by the phase executes in the background inside that run's own directory, so a long model call never holds an HTTP request open and a client follows the run instead of waiting for it. A run's status is `queued`, `running`, `done`, `error`, `cancelled` or `interrupted`; a restart resumes a `queued` run and marks a `running` one `interrupted`, and an interrupted run is run again over the same frozen packet with `POST /api/universes/:id/assessments/:runId` and `{"action":"retry"}`.

`GET /api/universes/:id/assessments` answers `{"runs":[…],"arcEvents":[…],"workspace":"assessments"}` with the runs of that book newest first, each carrying `historical: true` when its version is no longer the accepted one, and `GET /api/universes/:id/assessments/:runId` answers `{"run":Run}`; an unknown run answers `404 NOT_FOUND`. `POST /api/universes/:id/assessments/:runId` with `{"action":"cancel"}` cancels a run and answers `200 {"run":Run}`, with `{"action":"retry"}` restarts it and answers `202 {"run":Run}`; a settled run answers `409 NOT_CANCELLABLE` to a cancel, and an unknown action answers `400 BAD_ACTION`.

`GET /api/universes/:id/assessments/:runId/report/:file` serves one published file of one run. The name is a plain file name and never a path, so it must match `[A-Za-z0-9][A-Za-z0-9._-]{0,120}` and must be listed in that run's own `outputs`; this is how a client reads the bundle `assessment.json`, the index `index.md` and the five views, and how the rest of the run directory stays unreachable. A name that is a path, or that carries `..`, answers `400 BAD_FILE`, and a name the run never published answers `404 NOT_FOUND`.

`POST /api/universes/:id/approvals` records the human decision on a design or craft proposal — the only bridge from a separate phase into a later writing request — and answers `201 {"approval":Approval}`; `GET /api/universes/:id/approvals` lists the approvals of that book. The body carries `proposal`, either the document itself or the path of one, `decision` (`approved` or `declined`), `reviewer`, `directions` and `version`. A decision other than those two, or a declined proposal that carries accepted directions, is `400 BAD_DECISION`; a proposal that is neither a document nor a path is `400 BAD_PROPOSAL`; more than eight directions, or one longer than 400 characters, is `400 BAD_DIRECTIONS`; a proposal written against another version is `409 STALE_REQUEST`; a second decision on the same proposal and version is `409 ALREADY_DECIDED`, because an approval that could be rewritten would not be an approval; and a book that is being written has no stable version to decide against, which is `409 UNSTABLE_VERSION`.

`POST /api/universes/:id/arc-events` declares an [arc completion](wiki.html#definition-arc-completion) against the accepted version and answers `202 {"event":Event,"run":Run}`, where `run` is the review the declaration started, since the event is the durable fact and the report it implies is scheduled by the same call. The body carries `arcId`, `note`, `phase`, `profile`, `aggregate` and `intention`; an identifier that is not lowercase letters, digits and hyphens is `400 BAD_ARC`, and a book that is being written answers `409 UNSTABLE_VERSION`. `GET /api/universes/:id/arc-events` lists the declared events, newest first.

### Reader feedback

[Reader feedback](wiki.html#definition-reader-feedback) is what the people who read a book say about it, and it is stored beside the reviews rather than inside the book, because it is about one version of the text and it must survive every rewrite and re-import of the store.

`POST /api/universes/:id/feedback/targets` freezes the text a reader was looking at and answers `201 {"target":Target}`. The body carries `scope` (`{"kind":"book"|"arc"|"chapter","chapters":[…]}`), `runId` for the report the reader was reading, `note`, and `findingIds`; the identifier of a target is derived from the universe, the accepted version and the scope, so the same version and scope open the same frozen copy and a second call answers `200` with the existing target and `deduplicated: true` instead of copying the prose twice. Freezing needs a stable accepted version, and a book with a turn in flight answers `409 STALE_TARGET`; a scope kind that is none of the three, a note longer than 200 characters, or more than 20 finding identifiers answers `400 INVALID_FEEDBACK`; a chapter that is not an accepted chapter answers `404 NOT_FOUND`; and a `runId` that names no report of that book answers `404 NOT_FOUND`. `GET /api/universes/:id/feedback/targets/:targetId` answers `{"target":Target}` with its frozen files listed, or `404 NOT_FOUND` when no target has that identifier.

`GET /api/universes/:id/feedback` answers the responses of that book newest first, the targets they answer and the counts the team reads, and each response carries `historical` when its target is no longer the accepted version and `withdrawn` when it was taken back. `GET /api/universes/:id/feedback/:feedbackId` answers `{"feedback":Response}` and `404 NOT_FOUND` for an unknown response. The counts separate provenance: a response whose `reader_kind` is `model` or `synthetic` is never added to the number of team readers or team responses, because the difference between what a reader said and what a model annotated is the whole point of keeping both.

`POST /api/universes/:id/feedback` submits one reader's response and answers `201 {"feedback":Response}`. The body carries `targetId`, `readerId`, the optional `feedbackId`, `answers`, `comments`, `conditions`, `revision_of` and the optional `readerKind` and `questionnaireVersion`; an answer is `null` for a question the reader skipped, or one of the numbers 1 to 5 the questionnaire declares, and a comment may quote a range of the frozen file with the words it covers. A response whose quotes do not resolve inside the target's frozen file, whose answers name options the questionnaire does not declare, or that breaks one of the limits is `400 INVALID_FEEDBACK` and nothing is written; an unknown target is `404 NOT_FOUND`; the same `feedback_id` with the same content answers `200` with the entry that exists and `deduplicated: true`, while different content under the same identifier answers `409 CONFLICT`. `POST /api/universes/:id/feedback/:feedbackId` with `{"action":"withdraw"}` withdraws a response and answers `200 {"feedback":Response}`: the entry stays readable, flagged `withdrawn: true`, and its answers are no longer shown, so a correction is a new submission that carries `revision_of`. Any other action answers `400 INVALID_FEEDBACK`.

`GET /api/universes/:id/readers` answers `{"readers":[…]}` oldest first, the roster of the book, and `POST /api/universes/:id/readers` creates an identity from `{"displayName":…}` and answers `201 {"reader":Reader}`. `GET /api/universes/:id/readers/:readerId` answers one identity. `POST` on one identity with `{"displayName":…}` renames that reader and answers `200 {"reader":Reader}` without losing attribution, and with `{"action":"delete"}` records a deletion request and answers `201 {"reader":Reader,"entry":Response}`, which marks the identity rather than erasing it and refuses a later response from it with `404 READER_NOT_FOUND`. An identifier no identity carries is `404 READER_NOT_FOUND`, and any other body is `400 INVALID_FEEDBACK`.

`GET /api/universes/:id/feedback/export` answers the reusable dataset of a book's feedback as an attachment named `<universe-id>-feedback-export.json` whose body is the `reader-feedback-export.v1` document, and `GET /api/universes/:id/feedback/summary` answers `{"summary":…}`, the `reader-feedback-summary.v1` document. Both read the store and never the accepted text: they carry paths, hashes and the reader's own words, they write nothing, the same store always exports the same bytes for the same document, and they count the three reader kinds separately so that a model annotation is never added to what a reader said. A book no reader has responded to yet answers `404 NO_FEEDBACK` for both, and a wrong method answers `405 METHOD_NOT_ALLOWED`. `targets`, `export` and `summary` are reserved segments of the feedback route and are matched before a response identifier, so a response cannot be read or withdrawn under one of those three names. The documents, their fields and their refusal rules are in `docs/contracts.md` §8.7, and `node scripts/export-feedback.mjs --universe <id> [--out <file>] [--summary]` builds the same documents from the command line.

`GET /api/universes/:id/feedback/comparison` compares one question between two accepted versions and answers `{"comparison":Comparison}`. The query names `question`, `from` and `to`. It restates the summary's rule rather than inventing one: a comparison is produced only when each named version holds at least three answered current responses on that question, and even then it reports the two distributions, the readers behind each and the model's annotations apart, with `ordering.stated` false and `difference` null, because two distributions of ordinal answers are not a number. When the counts do not carry it, the route answers `409 COMPARISON_NOT_SUPPORTED` with the summary's own reason verbatim and only the counts that would be needed — never a distribution, a mean or a difference; a version this book does not hold answers `409 COMPARISON_UNKNOWN_VERSION`, and a request that does not name one question and two different versions answers `400 BAD_COMPARISON`.

`POST /api/universes/:id/feedback/revisions` turns selected responses into a proposal that binds them to the accepted version they were given against, answering `201 {"proposal":Proposal}`; it refuses an item from another version or a withdrawn response with `409 STALE_REQUEST`, carries a correction in place of the response it replaces, and marks a model's or a fixture's response as such rather than as a reader's. `POST /api/universes/:id/feedback/revisions/rewrite` turns an **approved** proposal into a rewrite request through the approval path of §8.4: it answers `409 NOT_APPROVED` for a declined or missing decision, `409 STALE_REQUEST` when the proposal changed after it was decided, when the approval names another version, or when the accepted version moved on — checked at selection, at the request and again by the rewrite path itself. Neither route writes inside `universes/`.

The questionnaire is the server's and it is frozen into every target under the version `reader-questionnaire.v1`: the questions `interest`, `clarity`, `voice`, `emotion` and `continue`, each with its label, its two anchored ends and the options 1 to 5. A response is therefore read against exactly the questions its reader saw, a skipped answer stays visible as skipped and is never counted as a low score, and nothing is averaged. The limits are 4 000 characters for a comment, 1 200 for the comment on one answer, 20 entries for a list, 600 characters for a quoted range, and 200 characters for a note or for the place where a reader read. The records themselves — the target, the response and the reader identity, with their fields — and the layout of the folders that hold them are stated in `docs/contracts.md` §8.7 and `DS004-universe-storage`.

### Access boundary

The API has no authentication, no session and no authorization: every route is available to every client that can reach the listening address, including creating, closing, rewriting and exporting. The server also has no CORS configuration to relax or tighten, because the interface is served from the same origin. An operator who needs a private instance restricts reachability with `HOST` or a reverse proxy in front of the server. A reverse proxy that buffers responses also degrades the event stream into a polled view, which the reader interface tolerates.
