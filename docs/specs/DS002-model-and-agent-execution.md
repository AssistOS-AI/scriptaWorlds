## Introduction

Every chapter, every rewrite and every printed edition in scriptaWorlds is produced by one headless run of the [omp](wiki.html#definition-omp) coding agent (Oh My Pi) inside the universe folder. This specification states how the server becomes the single owner of the store, how the process is chosen, started, prompted, bounded, parsed and verified, and which failures the server repairs. The durable turn record it produces is specified in `DS004-universe-storage`, the queue that schedules it in `DS003-main-behavior`, and the exact prompt text convention in `docs/contracts.md`.

## Core Content

### Model and binary selection

The server runs one configured model for all turns. `src/config.mjs` reads `SCRIPTAS_MODEL` and falls back to `deepseek/deepseek-v4-flash`; the value is exposed as `model` by `GET /api/config` and `GET /api/health`, written into `universe.json` when a universe is created, and written into every turn record, so a book can be read later together with the model that wrote it. There is no per-universe model switch, no routing between model tiers and no automatic fallback to a cheaper model; changing the model is an operator decision made with the `SCRIPTAS_MODEL` environment variable.

The agent binary is resolved from `OMP_BIN` and falls back to the bare command name `omp`. `probeOmp()` in `src/config.mjs` runs `<binary> --version` with a 20 second deadline and captures stdout, stderr and the exit code without a shell. `requireOmp()` turns a failed probe into an error carrying the code `OMP_MISSING` whose message names the binary, the first lines of the probe output, and the remediation steps. `src/server.mjs` calls `requireOmp()` before it creates the listener and exits with status 1 when it fails, so a machine without a working agent never serves a universe that cannot be continued. `npm run check` performs the same probe and reports the same condition as a failed check.

An authenticated agent is a prerequisite of the product, not of the individual turn: the server trusts that the configured binary can reach its model, and a turn that ends unsuccessfully is recorded as a failed turn rather than diagnosed as a credentials problem.

### One server owns the store

The queue is durable, so the process that owns it must be unique. `src/server.mjs` starts work only when it is the process entry point: the module compares `process.argv[1]` with its own `import.meta.url` and calls `main()` only then, so importing the module — which `scripts/check.mjs` does to read `universeInputFromRequest` and `universeInputFromBody` — takes no lock, recovers nothing, resumes nothing and opens no listener. Before anything touches a universe folder, `main()` takes the store lock through `acquireStoreLock(universesDir)` in `src/lock.mjs`, which creates `universes/.server.lock` exclusively and writes the process identifier and start time into it. A second server started against the same store refuses to start, prints the identifier of the running process and exits with status 1, because two instances would each treat the other's running turns as interrupted and would resume the same queue twice. A lock left behind by a process that no longer exists is taken over, and the lock file is removed on `SIGINT` and `SIGTERM`.

The lock is the first thing the server takes and the queue is the first thing it repairs. `recoverAllUniverses()` scans every universe: a turn recorded as `running` becomes `interrupted` with the last accepted book restored and its partial chapter files removed, and a turn recorded as `queued` is put back into its universe's queue in turn-number order and continues with the same request — including the operation kind and, for a rewrite, its target chapter — which is what makes a restart lose no accepted work. The recovery step and the queue it restores are specified in `DS003-main-behavior` and `DS004-universe-storage`.

### Turn invocation

A turn starts exactly one child process. `runOmpAgent()` in `src/omp.mjs` spawns the binary with the argument vector `-p`, `--mode json`, `--no-session`, `--no-title`, `--auto-approve`, `--model <model>`, `--cwd <universe folder>` and `--max-time <seconds>`, where the seconds value is the configured timeout rounded up with a floor of 60. The process working directory is the universe folder, and `PI_NO_TITLE` is set in its environment. The prompt is written to the child's standard input and the stream is then closed; the prompt is never passed as a command-line argument, which keeps its text out of process listings and out of shell interpretation.

The three prompt families differ in what they ask for. A chapter turn asks for the next chapter of the book and an up-to-date canon. A rewrite turn asks for a better version of one named chapter, carries the previous text of that chapter as reference, states which later chapters no longer exist, and gives the reader's complaint priority over the agent's own judgement. An export turn asks for the editorial metadata of the printed edition and for one renderer run. A chapter turn and a rewrite turn both carry the ingredients of the universe, and the export prompt does not, because a printed edition composes no new world.

### Prompt contract

Every prompt is built by the server from the universe record rather than from free client text alone, and every prompt contains the same fixed elements. The agent is told that it is ALA, the narrative agent of the named universe, and it is given the fundamental law as an inviolable block with the instruction that every important event in the chapter is a consequence of that law, that the law is never broken, and that no second fundamental law is introduced without a cause already established in the canon. Civilizations, technologies and conflicts are effects of the law, not decoration.

The fiction language is stated explicitly with its code, together with the rule that all narrative text, chapter titles, dialogue and place names are written in that language, while the schema vocabulary of the plan keys, canon sections, JSON fields and file names stays English, and the agent's own final report to the system is written in English. The client request is quoted verbatim inside a delimited block so that reader text cannot be read as instructions to the server.

The mandatory steps repeat the file contract: read the narrative skill, read `charter.md`, `canon.md`, `threads.json` and the last two chapter files in that order, write the chapter as `chapters/NNNN-<slug>.md` with the title on the first line, keep the narrative text free of notes and meta commentary, respect the configured word target, update `canon.md`, `threads.json` and `atlas.json`, write `chapters/NNNN-offer.json` with a teaser and two or three concrete options, and never touch `universe.json`, `charter.md`, `turns/`, the `.agents` folder or `git`. The prompt ends by asking for a short final report: the chapter title and file, what changed in the canon, which promise was closed and which thread stays open.

While the universe still has no name of its own — or while its displayed title is still a whole sentence — the prompt adds a naming duty: after the chapter, the agent writes a [short name](wiki.html#definition-short-name) to `universe-title.txt` in the language of the fiction, and the prompt states that it must be a name and not a sentence, with no colon, no final period and no description of the law. The server reads that file after a successful turn, accepts the first non-empty line only when it has two to seven words and at most 60 characters, and then clears the provisional flag and removes the hand-off file, which exists only while the book has no name; that is why a universe created without a title is named by its first chapter rather than by its creator. A longer line is refused, the universe keeps its provisional title and the duty returns at the next chapter; when the previous title was itself a sentence, that sentence is kept as `summary` instead of being lost.

A revision may also carry the findings an author selected from an external review, each with the stable identifier the review published and the evidence it came from, together with the qualities the author wants preserved; the prompt states them, binds them to the version they were reported against and asks for one candidate version rather than a second pass. A writing request may also carry approved directions — short instructions a separate design or craft phase produced and a human accepted, with the approval record they came from. They reach the agent as input data of that request, stated under the fundamental law and the accepted canon, and they are recorded with the turn; the agent never reads the design or review skills and no handbook is copied into the prompt. The prompt also carries the ingredients of the universe. When the reader chose [cells](wiki.html#definition-cell) of the [Periodic Table of Speculative Ideas](wiki.html#definition-periodic-table), or proposed elements of their own, the chapter prompt and the rewrite prompt repeat them as one line per ingredient with the mechanism each one gives, under a heading that states the world is a [compound](wiki.html#definition-compound), that a chapter may develop one of those operations or the friction between two of them, and that no new fundamental operation is introduced without being recorded in `canon.md` first. The ingredient lines are the recipe itself, not a summary of it, and the same sentences are written into `canon.md` and into the universe's own `AGENTS.md`; the two-letter address of a cell appears only in the structured data and as the address of the cell in the table.

The word target comes from `CHAPTER_MIN_WORDS` and `CHAPTER_MAX_WORDS` and is stated in the prompt as a range. The word count is measured afterwards by the server on the written file, where headings are stripped and the remaining text is split on whitespace.

The export prompt is shorter and differently shaped: it states the book, its chapter count, the law, the language in which the edition labels must be written, and the required steps of reading the print skill, writing `exports/edition.json` with title, subtitle, author, year, dedication, preface and afterword, running the renderer from the universe folder with the requested format, and verifying the JSON line and the produced files.

### Reading the agent stream

The agent runs in JSON event mode, so the server reads its standard output line by line and reacts to three event families. Assistant text deltas are forwarded as live `delta` events and accumulated into the job's narration. Tool execution start and end events are forwarded as `tool` events with the tool name, a short detail string for the argument that identifies the work, and a success flag for the end event. The agent end event supplies the messages of the run, from which the server takes the last assistant text as the final answer, falling back to the accumulated narration when that is empty.

Every event is also written down as it happens: the job pipeline appends each one to the [turn journal](wiki.html#definition-turn-journal) `turns/NNNN.events.jsonl`, one JSON object per line with an `at` timestamp, from the queued line that carries the request through the phase lines, the tool calls, the narration fragments and the settle line of a finished or failed run. That file is the durable half of the same stream — the in-memory buffer exists for the live subscribers and disappears with the process — and it is what `GET /api/universes/:id/turns/:number/console` renders as the [console](wiki.html#definition-console) of the run. A retry appends to the same journal rather than replacing it, and a journal write that fails is logged as `[console]` and never fails the turn.

Non-JSON lines are diagnostics, not events: they are kept only in a bounded tail of the last 120 raw lines that accompanies a failed turn. Standard error is captured into the same record, bounded to 20 000 characters. Live narration is bounded to 120 000 characters, the composed agent log to 400 000 characters, and the journal to 400 000 characters of its own — past that, raw narration text stops being appended while the phase, tool and settle lines continue — so a runaway agent cannot grow a turn record or a console without limit.

### Time limits and failure handling

`CHAPTER_TIMEOUT_MS` and `EXPORT_TIMEOUT_MS` both default to 20 minutes and are applied as the child deadline in the server and as `--max-time` for the agent. When the deadline passes, the server sends `SIGTERM`, escalates to `SIGKILL` five seconds later, and treats the run as timed out.

A turn fails when the process was not started, when it ended with a nonzero code, when it timed out, or when the verification step below rejects its result. Every failure follows the same repair path: the server restores `canon.md`, `threads.json` and `atlas.json` from the snapshot taken before the turn, deletes the partial chapter files of that chapter number when the turn was a chapter or a rewrite, writes the turn record with status `error` and the failure message, and emits an `error` event on the event stream. The agent's narration tail is kept in the record so a reader can see what the agent had produced before it failed, and the journal of the run keeps everything the agent displayed up to the failure — including the line that records why it failed — so the console of a failed run is read in the sessions dialog like any other. The turn can then be restarted with `POST /api/universes/:id/turns/:number/retry`, which reuses the same turn number and the same request.

### Result verification

Every turn snapshots the accepted book first (`DS004-universe-storage`), and every failure restores it. After a successful process exit the server verifies the result instead of trusting the agent's report. For a chapter or rewrite turn it requires exactly one file named `chapters/NNNN-<slug>.md` for the chapter number of the turn: a missing file fails with `NO_CHAPTER`, and two files for the same number fail with `DUPLICATE_CHAPTER`. It then runs the skill's own validator as a child process and fails the turn with `INVALID_CHAPTER` when it does not report `ok: true`, so a valid plan, valid canon/threads/atlas schemas and a usable offer are required before the turn can become `done`. It measures the chapter length and records a warning when the chapter is below the configured minimum or above 1.35 times the configured maximum, without failing the turn, and it reads and normalizes `chapters/NNNN-offer.json`, recording a warning when the offer file is missing. For a rewrite it also compares the chapter directory before and after the run and warns when the agent created chapter files other than the one being rewritten. For an export turn it requires at least one `.pdf` or `.docx` file in `exports/` written after the turn started, and fails with `NO_EXPORT` otherwise.

On success the turn record is written with status `done`, the elapsed duration, the final answer, the composed agent log, the chapter file, title, word-derived warnings and the offer, or the produced export files. The universe record is then touched so its `updatedAt` ordering changes, and the job emits a `done` event carrying the same summary that `GET /api/jobs/:jobId` returns. What the reader re-reads afterwards is the journal rather than the record: the console route renders the journal while the run is live and after it settled, and it falls back to the composed `agentLog` only for a turn that ran before journals existed.
