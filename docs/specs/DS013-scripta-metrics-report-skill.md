## Introduction

`skills/scripta-metrics-report/` turns a frozen assessment packet plus optional annotations into one validated assessment bundle and the five readable reports rendered from that bundle. It measures what deterministic code can measure — lexical similarity, exact overlap, rule adherence, the continuity counts of a supplied result, the checked items of a verifiable dataset record and opt-in human timing — records an explicit unavailable status with a reason for everything it cannot measure, and never starts a model, downloads a corpus or touches the network. This specification states the input contracts, the metric and indicator identifiers with their output kinds, the status vocabulary, the rule registry and the five views, the command-line and publication contract, and the boundary that keeps literary judgement advisory. The continuity result it consumes is `DS012-scripta-continuity-review-skill`.

## Core Content

### Purpose and scope

A book project needs an honest answer to "how is this going, and what should I look at?" without that answer becoming a gate on publication or a number to optimise. This skill produces that answer as one bundle with provenance: every result names its method, its inputs, its scope, its coverage and its limits, and a result whose input does not exist is reported as unavailable with the missing prerequisite written out, never as a zero.

The skill is a separate-phase skill. It is chosen for a review on request, and it never runs inside a chapter turn, never blocks a chapter from being accepted and never rewrites a passage. Literary scores are advisory under the project's own decision: a report informs a revision choice made by a person.

The folder contains `SKILL.md` with the contract summary, `references/metric-catalog.md` with the definition, purpose, procedure, inputs, output, interpretation and limits of every metric, `references/literary-rubric.md` with the eight interpretive indicators, `references/report-contract.md` with the bundle and view contract, `references/calibration.md` with the proposed calibration protocol, `references/literary-cases.md` with the synthetic case library, `skill.json` as the catalog manifest, `dependencies.md` as the local dependency record, `scripts/build-report.mjs` as the report executable, `scripts/validate-cases.mjs` as the validator of the case library, `scripts/lib/` with the loading, measuring, registry, aggregation, assembly, rendering and case-validation modules, `fixtures/literary-cases/` with the index, the cases and the model-agreement record, `schema/annotations.v1.json` with the vocabulary an outside producer of annotations reads, `schema/rules.v1.json`, the published [general rule set](wiki.html#definition-applicable-rules) (`stg`) whose definitions the host copies into the registry it supplies — `registry_version` `stg-rules.v1`, the five rules an observed reading can check — so an evaluator reports outcomes and never defines the standard, and `tests/vocabulary.test.mjs` as the test that holds that published vocabulary and the validators together.

### Inputs

The command reads an `assessment-input.v2` packet, which is a directory containing `manifest.json` plus the referenced files at their relative paths. The manifest declares the universe, the content identity of the accepted version, the capture time, the book, the declared scope and one entry per file with its path, hash, byte count, role and artifact identifier. Every declared file must exist inside the packet, decode as UTF-8, match its declared byte count and hash, and stay inside the packet after symlinks are resolved, and the version identity is recomputed from the chapter, offer, canon, threads and atlas entries and compared with the declared one; a mismatch exits with status `2` and writes nothing. Refusals carry the shared codes of `docs/contracts.md` §8.3: `MISSING_CONTEXT`, `MISSING_MANIFEST`, `BAD_JSON`, `INVALID_MANIFEST`, `SCHEMA_VERSION`, `PATH_ESCAPE`, `DUPLICATE_PATH`, `DUPLICATE_ARTIFACT_ID`, `DUPLICATE_CHAPTER`, `MISSING_FILE`, `BYTE_MISMATCH`, `HASH_MISMATCH`, `VERSION_MISMATCH`, `ROLE_UNDECLARED`, `INVALID_ENCODING`, `SCOPE_INCOMPLETE` and `SCOPE_INCONSISTENT`. A declared `partial` packet names the chapters it omits, a `textual_only` packet carries prose alone and reports that no continuity context was available, and a `complete` packet that omits an interior chapter or a required state role is refused.

The evaluation profile declares `schema_version` `evaluation-profile.v1` (documents written earlier with `assessment-profile.v1` or `profile.v1` still load), a `profile_id`, a `scope` whose `kind` is `scene`, `chapter`, `arc` or `book`, the optional `context_chapters` that may explain a fact without being counted as candidate text, an optional `rubric` block and an `aggregation` block that is disabled by default. Chapter selections are resolved against the accepted inventory before any metric, adherence population, continuity input or evidence coverage is computed, so a duplicate, nonexistent or invalid chapter identifier is a contract violation; a scene or arc scope must name what it covers and never falls back to every chapter, and a book scope requires a complete packet.

An optional `annotations.v1` document supplies everything that cannot be computed: verified evidence items with byte ranges and quotes, scene and arc segments with declared or inferred boundaries, judged metric annotations, the eight literary indicators, the rule registry with its outcomes, an optional embedded `continuity-result.v1`, an optional `timing-study.v1` block, findings, declared departures and the passages worth preserving. A semantic annotation may declare the accepted `source_version` it was judged against, and a stale declaration is refused with `STALE_ANNOTATION`. An optional `corpus.v1` manifest names reference texts with their identifiers, paths, hashes, languages, provenance and permitted use, and it is read only from that explicit file: the corpus is never downloaded, and source identity is declared rather than inferred from bytes, so a reference is excluded as the candidate's own source version only when it declares the packet's `universe_id` and accepted `version`, a reference whose bytes equal a selected chapter while declaring nothing stays eligible and is labelled duplicate text, and an unknown identity is reported as unknown.

### The published annotation vocabulary

A report validates annotation documents against the lists its own code implements, and a producer outside the skill cannot read those lists from the code. `schema/annotations.v1.json` therefore publishes the vocabulary an `annotations.v1` document may use — the metric and indicator statuses, the eight indicator identifiers with their source categories, the indicator fields, the segment kinds and their provenance values, the EAP orderings, the finding kinds, severities, certainties, statuses and temporal keys, the departure statuses, the preserved-passage fields and the anchored rating scale — and the [annotation stage](wiki.html#definition-annotation-stage) of a review composes the prompt it gives a model from exactly those lists instead of inventing its own. The published file states the contract rather than the implementation: the validators under `scripts/lib/` remain the authority on what is accepted, and the published lists are what an outside producer reads.

`tests/vocabulary.test.mjs` holds the two sides together. It drives the real validators with every published value and with values that deliberately fall outside the published lists, and it asserts that a published value is accepted and an unpublished one is refused, so a value that is published but rejected, or accepted but unpublished, fails the test instead of reaching a report. The producer of annotations and the consumer of annotations therefore cannot drift apart without a failing check.

### Metrics, indicators and statuses

The registry has twelve metric identifiers: `CS` the coherence score, `NQS` the narrative quality score, `CCI` the continuity control indicator, `CAD` the character attribute drift, `EAP` the emotional arc profile, `CAR` the compliance adherence rate, `OI` the originality index, `SI` the similarity index, `NCS` the novelty and cliché score, `CR` the contamination rate, `TOP` the textual overlap percentage and `AEG` the author efficiency gain. Each carries a definition version, a purpose, a method, a direction, a unit, its limits and a discriminated value kind. `VAD` and `BCI` are reserved names without a sufficient definition and are never implemented as values.

A result is a scalar, a set of anchored components or an ordered trajectory, so a diagnostic profile is never flattened into an invented number. `CS` keeps four anchored dimensions (referential clarity, discourse connection, causal support, temporal intelligibility) and derives its experimental scalar only when all four are assessable under the versioned rubric profile; `OI` keeps three dimensions (perspective, dramatic development, expression) with the comparison scope they were judged against; `NCS` keeps novelty and cliché reliance separate with their own rationales and evidence and produces no combined scalar before calibration; `EAP` is an ordered trajectory of segments with focalization, valence, tension, evidence and uncertainty, its emotional-fit component stays separate, and the published series is ordered by the declared chronology while the received reading order is retained on every point: `ordering: "story"` must state a distinct `story_order` for every point, one point is one reading of one segment by one focalization, coverage is the fraction of the selected segments the trajectory actually assessed with its omissions named, a trajectory that assesses nothing inside the selection is unavailable, and a low-tension point is reported as a description of the arc rather than as a defect. A bare supplied number where components are required is classified as unsupported legacy data.

`CCI` and `CAD` come from a supplied continuity result and consume its counts once: the same continuity finding is never charged twice as an independent penalty, and repeated symptoms of one defect count as one candidate. The result is bound to the packet: its authoritative version is the packet's accepted version (`source_version`, with the legacy `version` only as a fallback, two different versions refused, a stale one refused as `STALE_ANNOTATION`), the population its counts describe is the reviewed chapters and must be exactly the selection and lie inside the packet, and its counts must partition the eligible comparisons — recomputed from the result's own comparison ledger when it carries one, and otherwise with the unattributed remainder carried as unresolved, so one observed success among a hundred eligible comparisons reports coverage and bounds instead of complete consistency. `CAD` draws its candidates from the same counted chapters, and a defect whose symptoms disagree about their status is contested rather than resolved by whichever symptom was read first. `CAR` is computed from a rule registry whose outcomes are stored per (rule, output) pair, with hard and soft classes, `stg`, `request` and `editorial` sources, an explicit aggregation policy, unresolved checks that reduce coverage, and bounds whenever an evaluated output is unresolved. `SI` is the Jaccard similarity of distinct five-token shingles per eligible pair, reported with the reference that produced its maximum; `TOP` is the union of exact matching runs of at least eight tokens over the eligible candidate positions, `100 * matched_positions / eligible_tokens`, with both candidate and reference spans retained. `CR` needs a training-dataset record whose referenced files are hashed locally, returns `not_assessable` for an inaccessible training set and a qualified limited finding for a partial subset. `AEG` is computed from comparable opt-in timing records over active human minutes, where a negative result is a real result and server elapsed time is kept separate. `NQS` is derived from its saved components under the declared aggregation profile with weights that sum to one; it stays unavailable without an emotional intention, with incompatible versions and for an uncalibrated production profile, and it never redistributes weights around missing inputs.

The eight literary indicators are `narrative_coherence`, `thematic_depth`, `character_complexity`, `originality`, `stylistic_quality`, `emotional_impact`, `interpretive_openness` and `cultural_value`. Each records a status, a category from its own source list or an unavailable reason, evidence, rationale, counterevidence, intended-effect fit and evaluator provenance. Cultural value normally remains unavailable for a new book, because it needs reception evidence that a manuscript does not have.

Every result carries one of five statuses: `computed` when deterministic code measured it, `judged` when it rests on an annotation, `not_assessable` when its prerequisite is missing, `not_applicable` when the question does not apply, and `error` when a method failed. A zero and an unavailable result render differently: zero is a measurement, while an unavailable result names what is missing.

### Evidence eligibility and coverage

A judgement must point at the text it was asked about. Every semantic result — a judged metric or dimension, an indicator, a trajectory record, a finding and a preserved passage — carries evidence, and each item is verified against the packet bytes, so a result whose evidence lies outside the reviewed selection is refused with `EVIDENCE_OUT_OF_SCOPE` and nothing is written: a judgement about prose the review was not asked to read is unfixable data rather than a partial answer. Context chapters explain a fact and never become the sole basis of a score, so a claim whose evidence lies entirely in declared context is demoted instead of judged: a metric or indicator becomes `not_assessable` with its reason, a confirmed finding becomes `unresolved` with the alternative explanation, and a preserved passage is marked as context-only. Scene scope is enforced on byte ranges as well as on chapter numbers, so a quotation that straddles a declared scene boundary lies outside it. Coverage describes what a result's own evidence touches — for a judged component it is the fraction of the selected chapters that evidence actually reaches — which is why one quotation cannot claim coverage of a whole book, and component completeness is reported apart from textual coverage so a complete set of dimensions is never mistaken for a complete reading.

### Rubric anchors and teaching cases

`schema/rubric-anchors.v1.json` publishes the meaning of the ratings the report expects: for each dimension of `CS`, `OI` and `NCS` a definition, the evidence question a rating answers, a description of every rating from 0 to 4 with concrete distinctions and the justified exceptions; for each of the eight indicators its definition, evidence questions, intended-effect qualifications and categories; and a declared default under which no quiet scene, static character, closed ending or local cultural setting is a defect by itself. `references/rubric-anchors.md` states the same material for a human reader, and the skill's own tests fail whenever the published file, the prose and the code disagree, so a model asked for a rating receives the scale the report validates.

```sh
node skills/scripta-metrics-report/scripts/select-cases.mjs --language <code> [--max-size <n>]
```

The selector returns a bounded, language-matched set of the synthetic library for a caller that wants to show an evaluator what the distinctions look like: the paired passages, the single changed feature, the expected evidence and the acceptable alternative readings. It keeps the declared regression holdout out of that selection, so the material used to teach a distinction and the material used to measure it are never the same cases.

### The aggregate policy

The composite score `NQS` is optional and off by default, and when it is enabled it runs under one of two declared policies. `research` is an experimental formula that an ordinary report may use with declared weights, an explicit advisory note and a stated emotional intention: its result is marked qualified, it is a weighted experiment rather than an endorsed or validated formula, and it claims nothing about readers. `production` claims calibration support, so it needs a completed study that binds the aggregate to the rubric and profile versions, the language and the scope, and it stays refused until verifiable study artifacts exist; the refusal message says that the aggregate is optional and off by default and names the research profile. `references/calibration.md` states the same policy from the research side, including what a study has to measure before such a claim could be made.

An aggregation profile that declares another version, an aggregate without a stated emotional intention, and an aggregate whose required components are missing all keep `NQS` unavailable with their reason, because weights are never redistributed around a missing input. The rest of the report stays usable in each of those cases; only the composite is withheld.

### The five views

The command renders five reports plus a navigation index from the single validated bundle: the STG compliance view with the active general rule set, its outcomes, unresolved and failed checks and the CAR context; the specification-adherence view that maps the reader request, the brief, the request's own requirements, the editorial preferences and the declared departures to what the observed text did; the metrics-and-indicators view that lists all twelve metrics and all eight indicators with their statuses, scopes, units and missing reasons, plus segments, boundaries, chronology and coverage; the score-justification view with the method, components, trajectory, arithmetic, bounds, coverage, qualification and limits of each result and its profile provenance; and the detected-issues view with the prioritized findings, their passages, alternatives, bounded repair suggestions and the passages worth retaining. The index is navigation only and is not a sixth evaluation. A renderer reads the bundle and never changes a score or re-judges the text, so re-rendering a stored bundle is byte-identical, and supplied text is escaped so it cannot break a table, a code span, a link, raw HTML or a heading.

A review leads with what it found before it shows its numbers. The index and the detected-issues view open with the same review summary, and the reader interface renders it first: what was assessed and what could not be, the intention the selection was read against, the strengths the record observed, the most consequential supported problems with the exact passages they rest on, the alternative reading that was preserved and the bounded revision options the record itself proposed. The bundle states a `reading_status` of `not_evaluated`, `insufficient_evidence`, `no_supported_issue_found` or `problems_recorded`, so an empty findings list is never rendered as a clean bill of literary health, and every metric keeps its diagnostics in the default view — the reason it is unavailable, its coverage and bounds, and its whole `detail` record, including an aggregate's declared weights and arithmetic and the qualification its calibration carries.

The bundle is also portable evidence for a session that did not run it. Alongside the accepted version and the hash of every packet file, `provenance.resources` names each input the run read with the sha256 and byte count of the exact bytes, `provenance.annotations.sha256` identifies the judgement document the run was given, `provenance.evaluation` hashes the skill's own published vocabulary, rubric anchors, study schema and case index and lists the evaluator labels that authored the judgements, and `provenance.evaluator_provenance` carries the evaluator's own declaration — prompt, rubric and case hashes, resource selection, model and settings, attempt identities and the provider usage it observed — verbatim under its own digest, with a model identity or a usage figure left absent rather than guessed when the evaluator recorded none.

### Command-line contract, publication and determinism

```sh
node skills/scripta-metrics-report/scripts/build-report.mjs \
  --input <packet-dir> --out <result-dir> --profile <profile.json> \
  [--annotations <annotations.json>] [--corpus <manifest.json>] \
  [--trigger <request|arc>] [--arc-id <id>]
```

Standard output carries exactly one envelope, `assessment-result.v1`, with the assessment identifier, the published directory, the produced paths and the error list. Exit status `0` means the run completed, including runs with unavailable metrics, because an unavailable measurement is a result rather than a failure; status `2` means invalid arguments, input, schema or a rejected path, and nothing is written; status `1` means an execution failure. A missing `--out` is a usage error.

`--trigger` names the event that caused the run and defaults to `request`. The value `arc` requires `--arc-id <id>` and is refused without it; `--arc-id` is refused with any other trigger; an unknown trigger value is a usage error. The host maps its own `requested` and `arc` vocabulary onto these two values and passes the flags on every run. The published bundle keeps `trigger` and adds `trigger_ref`, which is `{ "kind": "request" }` or `{ "kind": "arc", "arc_id": "<id>" }`, and `index.md` states the same event in one line, so a stored report and the page a reader opens both name what produced them without the host's run record.

Before a single byte is written, the destination is checked on real paths against the packet, the profile, the annotations and the corpus manifest: an output that equals, contains, nests under or symlink-aliases any of them is refused, including a not-yet-created child beneath a symlink. The complete bundle is then staged in a fresh sibling directory, its inventory is verified there, and it is published with one `rename`, so a reader sees either the previous complete result or the new complete result; an existing non-empty result directory is refused rather than overwritten file by file, and a failed execution leaves no apparently current `assessment.json` with missing views.

The run is deterministic: the same inputs produce byte-identical bundle and views, the assessment identifier and creation time derive from the frozen inputs rather than the wall clock, and execution duration is not persisted. Re-rendering a stored bundle therefore reproduces the same reports without a model call, which is what makes a reported number auditable.

### The synthetic literary case library

`fixtures/literary-cases/` holds 24 paired short texts — twelve Romanian and twelve English — written for this repository as synthetic teaching and regression material, plus `index.json` as their machine-checkable inventory and `model-agreement.json` as the record of what has been measured against them. Each pair keeps its text and changes exactly one literary feature between its two halves, and the twelve target distinctions cover flat against specific emotion, interchangeable against distinct voices, unsupported against motivated choices, exposition in dialogue, meaningful against empty repetition, the quiet scene, nonlinear chronology, the static character, unreliable narration, intentional ambiguity and two counterexamples in which adding conflict or adding explanation weakens the intended effect.

A case carries a stable identifier, its language, the writer's intention, the target distinction, the difference between the halves, expected evidence anchored at real UTF-8 byte offsets in both halves, acceptable alternative readings and a creation provenance that records the material as `original_synthetic` with no model call. The library is not a human benchmark: `index.json` declares `human_benchmark: false`, every case is labelled synthetic, and no case contains a human judgement. A declared subset of the cases is reserved for prompt-regression checks.

```sh
node skills/scripta-metrics-report/scripts/validate-cases.mjs [--fixtures <literary-cases-dir>]
```

The validator enforces the schema, the pairing, the language counts, the single-feature rule and the anchoring of expected evidence, prints one JSON envelope with the counts and exits `2` with one `{ file, message }` problem per defect. Agreement with a real evaluator is recorded separately in `model-agreement.json`, which states `status: "unperformed"` while no run has happened and requires a run's model identity, prompt and rubric versions, input hashes and visible disagreements before any figure may be reported; nothing in the record is invented, and a human study remains separate optional research.

### Dependencies and boundary

The skill requires Node.js 20 or later and uses built-in `node:` modules only (`node:fs`, `node:path`, `node:crypto`, `node:util`). It has no npm package, no vendored code, no external command and no network access at runtime, and its `dependencies.md` records that position. Its tests use the built-in `node --test` runner and cover packet validation with the shared rejection codes, evidence verification with multibyte text, the similarity and overlap arithmetic against independently computed values including overlapping, nested and repeated matches, the tokenizer's declared applicability, empty and short inputs, declared source identity with independent exact copies and duplicate-text distinction, scope resolution with earlier context, the rule registry and CAR coverage and bounds, the component, trajectory, timing, contamination and aggregation contracts, output separation and atomic publication, deterministic re-rendering and the rule that a packet is byte-identical after a run. Two further suites validate the synthetic literary case library — its schema, its pairing, the single-feature rule, the 12/12 language split, the reserved regression subset, the anchored evidence offsets and the unperformed agreement record — and the trigger flags with their refusals.

The boundary is that this skill measures and reports. It does not rewrite the book, does not change the canon, does not start a model on its own, and does not block a chapter from being accepted. The [annotation stage](wiki.html#definition-annotation-stage) that asks a model for observations belongs to the review host rather than to this command: the host builds the prompt from the vocabulary in `schema/annotations.v1.json`, runs the evaluator in the run workspace, validates and stores the accepted answer beside the run, and hands that document to the metrics phase by path, so a run of this command consumes annotations and never produces them and a stored bundle can be re-rendered without a model call. A human calibration study and any future threshold belong to a separate effort with held-out examples, and until such a study exists the composite remains disabled and every value stays advisory.
