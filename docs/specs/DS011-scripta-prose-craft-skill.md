## Introduction

`skills/scripta-prose-craft/` holds the craft decisions a scene needs: who perceives it, what each person wants from the exchange, how much of the scene is description, dialogue, narration or interior thought, and where the reader's attention should slow down or accelerate. It ships one executable, `scripts/validate-profile.mjs`, which checks the structure, the identifiers and the declared support of a prose profile — the small document in which those decisions are recorded — against a frozen accepted version, and writes nothing. This specification states the profile schema, the command-line contract, the drafting and inspection procedure the skill prescribes, and the boundary that keeps it out of the chapter-writing turn and treats a profile as a proposal rather than as evidence. The narrative skill that writes the chapter is `DS007-scripta-ala-skill`, the chapter files themselves are `DS004-universe-storage`, and the workflow that may one day read this profile while drafting is `DS003-main-behavior`.

## Core Content

### Purpose and scope

A chapter prompt can state what must happen; it cannot state how a scene should feel to read. This skill carries that second half of the work as a compact, checkable artifact: a profile that records the intended reader experience, the narrator and the focalization limits, a few character voice notes, the purposeful recurring devices and the revision priorities. It exists so that a review or a revision pass can name a defect in a passage — a repeated explanation, an exchange that could be spoken by anyone, a sentence that states the lesson of the action before it — and propose a bounded change, instead of asking for `more adjectives`.

The skill is deliberately a separate-phase skill. It is read and validated during design work and during a requested revision, never while ALA is writing a chapter candidate: the chapter turn reads the narrative skill, the canon and the reader request, and the prose profile is not part of that turn's input. Nothing in this specification adds a step to the chapter prompt.

The folder contains `SKILL.md` with the procedure and the schema, `references/narrative-blocks.md` with the structural, content, expression and rhythm vocabulary, `references/voice-and-revision.md` with the profile fields and the revision record, `skill.json` as the catalog manifest, `dependencies.md` as the local dependency record, `scripts/validate-profile.mjs` as the single executable with its rules in `scripts/lib/packet.mjs`, `scripts/lib/profile.mjs` and `scripts/lib/components.mjs`, and `tests/` with the `node --test` suites and their fixtures.

**A profile is a proposal and never evidence.** The intended effect, a voice note, a recurring device, an expressive component or a calibration claim recorded in the profile is a direction: it is not part of the book until an accepted chapter shows it, and a profile that contradicts the accepted version is stale rather than applicable. Only an explicit approval record and a later writing request carry directions into the book (`docs/contracts.md` §8.4). This is why the skill is never part of the chapter prompt: ALA writes from `scripta-ala`, the canon and the reader request, and it neither reads nor executes this skill during a turn; handing approved directions to a later writing turn belongs to the host.

### Prose profile

The profile lives in the `proposal/` directory of an external assessment workspace, as `prose-profile.json`, and uses the schema version `profile.v1`; it is never written into a universe folder, because a craft profile is a proposal rather than accepted narrative state (`docs/contracts.md` §8). Narrative descriptions are written in the language of the book; the keys stay English.

Required keys are `schema_version` with the value `profile.v1`, `profile_id`, `language`, `reader_experience` and `narrator`. `narrator` answers who speaks. Optional keys are `based_on_version`, `focalization`, `register`, `character_voices`, `recurring_devices`, `revision_priorities`, `expressive_components`, `calibration` and `intended_use`.

`based_on_version` is the accepted content identity of `docs/contracts.md` §8.2 — `sha256:` followed by sixty-four hex characters — and nothing else: a universe identifier or a folder name identifies the book, not the accepted version of its content, so it is refused as `INVALID_BASED_ON_VERSION` whether or not a packet was supplied. A profile written against version A of a book is refused as stale (`STALE_BASED_ON_VERSION`) when it is checked against version B of the same book, and the result envelope records the `version` and the covered `scope` it was checked against, so a validated proposal always names the accepted version behind it.

`focalization` is either a prose string or an object with optional `mode`, `limits` and `focal_character`; `focal_character` is an entity reference, so it must be declared in `character_voices`. Focalization answers whose perception and knowledge limit the passage, and a deliberate violation is recorded as a design choice rather than treated as an error. Each `character_voices` entry requires `entity_id` and `notes` and accepts an optional `speech_habit`; the notes describe decisions a writer can use, such as answering a question indirectly to protect status or noticing machinery before faces. Two speakers may share vocabulary while pursuing different social actions, so a voice note is not a verbal tic. Each `recurring_devices` entry requires `device` and `purpose`, which is what separates a motif that gains meaning from an empty repetition. `revision_priorities` is a free list of strings. Identifiers — `profile_id`, `entity_id`, `device` and `component_id` — are compared after trimming surrounding whitespace and applying Unicode NFC normalization, so two identifiers that differ only by that collide and are refused.

`expressive_components` carries the observations of the inspection as evidence-bearing records rather than as adjectives or a score. Each entry requires a unique `component_id`, a `component` from the fixed vocabulary of `references/narrative-blocks.md` (`focalization`, `description`, `dialogue`, `narration`, `interior_monologue`, `rhythm`), the `anchor` that names the passage the observation is anchored to, a `status` of `observed`, `uncertain`, `unresolved` or `not_applicable`, the `evaluator` who judged it, an optional `method` label, a `rationale`, and — unless the status is `not_applicable` — a non-empty `evidence` array whose entries pair a `source` with the `quote` it supports. A reading that is `uncertain` or `unresolved` must state its `uncertainty`, and `alternatives` preserves a competing reading that a reviewer has not settled. When `--context` supplies a packet, each quote is located verbatim in the packet file it names, so a fabricated quotation (`EVIDENCE_NOT_FOUND`) or a source the packet does not declare (`UNVERIFIED_EVIDENCE`) is refused instead of being counted as support; without a packet the quoted support is reported as unverified rather than accepted.

`calibration` records the readiness of the profile instead of assuming it: `status` is `uncalibrated`, `experimental` or `calibrated`, an absent object means uncalibrated, an experimental profile names the `protocol_version` it follows and implies no validation, and a calibrated profile names its protocol and cites the `evidence` behind it. `intended_use` is `draft`, `review` or `production`, and `production` is refused with `UNCALIBRATED_PROFILE` unless the profile actually names a calibration protocol and its evidence. The calibration study of `astra_tasks.md` C34 does not exist yet, so no production prose profile can be licensed today and a profile stays advisory.

### Validator contract

```sh
node skills/scripta-prose-craft/scripts/validate-profile.mjs \
  --input <profile.json> [--context <assessment-input.v2 packet directory|manifest.json>]
```

`--input` names the profile file and is required. `--context` optionally names an `assessment-input.v2` frozen assessment packet (`docs/contracts.md` §8.3), given either as the packet directory that contains `manifest.json` or as that manifest file itself. The packet is verified before the profile is compared with it: the schema version (a superseded `assessment-input.v1` manifest or an unknown version is refused as `SCHEMA_VERSION`), unique paths, artifact identifiers and chapter numbers, path containment through real paths rather than string comparison (`PATH_ESCAPE` for an absolute path, a `..` segment or a symlink that leaves the packet), a declared file that is missing (`MISSING_FILE`), a `role` outside the documented vocabulary (`ROLE_UNDECLARED`), bytes that are not valid UTF-8 (`INVALID_ENCODING`), a byte count or hash that does not match (`BYTE_MISMATCH`, `HASH_MISMATCH`), a `version` that differs from the identity recomputed per §8.2 (`VERSION_MISMATCH`), and a declared `scope.kind` that contradicts the packet (`SCOPE_INCOMPLETE`, `SCOPE_INCONSISTENT`). Only then is the profile's `based_on_version` compared with the packet's `version` — the accepted content identity, never `book.universe_id` — and every declared component quote located in the packet file it names. A profile written for one accepted version is therefore refused as stale against another version of the same book, and a fabricated quotation is refused rather than reviewed.

Standard output carries exactly one JSON object, `{ "schema_version": "profile.v1", "ok": boolean, "errors": [], "warnings": [], "context": null | { universe_id, version, scope } }`, and standard error carries human diagnostics. `context` is null when no packet was supplied; otherwise it records the accepted `version` that was checked and the `scope` the packet covered, with its `kind`, `chapters`, `omitted` and `note`, so a result states the coverage it stands on. Every error is structured as `<CODE>: <message>`; besides the packet codes above and the CLI codes `USAGE`, `MISSING_FILE`, `INVALID_INPUT`, `BAD_JSON`, `PATH_ERROR`, `IO_ERROR` and `INTERNAL`, the profile codes are `INVALID_PROFILE`, `DUPLICATE_ID`, `SCHEMA_VERSION`, `INVALID_BASED_ON_VERSION`, `STALE_BASED_ON_VERSION`, `UNVERIFIED_EVIDENCE`, `EVIDENCE_NOT_FOUND`, `CALIBRATION_INCOMPLETE` and `UNCALIBRATED_PROFILE`. Exit status `0` means structurally valid, `2` means an invalid argument, an unreadable or malformed input, a wrong type or a violated structural rule, and `1` means an unexpected execution failure. A malformed JSON document is answered with a structured error list and exit status `2`, never with a stack trace.

The validator writes nothing at all: it is read-only by construction, it takes no output path, and it refuses one (`--out`, `--output`, `--emit`, `--write`, `--publish`) with `OUTPUT_NOT_SUPPORTED` before it reads anything, so no output can equal, nest under or alias back into the profile or the packet. This skill publishes no bundle of its own: the accepted proposal is written into `proposal/prose-profile.json` by the crafting session that owns the external workspace (§8.1), and it is published by writing a fresh temporary file and renaming it into place, never by rewriting an existing accepted proposal in place, so a reader sees either the previous complete proposal or the new one. A run whose validation fails leaves the previous proposal untouched.

The structural rules are the ones a machine can settle honestly: unique `profile_id`, which must not collide with a declared entity identifier; unique `entity_id` across `character_voices`; unique `device` across `recurring_devices`; unique `component_id` across `expressive_components`; every referenced identifier declared; the component vocabulary, statuses and required evidence, evaluator and limitation; the calibration status and the production gate; and `language` one of the nineteen supported codes. The supported list is duplicated inside the script with a comment naming `src/config.mjs` as its source, because a portable skill may not import the server. The validator applies no aesthetic judgement: adjective counts, sentence lengths, block ratios and register preferences are never inputs. A deliberately formal, deliberately minimal, deliberately repetitive or deliberately unreliable profile is structurally valid, and the review of whether such a choice serves the book belongs to a reader, not to this script. A prose profile and the metrics evaluation configuration are different documents with different schema identifiers — `profile.v1` names this one, `assessment-profile.v1` names the metrics side — and a document that names another kind, or that carries the evaluation configuration's own `aggregation` or `scope` fields under `profile.v1`, is refused instead of being validated against the wrong rules.

### Drafting and revision

The drafting pass fixes four things in order: what the scene gives the reader and which accepted conditions constrain it; the focal attention and the immediate desire, together with what the character cannot know yet; the change the encounter produces in a practical condition, a relationship, an understanding or an emotional position; and the point at which the scene ends, which may be a complete local gesture, an unresolved silence or a changed understanding rather than a cliffhanger.

A bounded revision pass starts from a named passage and a reason tied to this book, and it states the effect to preserve. The inspection asks whether a repeated image acquires a different meaning; whether a suspect exchange would keep its purpose if another character spoke it, which points at the speaker's stake and defence rather than at vocabulary; whether a sentence states the lesson of the action immediately before it, which is kept only when the narrator's judgement is itself revealing; and whether the reader has any ordinary human detail — a physical inconvenience, a mistaken gesture, humour, work, a private wish — through which to care about an abstract conflict. These details must belong to the character and the setting, so they are questions rather than a checklist of compulsory humanizing moments.

The default is one revision pass, after which the changed evidence and the structural validity are rechecked. A change that improves cadence while contradicting established knowledge is not ready. Changed prose is submitted through the narrative workflow that owns chapter candidates; this skill never writes a chapter, never changes permanent rules and never manufactures earlier evidence. Revising to raise a literary score is not a reason to change a passage.

### Dependencies and boundary

The skill requires Node.js 20 or later and uses `node:fs/promises`, `node:path`, `node:crypto` and `node:util` only. It has no npm package, no vendored code, no external command and no network access at runtime, and its `dependencies.md` records that position. Its tests run with the built-in `node --test` runner and `node:assert/strict` against temporary directories, and they assert that the input file and the packet are byte-identical after a run.

The boundary is that this skill owns craft decisions and the structure of the profile that records them. It does not produce chapter prose into a book, does not validate channels of the chapter contract, and does not decide whether a book is any good. Literary judgement stays advisory and out of the mechanical pass, and the accepted profile can always be overruled by the author who chose the effect it describes. Three suites cover it, all sharing the fixtures in `tests/helpers/fixtures.mjs`: `tests/profile.test.mjs` checks the structural rules and the argument contract — a minimal profile, voices and recurring devices, a deliberately formal register, duplicate and colliding identifiers, a missing note, malformed input, a non-object entry, an unsupported language, an undeclared entity reference, an unsupported schema version, a non-object root, a missing or directory `--input`, and a document that is an evaluation configuration; `tests/context.test.mjs` checks the frozen packet contract — a matching packet, a profile written for version A refused as stale against version B of the same book, the `version` and `scope` a result records, a superseded `assessment-input.v1` manifest, an unknown or absent manifest, a universe identifier refused as `based_on_version`, tampered bytes, a detached manifest, a symlink escape, an undeclared role, bytes that are not valid UTF-8, the required structure of an expressive component, the calibration gate, a fabricated quote and an undeclared evidence source; and `tests/cli.test.mjs` checks that the command refuses every output argument wherever it points without writing or creating anything, and that the whole skill folder runs after being copied outside the repository from an unrelated working directory.
