## Introduction

The interface in `public/` is the product's only client today and the reference implementation of the API. It reads like a book rather than like a control panel: one chapter at a time, [ALA](wiki.html#definition-ala)'s voice and decisions in the [composer](wiki.html#definition-composer) below, and work in progress shown as a number in the same line of chapters. The same document also carries the work that surrounds the book — a new world of the reader's own, a book the team uploaded, a review of one frozen version with the reports it published, and what the team's readers said about it — and all of that stays a dialog over the book rather than a page beside it, so the reading flow is never displaced. It is a static set of ES modules served by the same Node.js process, with no build step, no framework and no CDN. This specification fixes the surfaces, the rules the interface must not break, and the state it keeps in the browser. The routes it consumes are in `DS005-http-api`, the data it renders in `DS004-universe-storage`, the library it starts from in `DS009-start-template-library`, and the live protocol in `DS003-main-behavior`.

## Core Content

### Composition and module tree

`public/index.html` is the document and the only place where stable element identifiers are declared: the header (`#topbar`, `#uni-title`, `#uni-summary`, `#lang`, `#btn-universes`, `#btn-more`), the chapter navigation (`#nav-prev`, `#chapnav`, `#nav-next`, `#nav-title`, `#nav-count`), the eight dialogs (`#universes`, `#requests`, `#rewrite`, `#review`, `#report`, `#feedback`, `#more` and `#tabledialog`, each with a `-body` or `-list` container and a `-close` or `-hide` control), the reading area (`#thread`, `#track`), the composer (`#ala`, `#ala-voice`, `#ala-offer`, `#composer-error`, `#input`, `#send`) and the new-chapter notice (`#notice`). It links nine stylesheets and loads one module. The start screen and the Import tab build their own elements in JavaScript rather than declaring them in the document, so a re-render of that surface replaces them; every other dialog is static markup shown and hidden by the `hidden` attribute.

The module tree is flat and small. `public/app.js` is the bootstrap: it binds the DOM, wires the events and starts the reader. Everything else lives under `public/ui/`: `state.js` (the DOM map, the single state object and the stored keys), `api.js` (the only network helper, `api()`), `errors.js` (the error rows shown in the reading area), `universe.js` (selecting a universe, refreshing its detail, the live job registry), `slides.js` (the slide models, the chapter numbers and the navigation), `overlays.js` (the shared open and close machinery of the dialogs), `actions.js` (sending a request, creating a universe, retrying a turn), `icons.js` (the inline-SVG pictograms and the icon button that carries the accessible label of its control), `importer.js` (the Import tab: uploading a book, following its extraction and carrying its windows), `review.js` (asking for a review of a frozen version and watching the run it started), `report.js` (one run and the files it published), `feedback.js` (the form half of the reader-feedback surface: freezing the text, the questionnaire and its answers, the comments and their quotations, the submission), `responses.js` (the data half: the responses of a book and the targets they answer, the roster of identities and the identity this browser remembered, a correction and a withdrawal), `comparison.js` (the A/B comparison surface of §8.7), `sse.js` (the event stream and its fallbacks) and the renderers `ui/render/header.js`, `ui/render/composer.js`, `ui/render/menu.js`, `ui/render/reader.js`, `ui/render/explore.js`, `ui/render/custom.js`, `ui/render/library.js`, `ui/render/ingredients.js`, `ui/render/tableinfo.js`, `ui/render/review.js`, `ui/render/report.js`, `ui/render/runs.js`, `ui/render/bundle.js`, `ui/render/feedback.js` (the pane the reader answers in) and `ui/render/responses.js` (the pane that shows what the team said). The theme is the nine light stylesheets under `public/styles/` — `base.css`, `reader.css`, `live.css`, `explore.css`, `composer.css`, `overlays.css`, `analysis.css`, `report.css` and `feedback.css` — linked in that order by the document; there is no aggregated sheet and no build step. A module is kept small enough to review in one pass, and `fileSizesCheck.sh` at the repository root reports a source file above 500 lines as review input; the reader-feedback surface is the one that needed that treatment, which is why it is five modules — a form half, a data half, the comparison surface and one renderer for each of its two panes — rather than one.

Client behaviour is data-driven and one-directional: one state object holds the configuration, the universe detail, the library and the table, the chapter cache, the live job snapshots, the runs of the book with what one run published, its feedback targets and responses, the reader identity of the book and the reading position; handlers change the state and call a render function, which rebuilds the affected surface from that state. There is no component framework, no templating language and no virtual DOM.

The interface loads as plain ES modules, and a module that fails to load must not leave a dead page: an inline script in `public/index.html` listens for a failed script, a startup error and a rejected dynamic import, and shows a `Reload` banner (`#stale-banner` with a `Reload` button) instead of an empty screen. The reader is also told when JavaScript is unavailable through the `noscript` line in the document.

### The start screen

With no current universe — or when the stored one no longer exists — the reading area holds one welcome slice, the [exploration](wiki.html#definition-exploration) surface. It opens with a single note, marked by an info glyph, that states the contract before anything else: a start template is a world that already has rules and a problem under way, opening one puts its text in the field below where anything can be changed before `Send`, and a reader who prefers to build their own world takes the operations they want from the table of ideas under `Ingredients`.

Under the invitation there are exactly four tabs, `Custom`, `Import`, `Library` and `Ingredients`, and no form fields of the surface itself beyond the field of the Custom tab: no title field of the start screen, no premise field and no language selector, because the language is chosen in the header. `Custom` is the tab that is open first, and the tab bar itself carries no request text.

The `Custom` tab is the fastest way in for a reader who arrives with an idea. It holds one large text area and one `Start` control, and nothing else: the text written there is the specification of a new universe — what exists, what is impossible, who is in it and what is already wrong — and pressing `Start` creates that universe through `POST /api/universes` with `start: true`, sending the text as `prompt` and the language chosen in the header, with no template and no ingredient. The text therefore becomes the [fundamental law](wiki.html#definition-fundamental-law) of the new universe, exactly as the [empty template](wiki.html#definition-empty-template) composes one, and the first chapter begins from the same text. A specification shorter than a sentence is refused in the panel before anything is sent, and the answer of the server is shown under the same field without clearing it, because that is where the reader is looking. The tab is a panel of its own rather than a helper for the composer: it creates directly, while `Library` and `Ingredients` only put text in the field below and `Import` hands a whole book to the server.

The `Import` tab is how a book the team did not write here enters the same store. It holds one file control that accepts a PDF or a DOCX, an optional title field of at most 120 characters, an optional language selector whose first option is `Language: as the file says`, an `Upload the book` control, a `Create the universe` control that appears only once the text has been read, and a note that states the two refusals before they happen: only a PDF or a DOCX of the size the server accepts, and a scanned PDF without a text layer is refused rather than guessed at. The panel never guesses what the server found: it draws the record itself, in the record's own words — the file name, its format and its size in kibibytes, its state (`Uploaded; its text has not been read yet.`, `Reading the text of the book…`, `The text is read.` or `The book could not be read.`), the detected title with `(from the uploaded name)` when the file did not name itself, the chapter and word counts, the warnings of the extraction, the error text when the extraction failed, and, once a universe exists, how many chapters are in it and which window the next import turn will carry.

Uploading is therefore not creating. `Upload the book` streams the file to the server, starts the extraction and follows the record until it is `ready` or `error`; the universe appears when the reader presses `Create the universe`, which sends the title and the language with the import and then carries the import window by window: it waits until the universe has no turn running or queued, reads the import record again, and queues the next window, so the interface drives a long book one bounded turn at a time and never queues two windows of the same import at once. When the record says the import is complete the control reads `Open the universe` and loads the book, and a turn that added no chapter stops the loop with a message that names the universe and tells the reader to read its last turn for the reason instead of queueing the same window again. The errors of those routes are shown under the panel, and a refusal in the server's words — an unusable file, or `409 CLOSED` for a closed universe — is shown as it arrived.

The `Library` tab shows the start templates of `GET /api/library` in two halves: the list on the left, the template that is open on the right, the two stacking on a narrow screen. A row of the list shows the title of the template, its sector when it has one, its genealogy, the symbols of its cells and the one-line summary of the problem it puts at the centre; the empty template, which has none of those extras, therefore shows only its title and its summary, and no row shows a night number. Clicking a row fetches that template through `GET /api/library/:slug`, marks the row and opens it in the right half without touching the request field: the detail pane shows the exact text the reader is about to send under `Request sent to ALA`, the indications of the world under `From the table of ideas`, and the text of the book behind a `From the book` control that stays collapsed. The `Use` control in that pane is what puts the template in charge of the request field, where the request is composed with the ingredients already chosen in the other tab; while a template is in use the control is disabled and reads `In use`. Nothing else happens: no universe is created, no folder is written and no turn is queued. If the template carries no request text, the composer shows a single line saying so instead of leaving an empty field unexplained.

The `Ingredients` tab builds a world from the [design instrument](wiki.html#definition-design-instrument) served by `GET /api/table`. It shows twelve families as rows and fifteen [operators](wiki.html#definition-operator) as columns, one button per [cell](wiki.html#definition-cell), a search box that dims the cells which do not match, a counter of the form `n of 6 chosen`, a `Clear` control, the list of the ingredients chosen so far with a remove control for each, and two collapsible sections: a legend of what the operators do, and `Propose another element`, which takes a name, an optional [family](wiki.html#definition-family), an optional operator and a note for an [ingredient](wiki.html#definition-ingredient) the table does not contain. At most six ingredients are accepted; a seventh is refused with the sentence `Six ingredients are the most a universe law can hold. Remove one first.` Every change — choosing, removing, clearing, proposing — recomposes the request field and keeps the chosen template, so the two composing tabs, `Library` and `Ingredients`, hold one starting point between them rather than replacing each other. Clicking a cell opens the `Details` dialog with what the book says about it; clicking an operator or a family name opens the same dialog for that operator or family.

The composer is the only input of the interface, and `Send` is the only way to start. The two composing tabs, `Library` and `Ingredients`, build one text together: one function composes the field from the request of the chosen template and the chosen operations, so a change on either tab rewrites it and a chosen template is never cancelled by a choice made on the other tab — a world can be a night of the book plus two operations the reader added to it. With no universe loaded, a submission creates one through `POST /api/universes` with `start: true`, sending the edited text as `prompt`, the language chosen in the header, and `library`, `elements` or both together, according to what the reader chose; the errors of that route are shown next to the field, without clearing the text. The `Custom` and `Import` tabs do not touch that field: `Custom` creates from its own text and `Import` hands a whole book to the server.

### The reading flow

The header is sticky and has two rows. The first row carries the short title of the universe with `universe.summary` underneath as one discreet line with an ellipsis, the language selector, the `Universes` button and the compact `⋯` button, which is disabled while no universe is loaded. The second row is the book navigation: `‹`, one number per slice, `›`, then the label of the current slice and the position counter `index/total`.

The numbers are the identity of the book. A chapter contributes one number, and a turn that is running or queued contributes a number of its own, carrying the number of the chapter it will write and marked as in progress, so a queue reads as `9 10 11` instead of repeating the next chapter. Clicking a number moves to that slice, and an interrupted or failed turn is one of them until it is retried or its chapter arrives.

A chapter slice holds the chapter and nothing else. Its head is `Chapter N · Title`, with a toolbar of icon controls on the same row: each control is an inline-SVG drawing that carries no text of its own and one accessible label, so the row of words that used to sit there is gone and the pictogram is announced through the label of its button. Below the head the chapter is rendered as a book page with a serif, justified face. The toolbar holds, in order, `What you asked for` (the `i` pictogram), which appears when a turn is recorded for that chapter and opens the `What you asked for` dialog with the request of the turn that produced it, and that dialog is the only place the request is shown: it is never rendered inside the slice; `Rewrite chapter N` (a pencil over the page), which opens the rewrite dialog; the console control, which appears for the same chapters as `i` and unfolds the agent log of that turn — the [console](wiki.html#definition-console) — inside the card, collapsed by default, reading `Show the scene log` or `Hide the scene log`; `Say what you think of this book, from chapter N` (a speech bubble), which opens the reader-feedback surface with that chapter as the default source of a quotation; `Review chapter N` (a checklist), which opens the review surface with that chapter chosen as the scope; and `Reports and reviews` (a report sheet), which opens the published reports of the book. A chapter that is still being fetched shows a loading line, and a chapter that cannot be fetched shows the failure in place of the prose instead of breaking the view.

Chapter Markdown is fetched per chapter through `GET /api/universes/:id/chapters/:number` and cached in the client under the identity of the text it belongs to — the chapter's byte count, its store timestamp, its word count and its title. The byte count alone is not an identity: a rewrite can replace the prose with a body of exactly the same length, and the reader would then keep reading the old chapter. A fetch that fails is not cached as the chapter either: the next refresh tries again, and the slide says what happened in the meantime. and it is rendered by `public/markdown.js`, which builds DOM nodes for headings, paragraphs, blockquotes, scene separators and bold or italic emphasis and never assigns rendered text with `innerHTML`. That subset is exactly what the narrative contract allows, so chapter text cannot introduce markup. The prose element carries the `lang` attribute of the universe, while the interface around it stays English.

### The composer and ALA's offers

One sticky card at the bottom of the page holds ALA's voice and the writing field. When the current chapter carries an [offer](wiki.html#definition-offer), the card shows its teaser, clamped to two lines with a control that shows the rest when it is longer, and up to three compact links whose labels come from the offer options; pressing a link fills the field with the prompt it carries and does not send it, so a reader can change the wording first. When the chapter has no offer, the card shows the first [continuation idea](wiki.html#definition-continuation-ideas) from `GET /api/universes/:id/ideas` instead, again as a suggestion that fills the field rather than sending it.

The field accepts any text and carries a drag handle in its top-right corner: pulling it up makes the field taller, the height the reader dragged is kept, and automatic growth — a lower bound of about seven lines, or forty percent of the viewport height when that is smaller — only ever adds to it rather than shrinking it. The native resize of the text area is switched off, as is the text area's own scrollbar until the content passes that height. The field sends on `Enter`, inserts a newline on `Shift+Enter`, and keeps its text when a submission fails. A chapter request is submitted as a normal turn, so it joins the same durable queue as every other request, and the interface shows it immediately as a numbered slice while it waits. Interface strings are English literals; the only text in another language is the book itself and, on the start screen, the texts of the library.

### The dialogs

Everything that is not the book is a [dialog](wiki.html#definition-dialog). There are exactly eight, and each is static markup in `public/index.html` shown by the `hidden` attribute:

| Dialog | Opened from | What it holds |
| --- | --- | --- |
| `Universes` (`#universes`) | the `Universes` button in the header | the universes on disk, most recently updated first, each row with its short title, its language and its chapter count; closed universes are grouped at the end under `Closed`. Selecting a row loads that universe and closes the dialog. |
| `What you asked for` (`#requests`) | the `What you asked for` icon in the toolbar of a chapter slice | the request of the turn that wrote that chapter, loaded through `GET /api/universes/:id/turns/:number`, with the chapter labelled above it. |
| `Rewrite chapter` (`#rewrite`) | the rewrite icon in the toolbar of a chapter slice | the instructions field, the submit control and the error line; a submission shorter than a sentence is refused in the dialog, and a `409 LATER_CHAPTERS` answer states which later chapters would be removed and turns the submit control into an explicit confirmation. |
| `Review` (`#review`) | the review icon in the toolbar of a chapter slice | the review form and the runs of the book; opening it from a chapter preselects that chapter as the scope. |
| `Reports` (`#report`) | the report icon in the toolbar of a chapter slice, or the run list of the review dialog | one run and everything it published, as a run head, a strip of its views and the view itself. |
| `Reader feedback` (`#feedback`) | the feedback icon in the toolbar of a chapter slice | the questionnaire and what the team already said, in two panes. |
| `Edition` (`#more`) | the `⋯` button in the header | `Download PDF` and `Download DOCX`, shown as `not yet` before an edition exists, `Generate edition`, or the state of an export turn while one is queued or running, then `New universe`, which closes the dialog and returns to the start screen. |
| `Details` (`#tabledialog`) | a cell, an operator or a family name in the ingredients grid | what the book says about the thing that was clicked, in three modes. |

The `Details` dialog is what makes the grid readable without bloat, and it is the only dialog of the start screen that can add anything. For a cell it loads `GET /api/table/cells/:symbol` and titles itself with the symbol, then shows, under `The idea`, the one-line essence of the cell and the sentence that states it as a world; under `What <family> changes`, the single substantial sentence of that family; the work the cell comes from, labelled `Seen in`; and, when the library already puts the cell to work, up to three start templates that use it under the heading `Used in N worlds`, each with its title, its sector, the situation it opens with and its central tension, and an `Open this template` control that switches to the `Library` tab with that template open in the detail pane. It carries an `Insert in my new world` control that is disabled and reads `In your world` once the cell is one of the chosen ingredients. The dialog never removes an ingredient: a chosen cell is removed through the `×` of its chip in the chosen list of the Ingredients tab, and clicking a cell of the grid opens this dialog instead of toggling the choice. For an operator it titles itself with the letter and the name of the operator, shows what the operator does and lists the first eight cells that work that way. For a family it titles itself with the long label the book gives the family and lists its cells with their names and mechanisms. Only the cell mode carries the insert control, and every mode reads from the table already loaded by the grid except the cell, whose page with the templates that use it is fetched on demand.

A dialog is a fixed overlay drawn above the page, with a dimmed backdrop, never taking layout space and never pushing the content, with its panel centred on both axes: `.popup` covers the viewport, and `.popup__panel` is `width: min(96vw, 1200px)` with `max-height: 92vh` and its own scroll. The `Edition` dialog is the deliberate exception because it holds short rows: its panel is `width: min(92vw, 320px)` with `max-height: 70vh`. The `Review`, `Reports` and `Reader feedback` dialogs use the same machinery with a panel of `width: min(96vw, 1000px)` — the `popup__panel--analysis` class — so a run head, a form or a view strip and the view itself sit in one scrolling panel instead of three nested overlays. Every dialog carries a visible `×` and closes on `Esc`, on a click on the backdrop and through the `×`; the backdrop is the `.popup` element itself, which covers the viewport, so a click outside the panel closes whichever dialog is open, and `Esc` closes that dialog before any other keyboard handling runs. Reading is never a dialog: a chapter always occupies the page.

### Reviews and reports

The review surface is where the team asks a question of one frozen version, and it is one dialog opened from a chapter or from the book. Its form is built from the accepted book rather than from anything a reader types. `What to run` chooses between `Metrics` — twelve measures, eight indicators and the five reports — and `Continuity`, the integrity and contradiction checks over the frozen state. `What to cover` chooses `This chapter`, which is the chapter whose toolbar opened the panel, `An arc — a run of chapters` with two selects that name a contiguous stretch of accepted chapters, or `The whole book`; only chapters the book already accepted can be named, so a review never reads a version a turn is still writing. `Who produces the observations` chooses `Generic — the host asks the configured evaluator`, the ordinary review that needs no profile and no annotations from the caller, or `Deterministic — no model call`, which measures only what can be measured and reports for everything else why it is unavailable. Under `Aggregate (optional)`, a checkbox combines the components into one score — off by default, published as an advisory research result and never as a calibrated one — with a field for the intention the emotional component is compared against. The panel states the contract in its own words: a review freezes the accepted version into a packet outside the book and reads that copy, it never changes a chapter, and it spends the evaluator only when the observations ask for it.

`Start the review` sends `POST /api/universes/:id/assessments` with the phase, the scope and the chosen mode, and the interface then follows the run rather than the request: while a run is `queued` or `running` the panel re-reads it every two seconds and stops the moment it settles, so an open panel watches one run and never the whole store. A row of the run list names the phase, its state, the version it was frozen against and whether a later accepted version has made it `historical`, and a recorded failure is shown as the host recorded it; a live row offers `Cancel` and a settled failure offers `Retry`. The list follows the book instead of a timer: when the event stream reports that a turn finished or a review settled, the client re-reads the runs, and the feedback surface re-reads the responses at the same moment.

The report surface shows one run and everything it published, and it opens by default on the newest run of the book that published something readable. The strip lists the published files in reading order — the bundle first, then `index.md`, then the five views and the continuity result of a continuity run — and the body renders the chosen file as Markdown, because that is what most of them are. A link from one view of a run to another is rewritten to open its sibling inside the panel, so a reader follows the report without leaving it, while a link to anything else is left to the browser; a control beside the strip points at the published file itself, which is the URL `GET /api/universes/:id/assessments/:runId/report/:file` returns. The panel renders the files and never interprets them, so a report is read exactly as the run published it, and there is nothing to recompute on the client.

### Reader feedback

The [reader-feedback surface](wiki.html#definition-reader-feedback) is where the people who read the book say what they think of it, and nothing in it is averaged. It has two panes behind one strip: `Answer the questionnaire`, which becomes `Correct a response` while a reader corrects one of their own, and `What readers said (N)`, where the number is the responses of the book.

The same dialog holds the comparison surface. A `Compare two versions` control mounts `comparison.js` into the comparison container, and the surface lists the book's frozen readings and a reader, opens a session over two of them on a question both declare, and shows the two texts in the place order the session stored — each side fetched from the frozen copy of its own target through `GET /api/universes/:id/feedback/targets/:targetId/text/:name`, so an earlier version is shown as the prose its reader was given rather than as the chapter of today. The reader chooses one of the four answers (the text on the left, the text on the right, neither was better, could not tell them apart), writes why, may rate each side, records where and how they read and which of the two they had seen before, and the answer is stored under the session; the surface then states what was recorded and the counts of that pair by place and by role, apart, with the note that these are recorded observations and not a measurement of a difference.

The pane a reader answers in begins by freezing the text: nothing is asked about the book before the version on screen is frozen, because a reading is evidence about one text rather than about a book that keeps changing. The panel says what the frozen copy is — the scope, when it was frozen, the version and the questionnaire version — and tells the reader when the book has been rewritten since, in which case this copy is an earlier version and a response to it is listed as `historical`, and a control then freezes the version currently on screen instead. The questions arrive inside the frozen copy: each one carries its label, its two anchored ends and the numbers 1 to 5, and every question can be skipped, because a skipped answer is recorded as skipped and never read as a low one. Below the questions the form carries what one session adds rather than what the frozen copy holds: the two optional declarations of what the reader had already seen before answering (the model's scores or findings, other readers' comments — recorded exactly as declared, never assumed on the reader's behalf), and the two optional reactions the target's questionnaire declares, `usefulness` about the report the reader had open and `defect_present` about the text itself, each with its own optional sentence. An untouched reaction stays undeclared. What other readers said stays behind the second pane and is shown after the reader has answered, and the store claims nothing about who read before answering beyond those declarations. A comment may stand on its own, and it may quote a passage of the frozen copy: the reader selects that passage in the copy shown in the dialog, where the offsets are exact, or in the book behind it, where the selection is remembered as it is made and resolved in the frozen copy when its words can still be anchored, and the panel says why quoting is not offered when they cannot. The reader is named under `Who is answering`, with a name of at most 80 characters and the identity the server issued for this book, remembered in `localStorage` under `scriptaWorlds.reader.<universeId>`, so the same person is not asked twice and a rename keeps every response already given attributed to them; the place a reader read is asked for and recorded, and never required. It sends the version it read — read from the listing when the pane opens — and the sha256 of every chapter of that text this browser displayed, so a rewrite that landed between reading and answering is answered with `STALE_TARGET` instead of attaching the answers to prose the reader never saw: nothing is frozen then, every answer and comment stays in the form, and the button that says so reads the accepted text again and freezes that. The pane also keeps the frozen copy it quotes from: a chapter whose browser copy is missing, or whose text is not the one the target recorded, is read back from the target's own frozen bytes, so a reader on another machine quotes the words of that copy rather than today's chapter. A `Compare two versions` control in that pane opens the two-text reading session of §8.7, whose own surface is mounted into the form by `public/ui/comparison.js`.

The form respects the limits of the route before the server has to refuse anything: a quotation is at most 600 characters, a comment 4 000, the comment on one answer 1 200, the where field 200, and one response carries at most 20 comments. A response that answers no question and writes no comment is refused in the panel, because skipping every question is allowed but saying nothing is not; a refusal from the server is shown with the advice of its error code, and the text the reader wrote is kept. The pane states the point of the whole surface: these are one reader's answers to one frozen text, they are never combined into a score, and nothing else about the reader is recorded.

The pane that shows what the team said lists the responses newest first, each as its own reader gave it: the name it is attributed to, its kind, when it was given, the frozen copy it answers with that copy's version, the answers with the skipped ones saying that they were skipped, the comments with the passages they quote, and the state of the response. The counts separate provenance in words: it says how many team readers have answered and how many times, then how many model annotations and fixtures the book holds and that they are not readers, so a model's annotation or a fixture is listed and never added to what a reader said. A response whose target is no longer the accepted version is marked `historical`, a withdrawn one stays visible with its reader, its moment and its state while its answers are no longer shown, and a withdrawn or corrected response is read from the frozen copy that response quotes. A reader takes a response back in two presses — the first asks, the second withdraws it — and corrects one of their own by sending a new response that names the one it replaces, which is the `revision_of` field of the submission. The routes behind all of this are in `DS005-http-api`, the records and their fields in `docs/contracts.md` §8.7, and the folders that hold them in `DS004-universe-storage`.

### Live activity and failure surfaces

A turn that is running or queued is a numbered slice in the reading flow, not a separate view. A queued turn shows that it is waiting and how many turns are ahead of it in that universe; a running turn shows what ALA is doing, the number and title of the chapter it is writing, a phase line with the agent's live text tail and the recent tool calls with their outcome; a turn that failed or was interrupted shows its message and a `Retry` control that restarts it through `POST /api/universes/:id/turns/:number/retry`.

The live data comes from one event stream per universe. The client opens `GET /api/universes/:id/events` while the universe is open — including while this client watches nothing at all, because a second client may start a turn at any moment and a page that has been away has to reconcile what happened without it. It applies `job` payload applies `job` payloads to its live state, appends `delta` text and `tool` entries, and reloads the universe on `done` or `error`. If the aggregate stream cannot be established or keeps failing, the client falls back to one stream per job plus periodic reads of `GET /api/jobs/:jobId`, so a proxy that buffers server-sent events turns live text into slower progress rather than into a broken page. A reload during a turn reconstructs the in-flight work from `activeJob` and `queuedJobs` in the universe detail.

Two discreet notifications keep the reader oriented. When a new chapter appeared while the reader was not at the end of the book, a `New chapter ready — read it` button appears above the composer and moves to that chapter when pressed, instead of pulling the reader away from the page they were reading. Reading errors are deduplicated, appended to the reading area and dismissible, so a repeated failure does not fill the page.

### Persisted state and navigation

A pending turn is shown as a live slice numbered by the chapter it will write, taken from the accepted book rather than from the turn number: a queue of three chapter turns behind a book of eight accepted chapters reads 9, 10 and 11 even when rewrites and editions have pushed the turn numbers far ahead, and an edition never takes a chapter number. A chapter that a running turn is writing or replacing disappears from the accepted list while that turn works, so the reader sees the live slice instead of a chapter that does not exist on disk, and the chapter returns by itself when the turn commits or when a failure restores it.

The composer states what sending does. When the reader is looking at a chapter that is not the last one, a hint says that the request opens the next chapter rather than changing the one on screen, and points at `Rewrite` for that. The request carries the chapter the reader was looking at as `sourceChapter`, so a chapter can be traced back to the reader's place in the book even when the turn it caused wrote a later chapter.

The current universe is stored under `scriptaWorlds.currentUniverse`, the reading position of each universe under `scriptaWorlds.currentChapter.<universeId>`, the language chosen in the header under `scriptaWorlds.language`, and the identity a person answers a book's questionnaire with under `scriptaWorlds.reader.<universeId>`, all in `localStorage` inside guarded blocks so a browser that refuses storage does not break the interface. The same state is mirrored into the URL as a universe and chapter query pair through the history API, so a link can be shared and reloading the page returns to the same chapter; a universe in the query takes precedence over the stored one at boot.

The language selector in the header is filled from the language list of `GET /api/config` and applies to the next universe the reader creates; the choice is remembered and reused until it is changed. Keyboard and pointer navigation follow the same model: the arrow keys move between slices unless focus is in a text field or a modifier key is held, `Esc` closes any open dialog, and a horizontal swipe over the reading area moves between slices with a threshold large enough that vertical scrolling is unaffected.

### Boundaries

The interface has no administration surface and no account system: everything it can do is available to every client that can reach the server, because the API has no authentication. The reader identity a questionnaire is answered under is a display name plus an identifier the server issued for one book, not an account: it grants nothing and unlocks nothing. The interface cannot change the language of an existing book, which is an API call (`POST /api/universes/:id/settings`), and it deliberately exposes no closing or reopening control, no dashboards, no statistics and no technical badges such as durations, model names or turn numbers in the reading flow. The print edition is reached only from the `Edition` dialog and is never a reading page and never a chapter number. Reviews and feedback are the same kind of surface: the interface reads a frozen copy and writes records outside the book, and no control of it edits a chapter, a canon file or an accepted version — a revision still begins with `Rewrite` or with a chapter request, and an approved direction still reaches the book only through a writing request.
