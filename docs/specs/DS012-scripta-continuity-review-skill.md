## Introduction

`skills/scripta-continuity-review/` reviews accepted chapters for continuity defects without changing a single byte of the book. It reads a frozen assessment packet, checks what a machine can settle — file hashes and encodings, chapter numbering, references to chapters that do not exist, malformed state containers, impossible chapter references in a blueprint — and, when a reviewer supplies semantic annotations, re-verifies every quoted piece of evidence against the packet, derives a comparison ledger from those judgements and publishes the findings with the indices that follow from them. This specification states the packet contract, the two review layers, the ledger and its derived counts, the command-line and publication contract, and the boundary that makes the reviewer read-only. The state model it reasons about is `DS004-universe-storage`, the narrative rules that define what may change are `DS007-scripta-ala-skill`, the packet contract it implements is `docs/contracts.md` §8, and the metrics that consume its findings are `DS013-scripta-metrics-report-skill`.

## Core Content

### Purpose and scope

A book accumulates facts: a valve was opened all the way, a child cannot yet read, a character learned a name in chapter six. A continuation that contradicts one of those facts is a defect a reader notices immediately, and a reviewer that invents a correction is worse than the defect. This skill exists so that continuity is reviewed against frozen evidence — the exact bytes of the accepted version — and so that a finding always names the passage it came from.

It is a separate-phase skill, chosen for validation and design work and never during chapter writing. It does not run inside a chapter turn, it does not add a step to the chapter prompt, and it never edits the story. The folder contains `SKILL.md` with the procedure, the refusal codes and the envelope, `references/state-and-evidence.md` with the evidence classes and the evidence reference contract, `references/review-protocol.md` with the review order, the questions for a suspected contradiction and the CCI/CAD handoff, `skill.json` as the catalog manifest, `dependencies.md` as the local dependency record, `scripts/review-continuity.mjs` as the single executable, and `scripts/lib/` with the packet loader, the scope module, the span-aware JSON parser, the evidence builder, the deterministic checks, the claim validator, the annotations envelope, the ledger, the path-separation module and the publication module.

### Assessment packet

The reviewer reads an `assessment-input.v2` packet: a directory that contains `manifest.json` plus every referenced file at its relative path. The manifest declares `schema_version`, the `universe_id`, the content identity of the accepted version, the capture time, a `book` object with the title, the language and `last_accepted_chapter`, the declared `scope`, and a `files` array whose entries carry a relative forward-slash `path`, a 64-hex `sha256`, a byte count, a `role` and an `artifact_id`. The roles are `chapter`, `offer`, `canon`, `threads`, `atlas`, `meta`, `design`, `profile`, `annotations`, `corpus`, `rules` and `timing`.

Every declared file must exist inside the packet, be valid UTF-8, match its declared byte count and hash, and still resolve inside the packet directory after symlinks are resolved. The version identity is recomputed from the chapter, offer, canon, threads and atlas entries exactly as `docs/contracts.md` §8.2 defines it and compared with the declared one, so a packet whose content and identity disagree is refused rather than reviewed. The declared scope is honoured rather than assumed: `complete` requires every chapter up to the last accepted one, the three state containers and no declared omission; `partial` names the chapters it contains and must declare every absent chapter in `scope.omitted`; `textual_only` carries prose alone, in which case the result says that no continuity context was available. A `partial` or `textual_only` packet with no chapter prose is refused as `SCOPE_INCOMPLETE`, because a review of nothing cannot be a review.

Every refusal carries one of the shared codes of §8.3, formatted as `CODE: message`, and each case has exactly one name. A missing or unreadable input is `MISSING_CONTEXT` and a missing manifest is `MISSING_MANIFEST`; a manifest that is not JSON is `BAD_JSON`; a malformed field, an unknown scope kind, a duplicate chapter number in `scope.chapters` or an omission outside the accepted book is `INVALID_MANIFEST`; an unknown or superseded `schema_version` is `SCHEMA_VERSION`; an absolute path, a `..` segment, or a path that resolves outside the packet after symlinks is `PATH_ESCAPE`; a repeated path is `DUPLICATE_PATH` and a repeated artifact identifier is `DUPLICATE_ARTIFACT_ID`; two chapter entries for one chapter are `DUPLICATE_CHAPTER`; a declared file that is absent is `MISSING_FILE`; bytes that are not valid UTF-8 are `INVALID_ENCODING`; a byte count that does not match is `BYTE_MISMATCH` and a hash that does not match is `HASH_MISMATCH`; a version identity that does not match the recomputed one is `VERSION_MISMATCH`; an undeclared role is `ROLE_UNDECLARED`; an interior chapter or a required role missing from a `complete` scope, or a scope naming a chapter the packet does not contain, is `SCOPE_INCOMPLETE`; and a scope that declares a chapter it contains as omitted, omits a chapter without declaring it, declares omissions under `complete`, or carries state containers under `textual_only` is `SCOPE_INCONSISTENT`. Any refusal prints the envelope with `ok: false` and exits with status `2`, writing nothing to the result directory. A packet is therefore two things at once — the input and the proof that the input did not change.

### Deterministic checks

The first layer needs no model and no annotations. Chapter references are read field by field rather than by a `_chapter` pattern, because the fields do not mean the same thing. `asked_chapter`, `created_chapter`, `closed_chapter` and `occurrence_chapter` assert accepted material, so each must name a chapter the packet contains: a chapter the packet declares omitted is a declared omission rather than a defect, a chapter beyond `last_accepted_chapter` is a `future_reference`, and a chapter of the accepted book that the packet neither carries nor declares is a `missing_reference`. An atlas node's `chapters` list records accepted occurrences and is checked the same way.

`due_chapter` is a deadline of an open thread and a blueprint destination is a plan, so neither may be read as an accepted event: `due_chapter`, `target_chapter`, `destination_chapter` and a blueprint's `chapter_memberships` and `planned_chapters` may point forward inside their own contract, and only the shape of their value is checked. A JSON document under the `design` or `profile` role is read as a blueprint in exactly that mode — its chapter numbers must be chapter numbers, and a chapter it plans is never reported as an unaccepted occurrence — while a non-JSON file under those roles holds no chapter reference to check and is not parsed.

The layer also reports duplicate active chapter numbers, which is the file-level symptom of a chapter that has two live versions and covers a chapter-numbered file the manifest classified under another role; a chapter file numbered beyond `last_accepted_chapter`; a malformed state container, meaning invalid JSON, a non-object root or a collection key that is not an array; and a malformed JSON blueprint. Each finding carries `certainty: "deterministic"` and `status: "confirmed"`, and each cites evidence inside the offending file. Evidence is built from the byte spans of the parsed document, so a key that repeats across objects cites the object that actually offends rather than the first occurrence of its key, and every window ends on a UTF-8 code-point boundary, so a window that would split a Romanian diacritic is shortened instead. A malformed container is answered with a structured finding rather than a stack trace, so the review always returns a readable result.

### Annotation-driven semantic review

Semantic continuity — a character who knows something they cannot know, a fact that changes without a cause, a rule that quietly stops applying — cannot be settled by a regular expression, so the second layer consumes annotations from `annotations.v1`. Each entry of `findings` is an evidence-bearing record, not an opinion with a label: it must name a stable `id`, the `source_version` it was written against, the `scope` it reviewed, its `evaluator` and `method`, a `kind` from `contradiction` | `unsupported_change` | `editorial`, a `category` from the declared set, a `severity`, a `certainty`, a `status` from `confirmed` | `unresolved` | `dismissed`, a `rationale` and the `evidence` it rests on. Enumerations, category membership, container types and numeric finiteness are validated before any value is used, an eligible claim must state or explicitly null an `alternative_explanation`, an `unresolved` reading must state its `limitations`, a `character_attribute` claim must name its `attribute` and its `catalyst`, and the claim's `chapters` must be chapters of the accepted book.

Every evidence item is an `id`, `file`, `sha256`, zero-based half-open UTF-8 byte range and the exact `quote`, and it is verified with the same strict semantics the metrics skill uses: the hash of the packet file is recomputed, both offsets must sit on UTF-8 code-point boundaries, the range must decode as UTF-8, and the decoded slice must equal the declared quote byte for byte. A fabricated or stale quotation — one that is not found at the declared bytes — refuses the whole file as `INVALID_EVIDENCE`, as do duplicate ids (`DUPLICATE_ID`) and malformed records (`INVALID_ANNOTATIONS`). Missing or invalid evidence can therefore never enter the confirmed counts, because the file that carries it is not accepted at all.

A resolved verdict — a confirmed contradiction, or a change the annotator declares supported — must additionally carry `baseline` and `later` evidence with the `temporal_scope` between them. Without that pairing the claim is preserved exactly as declared, reported as `unresolved`, marked `downgraded_to_unresolved` and disclosed in the warnings, so an unpaired confidence can inflate neither the contradicted nor the consistent count. An explicitly `unresolved` reading with its limitation is a legitimate answer, a dismissed reading with both passages is a supported comparison rather than a defect, and valid alternative explanations survive into the finding. The reviewer never invents a semantic finding, and when no annotations are supplied the semantic layer is absent and the coverage note says so.

### The comparison ledger and its derived indices

The reviewed comparisons are stored separately from the defect list, because a defect list is a list of symptoms and a ledger is a list of decisions. Each comparison names its subject, its kind, its baseline and later evidence, its temporal scope and one outcome — `supported`, `contradicted` or `unresolved` — and a character-change comparison additionally names the `attribute` and the `catalyst`. Symptoms linked by a shared `comparison` id form one comparison, so repeated symptoms of one defect add one penalty, while a shared subject alone never merges two distinct defects, which would hide one of them.

`counts` (`eligible_comparisons`, `consistent`, `contradicted`, `unresolved`) is derived from those records and never trusted from outside: a `counts` object supplied by the annotations, or by an embedded previous result, must reconcile with the ledger or the file is refused as `INVALID_ANNOTATIONS`, which is how the reproduced `eligible=1, consistent=8` payload is rejected. An embedded `continuity-result.v1` is accepted only when it is `ok`, describes this same accepted version and a scope the packet contains, and reconciles; a failed, historical or foreign result is refused rather than merged.

Coverage is the share of eligible comparisons that reached an outcome and stays inside `[0, 1]` (`null` when there is no eligible comparison to cover), with `coverage_bounds` carrying the interval the unresolved comparisons leave open. `derived.cci` and `derived.cad` report `computed` with a single value, `unresolved` with bounds, or `not_applicable` with no denominator: no eligible comparison means there was nothing to measure, no eligible character change means CAD does not apply, and an index that cannot be settled is withheld rather than reported as perfect. Judged provenance — the claim and evidence identifiers of each comparison, the evaluator, the method, the rationale and the confidence — survives the arithmetic, and the result is bound to the packet version and the scope it covered, so a reading of two chapters is never presented as a whole-book result.

### Result envelope and counts

The command writes exactly one JSON line to standard output and the same envelope to `continuity-result.json` inside the result directory, pretty-printed for reading. The envelope carries `schema_version: "continuity-result.v1"`, `ok`, the packet `version`, a `scope` object with the universe identifier, the declared kind, the chapters, the omissions, the reviewed chapters, the coverage note, the coverage and its bounds, `reviewed_claims`, the `comparisons`, the `counts`, the `derived` indices, the `findings`, and the `errors`, `warnings` and `outputs` arrays. Findings are advisory: a major semantic finding may undermine a central causal chain and a local one may affect a limited passage, but a suspected semantic error does not become a publication veto, while a deterministic integrity error is what stops a dependent measurement.

### Command-line contract and publication

```sh
node skills/scripta-continuity-review/scripts/review-continuity.mjs \
  --input <packet-dir> --out <result-dir> [--annotations <annotations.json>]
```

`--input` names the packet and `--out` names the result directory of one run; both are required, and an optional `--annotations` file supplies the semantic judgements. Exit status `0` means the review completed, whatever it found, because findings and unsettled comparisons are result data rather than failure; status `2` means invalid arguments, an invalid packet, invalid annotations or an unusable result directory, in which case nothing is written; status `1` means an execution or publication failure, which the envelope reports while naming no bundle.

The result directory need not exist: missing parents are created beside the destination. Before any write, the destination is proven separate from every input on real paths, so an equal path, a nested path, a symlink alias and a not-yet-existing child beneath a symlink are refused as `OUTPUT_INSIDE_INPUT` or `OUTPUT_CONTAINS_INPUT`, and a supplied annotations file is protected the same way. A destination that exists as a file is `OUTPUT_NOT_DIRECTORY`; a non-empty directory is `OUTPUT_NOT_EMPTY`, because every run owns its directory and an accepted result is never overwritten file by file. The whole bundle is then assembled in a fresh sibling staging directory, its inventory and bytes verified there, the destination rechecked now that the staging directory exists, and published with a single `rename`. A failure is `IO_ERROR` or `INCOMPLETE_BUNDLE`, removes the staging directory, leaves `--out` untouched and publishes nothing; a run interrupted between staging and publication leaves only a staging directory that the next run for that destination removes before it starts.

### Dependencies and boundary

The skill requires Node.js 20 or later and uses `node:fs/promises`, `node:path`, `node:crypto` and `node:util` only. It has no npm package, no vendored code and no network access at runtime, and its `dependencies.md` records that position. Its tests run with the built-in `node --test` runner and `node:assert/strict`, they build real `assessment-input.v2` packets in temporary directories, and they assert observable behaviour rather than internals: every refusal code of §8.3, the declared-partial distinction, the input/output separation and the atomic publication, field-specific chapter references including a deadline that points forward and an occurrence that does not, the span-accurate citation of a repeated key, evidence windows on Romanian byte boundaries, the annotation rules, and the ledger arithmetic with its reconciliation and its withheld indices.

The boundary is that this skill observes and reports. It does not edit chapters, canon, threads, atlas, permanent rules or design plans, and it does not decide that a revision must happen. A host validates the result and publishes the report, and ALA or a human chooses and writes any revision through the normal transaction that owns the book.
