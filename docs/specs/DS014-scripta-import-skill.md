## Introduction

`skills/scripta-import/` turns an uploaded foreign book into a [universe](wiki.html#definition-universe) that behaves exactly like a written one: the same `chapters/NNNN-slug.md` files with `# Title` on the first line, the same `canon.md`, `threads.json` and `atlas.json`, and the same ability to be continued, rewritten, reviewed, measured and printed afterwards. It reads an extraction the host produced from the uploaded file and, in bounded turns, copies the book's own prose into chapter files and derives the state files from that prose. It writes no narrative content of its own: importing is archiving, and an import that invents prose is worthless. This specification states the extraction contract, the turn discipline and its continuation pointer, the segmentation and faithfulness rules, the state derivation, the language decision, the refusals, and the command-line contract of the validator the host runs after every turn.

The skill is the seventh [project skill](wiki.html#definition-project-skill) and the third that writes a book rather than reviewing one. It is read during an import turn of a universe the host created for an uploaded file, alongside `scripta-ala`, which owns everything written afterwards: a chapter that is later continued or rewritten is written by ALA, and the import neither writes a [turn record](wiki.html#definition-turn-record) nor an [offer](wiki.html#definition-offer).

## Core Content

### Purpose and scope

A reader can upload a book instead of writing one. The product then owes the same experience: a book that can be read chapter by chapter, continued by ALA, analysed by the separate-phase skills, rewritten chapter by chapter and exported as an edition. That is only possible when the imported book is structurally identical to a written one — same file names, same state files, same vocabulary — and factually faithful to what was uploaded.

The skill therefore has two halves. The instructions in `SKILL.md` and the six reference documents tell an agent how to import one bounded range of an extraction and how far it may go in cleaning, segmenting and describing it. The executable `scripts/validate-import.mjs` is what the host runs after every import turn: it checks, with no model and no budget, that the chapters are on disk in one contiguous run, that their words are plausible against the extraction they came from, that the state files parse and cite real chapters, and that the universe carries the machine-readable mark of an import.

The folder contains `SKILL.md` with the workflow and the invariants, `references/extraction-format.md` with the fixed input contract of the extraction, `references/turn-discipline.md` with the bound of one turn, the record schema and the continuation rules, `references/segmentation.md` with the boundary methods, `references/prose-cleaning.md` with what cleaning may and may not do to the book's words, `references/state-files.md` with the derivation of canon, threads and atlas from imported prose, `references/validator-contract.md` with the command, the envelope, the codes and the limits of the check, `schema/import.v1.json` with the published vocabulary a host plans the next window from, `schema/import-progress.v1.example.json` as the canonical record of a three-chapter book after its first two chapters, `skill.json` as the catalog manifest, `dependencies.md` as the local dependency record, `scripts/validate-import.mjs` as the single executable with its rules in `scripts/lib/`, and `tests/` with the `node --test` suites and their fixtures.

### The extraction contract

The host extracts the uploaded file and writes two files inside the universe: `.agents/import/extracted.json`, the structured extraction, and `.agents/import/book.md`, the same prose as plain text for reading. Both belong to the host; the import only reads them. The extraction declares `schema_version` `book-import.v1`, an `import_id` of the form `<YYYYMMDDTHHMMSS>-<4 hex>`, the `source` (`filename`, `format`, `sha256`, `bytes`, `pages`), the `detected` metadata (`title`, `author`, `language`, any of which except the title may be null), the `chapters` as `{ number, title, words, text }` entries with the prose of each chapter and paragraphs separated by blank lines, and the `warnings` that say what the host could not do.

Chapters are already segmented by the host when the source has detectable boundaries. When it does not, the host delivers one large chapter and a warning that says so, and the import segments the book itself. A chapter entry may carry an empty `text` when the source has a heading with no body; an extraction whose chapters all carry no prose is the scan without a text layer and is refused as `NO_EXTRACTION` rather than invented. The host refuses an upload it cannot read at all before writing anything, with `IMPORT_UNSUPPORTED`, `IMPORT_TOO_LARGE`, `IMPORT_NO_TEXT` or `IMPORT_UNREADABLE`.

### The import turn and its continuation

An import is a sequence of turns, because a book is far larger than one turn. One turn covers at most three extraction chapters and at most 6,000 words of their prose, whichever comes first, and always at least one chapter, so that a single chapter longer than the word bound is still importable. Whichever bound is reached first ends the window; a recorded turn above the bound is reported as the warning `TURN_OVERSIZE` and does not refuse the import. The window is always a prefix of the extraction from the continuation pointer, in order, with no chapter repeated and none skipped forward.

The continuation pointer is `next_source_chapter` of `drafts/import-progress.json`, the import record this skill writes: it names the extraction chapter the next turn starts at, or `null` when every extraction chapter has been imported or skipped, and `complete` is `true` exactly when it is `null`. It is authoritative — chapter files on disk do not carry the extraction chapter they came from — so a host plans the next window as the same function the skill does, `planTurnWindow(chapters, fromSourceChapter, { maxChapters, maxWords })` in `scripts/lib/turns.mjs`, whose limits are published in `schema/import.v1.json` under `turn_limits`. One turn writes the chapter files of its window, updates `canon.md`, `threads.json` and `atlas.json`, and rewrites the record with the new chapter entries, the new turn entry and the advanced pointer; it writes nothing else.

### Faithfulness, segmentation and language

Chapter prose is the book's own words, in the book's order, in the book's language. Cleaning may remove what a page has and add nothing: running heads, page numbers and scanner artefacts go, words broken across lines are rejoined, hard-wrapped lines are unwrapped, whitespace is normalized, scene breaks become `---`, and the accepted Markdown subset of the renderers is respected. Cleaning may not rewrite, translate, shorten, extend, reorder or annotate, may not invent a title, and may not drop a readable chapter in silence. A chapter the extraction declares with words is always imported; only a chapter the extraction declares with no words — a part title, a blank page — may be passed over, and each one is named in the record's `skipped` list with its reason. A chapter file carries `# Title` on the first line and the book's prose after it; where the source gives no title, the short label of the book's language is used (`Capitolul N` in Romanian, `Chapter N` otherwise), and the file name slug is transliterated to `[a-z0-9-]`.

A book that arrives as one chapter is cut by the import itself, and the record declares which method was used in `segmentation`. Headings win (`Chapter 7`, `Capitolul 5`, `PART TWO`, a standalone number or a short line of capitals); where there are none, scene breaks are grouped into chapters; where neither exists, the text is cut at paragraph boundaries around 2,000 words, never before 1,500 and never after 2,500, so an imported chapter reads like a written one. `host`, `scene` and `word_count` are the three declared values, and `word_count` is an approximation the skill declares rather than a discovery of the book's structure. The cut segments of one source chapter occupy consecutive chapter numbers and carry `segment` `1..k` in the record, so the division can be reconstructed. Outside the documented `min`–`max` band a non-final segment is reported as `SEGMENT_OFF_BAND`.

The prose is written in the book's language whatever `universe.json` says, and the state files are written in the book's language too, because they describe the book; schema vocabulary — file names, section names, JSON keys, thread kinds and statuses, atlas axes and states — stays English. A detected language that differs from `universe.json` is recorded in the record's `language` block (`book`, `state`, `universe`, `match`) and reported as the warning `LANGUAGE_MISMATCH`; the import never translates the book and never edits `universe.json`, which belongs to the server.

### State files derived from imported prose

`canon.md` carries the six fixed sections a written universe uses — `## Fundamental laws`, `## World`, `## Recurring characters`, `## Timeline`, `## Stable facts`, `## Mysteries with a fixed cause` — with every line traceable to the chapter that shows it, written as `(ch. N)`. The law is copied from `universe.json`; the rest is what the imported chapters establish and nothing else. `threads.json` records what the book leaves open at the frontier — promises unpaid, mysteries unsolved, decisions untaken, questions unanswered — in the four documented lists and the documented vocabulary, with `created_chapter`, `closed_chapter` and `due_chapter` naming chapters that exist; a later turn moves what the new chapters pay into `closed` with a one-sentence resolution. `atlas.json` names the published axes and the nodes the imported chapters work, in English identifiers and labels, with the state the prose shows and the chapters that show it, never an empty chapter list.

The rule that governs all three is that the import invents nothing: no fact the imported chapters do not show, no character who has not appeared, no date the book does not give, no axis, no node for an idea the book never touches, no thread for a promise nobody made, and no mystery with a cause the book has not given. An honest gap is part of the book; an invented fact is a defect a reader will find.

### Refusals

An unusable extraction is refused, and nothing is written. The extraction is absent, empty or wordless (`NO_EXTRACTION`); it does not parse, or its schema version is unknown, or a chapter entry carries no `text` field (`UNPARSEABLE_JSON`, `INVALID_IMPORT`); its prose arrives as replacement characters or in a script that cannot be copied faithfully; or the record already covers every extraction chapter, in which case there is nothing to do. A record that names another upload — a different `import_id` or `source.sha256` — is refused with `INVALID_IMPORT` rather than merged or repaired by guessing.

### Validator contract

```sh
node skills/scripta-import/scripts/validate-import.mjs \
  --universe <universe-folder> --import <extracted.json> [--chapters <from>-<to>]
```

`--universe` is required. `--import` defaults to `<universe>/.agents/import/extracted.json`. `--chapters` names a range of *extraction* chapters — the window one import turn covered, which is the range the record's own turn journal carries — so an import of a twelve-chapter book is accepted turn by turn while its later chapters are not imported yet; without it the whole import is checked. Standard output carries exactly one JSON envelope, printed as the last line and nothing else: `{"schema_version":"book-import-validation.v1","ok":…,"code":…,"errors":[…],"warnings":[…], …}` with the import's identity, range, pointer and the counts that were checked. Exit status is `0` when `ok` is true and `2` in every other case, including bad arguments (`USAGE`).

The codes are decided in this order, the first present naming the envelope: `NO_EXTRACTION`, `UNPARSEABLE_JSON`, `INVALID_IMPORT`, `MISSING_CHAPTER`, `WORD_COVERAGE`, plus `USAGE` for arguments. `NO_EXTRACTION` and an unreadable extraction stop the run because there is no text to check against; a record that does not parse or does not hold together stops it too; chapter and state defects are collected into one answer. `MISSING_CHAPTER` covers every defect of the chapter set — an absent file, a gap in the numbering from the import's `start_chapter`, two files for one number, a file whose name the record contradicts, a checked range that names an extraction chapter the extraction does not declare or that the import has not reached. `WORD_COVERAGE` covers the two measures of plausibility: the chapter's word count must lie within 0.8×–1.2× of its extraction chapter plus an absolute slack of 20 words, and at least 85% of the chapter's eight-token runs must occur in its extraction chapter with at least 85% of that chapter's runs occurring in the chapter. The overlap bound sits below one because cleaning removes page furniture and rejoins hyphenated words, and every removal breaks the runs that straddled it; prose that was written rather than copied scores near zero, which is what makes the measure decisive.

The validator is the machine-readable proof that the universe was imported rather than written: the import is marked by `drafts/import-progress.json`, whose absence is `INVALID_IMPORT` while the state files and chapter files may still be a perfectly ordinary book. It proves the extraction exists and holds prose, the record agrees with the extraction on the upload, the chapters it names exist once in a contiguous run with their titles, the words are plausible in quantity and in sequence, the state files parse and cite existing chapters, and the canon carries its sections. It does not prove that the cleaning kept every sentence, that a canon line is true of the book, that a thread is the right thread, or that the segmentation of a boundaryless book is the one the book itself would have used: those are readings of prose and declared approximations, and `references/validator-contract.md` states them as limits of the check rather than as results.

### Boundaries, dependencies and verification

The skill writes only what the [universe folder](wiki.html#definition-universe) permits an agent to write — `canon.md`, `threads.json`, `atlas.json`, `chapters/*` and `drafts/*` — and specifically `chapters/NNNN-slug.md`, those three state files and `drafts/import-progress.json`. It never writes `universe.json`, `charter.md`, `turns/*`, `.agents/*`, `universe-title.txt` or anything under `exports/`, never translates a book, never runs `git`, never reads another universe and never reads `turns/`. It writes no `drafts/NNNN-plan.md` and no `chapters/NNNN-offer.json`: a plan is how an episode is invented and an offer is ALA's voice about what could happen next, and an imported chapter has neither until it is continued or rewritten by `scripta-ala`.

The skill requires Node.js 20 or later and uses built-in `node:` modules only (`node:fs`, `node:path`, `node:url`), with no npm package, no vendored code, no external command and no network access at runtime; `dependencies.md` records that position, including the extraction as an input contract rather than a dependency. Its tests use the built-in `node --test` runner and cover the five failure codes end to end through the real command line, the precedence between them, the incremental range of a twelve-chapter book, the plausible word band, the run-overlap measure including page-furniture removal and outright invented prose, segmentation inside and outside its band, the skipped-chapter rule, the turn journal and the oversize warning, the language decision, the usage contract, and the agreement between the published vocabulary in `schema/import.v1.json` and the constants the code uses.

The boundary of the skill is that it imports and describes. It does not write prose, does not judge whether the cleaning read well, does not settle a language mismatch in the metadata, and does not decide that a book is finished: a host that wants the whole book imported runs the turns until the record says `complete: true`, and everything written afterwards belongs to `scripta-ala` and to the separate-phase skills.
