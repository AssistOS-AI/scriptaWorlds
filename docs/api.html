System

HTTP API

The server exposes JSON routes under /api and serves the static reader on every other path. The browser interface uses this API, and a second client can use it without any change to the server: create a universe, queue a turn, follow its progress over the event stream, read chapters and download editions.

Conventions

Requests and responses are UTF-8 JSON. Request bodies carry content-type: application/json and are limited to 512 KiB. Every failure is a body of the shape {"error":{"code":"…","message":"…"}} with a matching status: 400 for invalid input, 404 for a missing universe, chapter, turn, job or route, 405 for a wrong method, 409 for a refused state transition, 413 for an oversized body, 500 for an internal failure and 502 for a failed agent run. The code is the stable part of an error and the message may be reworded; an error can additionally carry laterChapters or details when a client needs structured data to proceed.

Universe identifiers follow the pattern [a-z0-9][a-z0-9-]{2,63}. A chapter or turn number in a path is read by taking the leading digits of the segment, so /chapters/1.5 addresses chapter 1 and /chapters/2abc addresses chapter 2; a segment with no leading digits, or a negative one, is rejected with 400 BAD_NUMBER. There is no authentication and no session: every route is available to every client that can reach the address, which is why the operator controls reachability through HOST or a reverse proxy.

Server state and data

Method and path Response
GET /api/health ok, the agent command and version, the configured model, the effective concurrency limit as null when unlimited, and the uptime in milliseconds. It reads no universe and is the cheapest liveness probe.
GET /api/config The model, the accepted languages as code and label, the accepted edition formats, the concurrency limit and the chapter word band. A client builds its language selector from this response instead of hardcoding a list.
GET /api/templates?language=<code> The catalog of proposed universes with id, tags, a descriptive title, law and openings, plus a count. Each opening is a concrete first move for the story, and the catalog is assembled from a main file plus optional part files merged by identifier. The query is truncated to two characters and lowercased, the default is ro, and a value falls back to English and then to Romanian.
GET /api/table The Periodic Table of Speculative Ideas as the interface reads it, small enough to load in one request: families (the twelve families as objects with the family name, its label, the letter used in a systematic symbol, the one-sentence note saying what that family changes, and the cells that belong to it), operators (the fifteen names with their letter and one sentence saying what the operator does) and elements (the one hundred and eighty cells, each with id, the systematic symbol, the mnemonic bookSymbol, name, family, operator, a one-line gist, the prompt line the interface can drop into the request field unchanged, the ingredient sentence written for a reader — for example Neutron Life: a universe where organisms live in degenerate matter (life and evolution, extension). — and a landmark). The six prose sections the book devotes to a cell are not in this payload; they are read one cell at a time through the cell route. The data file is missing → 500 NO_TABLE.
GET /api/table/cells/:symbol What one cell offers a reader, read only when the dialog opens it: id, symbol, bookSymbol, name, family, familyLabel, the familyNote saying what that family changes, operator, the sentence operatorDoes, the essence of the idea in one line, the prompt, the ingredient sentence, seenIn with the literary landmark, and scenes — up to three nights of the course that already work this cell, each with its slug, title, sector, situation and story. The raw prose sections of the book are deliberately absent: they repeat a skeleton for all one hundred and eighty cells, so the payload carries the distilled fields instead and the dialog shows the idea, the family note, the landmark and the nights that use the cell. A symbol the table does not contain answers 404 UNKNOWN_ELEMENT.
GET /api/library The index of the library of start templates: source, note, count, templates and cellScenes. Each template entry carries slug, kind, number, title, sector, genealogy, the cells it activates and a one-line summary. cellScenes is the reverse index the cell dialog needs — for every symbol, up to three nights that work it, with the slug, title, sector, situation and story of each — so a reader can jump from one operation of the table to the nights that already use it without reading the seventy-five folders. The empty template comes first and the seventy-four nights follow, seventy-five entries in all, and an entry whose slug is not usable is dropped. The library folder is missing → 500 NO_LIBRARY.
GET /api/library/:slug One start template with everything a universe needs before its first chapter: slug, kind, number, title, sector, genealogy, cells, operator, references, prohibition, situation, story, summary, request, indications and sourceText. Each cell of the template carries the same fields as a cell of the table, including the ingredient sentence, and indications names the active operations as the book does, never by their two-letter address. request is the text that lands in the reader's field and it adds nothing generic to what the book says; indications is the same material as a labelled list — Sector, Genealogy, Prohibition when the night states one, Active cells, Situation, Central tension and Seen in — which the Library tab shows next to the request; and sourceText is the night as the book writes it, up to six thousand characters, shown in a fold. The hand-written empty template carries no indications, because there is no night behind it. A slug the library does not contain answers 404 UNKNOWN_TEMPLATE and a malformed one 400 BAD_TEMPLATE.
GET /api/jobs/:jobId One job snapshot. Jobs exist only while the server process runs, so an identifier from an earlier process answers NOT_FOUND; the durable record of that work is the universe detail.

Universes

Method and path Effect
GET /api/universes Every universe on disk, sorted by updatedAt descending, with the law, the premise, the status, the language, the model, the chapter count, the last chapter title and the autoTitle flag that says whether the title is still provisional.
POST /api/universes Creates a universe from a library slug, a list of elements, a templateId, an optional title, law, premise (or its older name opening), prompt, language and start. With library the universe is built from that start template, and elements sent next to it are added on top of the template's own cells, deduplicated and cut at six; with elements alone the law is composed only from the chosen cells and from any element the reader proposed. A value the client sent always wins over the named template, which fills only the gaps. Answers 201 with the universe and a job that is null unless start is true. An overlong title is BAD_TITLE, an unsupported language is BAD_LANGUAGE, and an identifier that cannot be made free is ID_TAKEN. A universe created without a title starts with a provisional name, is named by its first chapter and keeps the earlier descriptive line as its summary.
GET /api/universes/:id The reading view: universe, chapters, turns, threads, a bounded canon summary, exports, activeJob and queuedJobs. A chapter entry carries its number, slug, title, word count, byte size, its producing turnNumber and its offer. The rewritten flag and the archived version count are added only by the single-chapter route, so a client that needs them reads that chapter.
POST /api/universes/:id/settings Changes the language of the book when the body carries language, and answers the universe. An empty body returns the current record.
POST /api/universes/:id/close and POST /api/universes/:id/open Set the status and answer the universe. Closing does not cancel work that is already queued, but a chapter turn for a closed universe answers CLOSED.
GET /api/universes/:id/ideas Up to four continuation ideas derived from the universe's own state, each with a label, a prompt and a source of promise, thread, deferred, latest or timejump. It performs no agent work.

Creation is one body with three ways of saying where the world comes from, and every way can be combined with a law, a premise and a first request of the client's own. library names a start template and brings its law, its premise, its cells and a provisional title with it; elements is the compound of at most six ingredients, each written as a symbol of the table, as an object with a symbol, or as a proposed element carrying custom: true and a name; templateId names an entry of the older proposed-universe catalog. The two are not alternatives: when a body carries library and elements together, the cells of the template come first, the ingredients the reader chose follow, an ingredient already present is dropped — a table cell by its symbol, a proposed element by its name — and the compound is cut at six, so a template built from two cells accepts four more. A list of more than six entries sent on its own is refused with BAD_ELEMENTS and the message Six ingredients are the most a universe law can hold. Remove one first. The starting situation is read from premise first and from opening second, so an older client that still sends opening keeps working while the reader interface sends premise. The composed law must be at least one sentence, otherwise the answer is BAD_LAW; a symbol the table does not contain is UNKNOWN_ELEMENT; a list that is not an array, that holds something other than a symbol or an object, or that carries more than six entries is BAD_ELEMENTS; a proposed element with a family or an operator the table does not have is BAD_ELEMENT_FAMILY or BAD_ELEMENT_OPERATOR, and one whose name is unusable is BAD_ELEMENT_NAME; and a library slug that is unknown is UNKNOWN_TEMPLATE while a malformed one is BAD_TEMPLATE. The first chapter request is the reader's own prompt, then the request text of the chosen template, and only when both are empty a structured request built by the server from the law, the premise and the ingredients.

The ingredients travel with the book. They are resolved before anything is written, stored in universe.json as elements, listed in canon.md under Ingredients, named in the AGENTS.md of the universe and repeated in every chapter and rewrite prompt, so the recipe defines what the world can do rather than a summary of it. The stored entry keeps the two-letter symbol of its cell, and that symbol is only an address: it identifies the cell inside the table and inside the structured data, and the prose that describes a world never carries it. The composed law, the ingredient list of canon.md, the AGENTS.md of the universe folder, the first-chapter request and the chapter and rewrite prompts use the ingredient sentence, and npm run check asserts that neither the ingredient lines nor the composed law nor that AGENTS.md carries a two-letter code. The symbol itself lives on in the structured data — universe.json and the table routes — where it is the key that names a cell, and in the grid and the library list, which show it as the address of the operations a world is built from.

Chapters, turns and rewrites

Method and path Effect
GET /api/universes/:id/chapters/:number One chapter with its Markdown, its normalized offer, the producing turn, its rewritten flag and its archived version count. Chapter files are not served as static files; this route is the only way to read one.
GET /api/universes/:id/turns/:number The full turn record, including the agent's answer and the composed log of what it did. The number is a turn number, not a chapter number; the mapping is the turnNumber field of a chapter.
POST /api/universes/:id/turns Queues a chapter or export turn from message, kind and, for an edition, format of docx, pdf or both. Always answers 202 with a job, including when the universe is already busy, because requests wait in that universe's queue instead of being refused.
POST /api/universes/:id/turns/:number/retry Restarts an interrupted or failed turn with the same request and the same turn number. Any other status is NOT_RETRYABLE, and an unknown turn is NOT_FOUND.
POST /api/universes/:id/chapters/:number/rewrite Starts a rewrite from instructions of at least ten characters and an optional dropLater. The route validates and enqueues; when the job runs under the per-universe execution lock the current version is archived together with its offer, the later chapters are archived before they are dropped, and the book is rewound to the state before that chapter. The answer is 202 with the job and the dropped chapter numbers. Without dropLater, a rewrite that would discard later chapters answers 409 with the code LATER_CHAPTERS and a laterChapters array inside the error object, which is what a client uses to confirm the loss. The request is bound to the version it was written for, so a rewrite that waited behind another turn and met a changed target, or a later chapter it never authorised, answers 409 STALE_REQUEST without rewriting anything; a book whose accepted state could not be restored answers 409 RECOVERY_REQUIRED, and a turn refused because the server is stopping answers 503 SHUTTING_DOWN.

A writing request may also carry sourceChapter, the accepted chapter the reader was looking at, which is recorded on the turn and refused with 400 BAD_NUMBER when it does not name an accepted chapter. It may also carry directions — the short instructions a separate design or craft phase produced and the author accepted — with the approval record they came from; they are stated in the prompt under the law, recorded with the turn, and a malformed list answers 400 BAD_DIRECTIONS. Instructions shorter than one sentence are rejected with BAD_INSTRUCTIONS, an unknown chapter with NOT_FOUND, and a closed universe with CLOSED. Once confirmed, dropLater removes and archives the later chapters, and the rewrite runs as a new turn so the discussion log of the book stays complete.

Editions and files

An edition is produced by the same pipeline as a chapter: the agent writes exports/edition.json, runs the print renderer, and the server fails the turn with NO_EXPORT when no edition file appeared. The universe detail then lists each file with its format, size, creation time and URL, and GET /api/files/:id/:name serves it as an attachment. The name must match a .pdf or .docx file inside that universe's exports/ folder, otherwise the answer is BAD_NAME, so the route cannot be used to read any other file.

Design and review phases

These routes run the separate design and review skills over a frozen packet of one accepted version. They live outside universes/: the host captures a packet into the assessment workspace, the skill publishes there, and no phase ever writes into a book, so a report can never roll back a chapter. A packet is captured only while the book is stable, and the runs are deduplicated by phase, version, profile and trigger.

Method and path Response
POST /api/universes/:id/assessments Starts one separate-phase review of a frozen accepted version. The body carries phase (continuity or metrics); a profile is optional, because a generic review uses the host's own profile and needs no hand-authored JSON. Optional annotations reach both phases; mode says who produces the semantic observations of the run — generic, deterministic or supplied — and defaults to the operator's ASSESSMENT_MODE; a corpus of {manifest, files} reaches the metrics phase with the text of every reference it names; scope, chapters, aggregate, intention and weights shape a generic run; fromTurn captures from the snapshot of a finished turn. A turn that is queued or running makes the capture answer 409 UNSTABLE_VERSION; a missing profile answers NO_PROFILE. The answer is 202 with the run record, or with the existing run and deduplicated: true when the same phase, version, profile and trigger were already reviewed.
GET /api/universes/:id/assessments The runs of that book, newest first, each with historical: true when its version is no longer the accepted one, plus the declared arc-completion events.
GET /api/universes/:id/assessments/:runId One run: phase, trigger, version, scope, profile hash, status, outputs and the envelope the phase printed. When the run asked a model for its observations, the record also carries annotation_mode, annotation_model, annotation_prompt_version, annotation_attempts, annotation_errors, generated_annotations and packet_intact.
POST /api/universes/:id/assessments/:runId {"action":"cancel"} stops a queued or running review (NOT_CANCELLABLE when it settled); {"action":"retry"} runs the same frozen packet again, which is how an interrupted review continues.
POST /api/universes/:id/arc-events Declares an arc complete against the current accepted version: {"arcId":"arc-ledger","note":"…","profile":{…}} writes a versioned event outside the book and starts the assessment the profile implies. A planned completed flag in a design proposal is not an event.
POST /api/universes/:id/approvals Records the human decision on a design or craft proposal: {"proposal":{…}|"path","decision":"approved|declined","reviewer":"…","directions":["…"],"version":"sha256:…"} → 201 with the approval. A proposal written against another version answers STALE_REQUEST, a second decision on the same proposal and version answers ALREADY_DECIDED, and only an approved proposal may carry directions.
GET /api/universes/:id/approvals The approvals recorded for that book, newest first. This is where a later writing request takes the directions it carries.
GET /api/universes/:id/arc-events The arc-completion events of that book, newest first.

The mode field decides who produces the semantic observations of a review — the judgements a model can make about the text. supplied means the caller brought an annotations document, generic means the host asks the configured evaluator for the observations, and deterministic means nobody does, so the model-only results stay unavailable with their reason. Supplied annotations and a generated mode are mutually exclusive and answer 400 BAD_MODE, as does a value outside the three, so a request that carries annotations is a supplied run and a request that names generic cannot bring them as well.

In generic mode the host runs the annotation stage before the phase: it writes the prompt from the vocabulary the report skill publishes at skills/scripta-metrics-report/schema/annotations.v1.json, runs OMP_BIN once in the run workspace with the model from SCRIPTAS_MODEL, and validates the answer itself — the schema version, the source version it claims, evidence that resolves to the exact bytes of the frozen packet, and the bounds on evidence and segments. A rejected answer gets exactly one repair call whose prompt names the fields that failed; a model that still produces no usable document fails the run with an annotation stage: error on the run, and the run is recorded as failed with its reason before the caller hears about it, so the cause survives a restart.

The accepted document is stored at generated/annotations.json beside the run and never inside the frozen packet, and it is passed to the metrics phase by absolute path; the packet keeps exactly the bytes the review was asked about, which packet_intact records. The model work belongs to the run rather than to the request: this route captures the packet, writes the run record and answers at once with the run queued or already running, and the annotation stage then runs before the phase, so no caller holds an HTTP request open for the minutes an evaluator may take and the interface can show the state from the first moment. A stage that produces no usable document ends the run as an error whose message begins annotation stage:, with every attempt, its exit code, its answer length and the validation errors kept on the record, and nothing published; a retry reuses the document it already accepted rather than paying for another reading. The annotation stage itself never changes the book, and the metrics phase never calls a model: it is spawned as a plain Node.js process which reads the packet, the profile, the corpus and the annotations and nothing else, so a reported number can be re-rendered without spending model budget.

Book import

These routes take a book the team uploaded — a PDF or a DOCX — into a universe of its own. The upload is stored outside universes/, its text is extracted without a model, and the store receives its chapters through bounded import turns guided by the import skill, so an imported book can afterwards be reviewed, analysed, rewritten chapter by chapter and exported exactly like a book written here.

Method and path Response
POST /api/imports Uploads one book. The body is the file itself with Content-Type: application/octet-stream, its name in the X-Filename header and optionally X-format: pdf|docx. The bytes are hashed and counted as they arrive, and a body over IMPORT_MAX_BYTES answers 413 IMPORT_TOO_LARGE during the transfer. Answers 202 {"import":Import} with the record in state received.
GET /api/imports Every import, newest first, with the size limit and the word bound this deployment accepts.
GET /api/imports/:id One import with its progress: how many of the book's chapters are already in the store, which range the next turn will carry and whether the import is complete.
POST /api/imports/:id/extract Starts the extraction and answers 202 {"import":Import}; the reader follows the record's state (received, extracting, ready or error) instead of holding a request open. A PDF with no text layer answers IMPORT_NO_TEXT on the record.
POST /api/imports/:id/universe Creates the universe for a ready import — or continues the import when it already has one — and queues the next bounded import turn. The body may carry title and language. Answers 202 {"universe":…,"turn":…,"range":…,"progress":…}; turn is null when every chapter is already imported.

An import record is book-import.v1: import_id, filename, format, sha256, bytes, state, source, created_at, extracted_at, universe_id, detected (title, author, language and whether the title came from the file or from the uploaded name), chapters with their word counts, words, warnings and error. A record whose file is gone answers 410 IMPORT_MISSING, and a step that needs an extraction which never succeeded answers 409 NOT_EXTRACTED.

The import turn is a normal turn of the store: it is queued, streamed like any other, retried when it fails, and its chapters are verified by the import skill's own validator before the turn counts as done. Nothing about the pipeline writes a chapter itself — the text of an uploaded book reaches the store only through that turn.

Live events

GET /api/universes/:id/events answers text/event-stream. Without a job query it covers the whole universe: it replays the buffered events of the running turn and then forwards the events of every turn of that universe, including turns queued later, and every payload carries its jobId. With ?job=<jobId> it covers that job only and validates that the job belongs to the universe.

Event type Payload
job A job snapshot, emitted when a turn is enqueued and when it starts running.
phase A short progress line, for example that the agent is writing or rewriting a chapter, or that the result is being verified.
delta A fragment of the agent's live text, which a reader sees as the chapter being written.
tool A tool call with state of start or end, the tool name, a short detail and, on the end event, whether it succeeded.
done The final job snapshot, including the chapter title, the produced exports, the warnings and the offer.
error The failure message and the job, after the state has already been rolled back.
refresh Emitted on the universe stream after a turn finished, so a client can reload the universe without deciding which events matter.

At most 800 events are buffered per job, so a client that connects in the middle of a run receives a recent history rather than the whole run. The stream is the live path and never the only path: the universe detail carries activeJob and queuedJobs precisely so that a reloaded page can reconstruct work in progress, and a client behind a buffering proxy can poll the job route instead. The route table and the exact payload fields are specified in DS005-http-api.
